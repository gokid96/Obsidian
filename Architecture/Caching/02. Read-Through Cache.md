
## 기본 개념
- Cache-Aside와 비슷하지만, **캐시 라이브러리/프레임워크가 DB 조회를 대신** 수행
- 애플리케이션은 항상 캐시에만 요청하고, miss 시 캐시가 알아서 DB에서 로드
- 캐시가 데이터 로딩의 책임을 가짐

## 동작 흐름

```
[Client] → [App] → [Cache] → Cache Hit → 반환
                             → Cache Miss → [Cache가 직접 DB 조회] → 캐시 저장 → 반환
```

> Cache-Aside와 차이: App이 DB를 직접 호출하지 않는다. Cache가 DB 호출을 한다.

## 코드 예시

```java
// Spring Cache 추상화 — 대표적인 Read-Through 방식
@Cacheable(value = "users", key = "#userId")
public User getUser(String userId) {
    // Cache miss일 때만 이 메서드가 실행됨
    // 캐시 프레임워크가 자동으로 결과를 캐싱
    return userRepository.findById(userId);
}
```

```java
// Guava LoadingCache — Read-Through 구현
LoadingCache<String, User> userCache = CacheBuilder.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(30, TimeUnit.MINUTES)
    .build(new CacheLoader<String, User>() {
        @Override
        public User load(String userId) {
            // Cache miss 시 자동 호출
            return userRepository.findById(userId);
        }
    });

// 사용: 캐시에만 요청하면 됨
User user = userCache.get(userId);
```

```python
# Python functools.lru_cache — 간단한 Read-Through
from functools import lru_cache

@lru_cache(maxsize=1024)
def get_user(user_id: str) -> dict:
    return db.query("SELECT * FROM users WHERE id = %s", user_id)
```

## Cache-Aside vs Read-Through 비교

| 항목 | Cache-Aside | Read-Through |
|------|------------|--------------|
| DB 호출 주체 | **애플리케이션** | **캐시** |
| 코드 복잡도 | 캐시 로직 직접 작성 | 프레임워크가 처리 |
| 유연성 | 높음 (세밀한 제어) | 낮음 (프레임워크 의존) |
| 대표 구현 | Redis 직접 사용 | Spring Cache, Guava |

## 장점
- 애플리케이션 코드가 깔끔해짐 (캐시 로직 분리)
- 캐시 로직 중복 제거
- 프레임워크가 동시성 처리를 해주는 경우가 많음

## 단점
- 캐시 라이브러리/프레임워크에 의존
- 세밀한 캐시 제어가 어려움 (TTL 조건부 설정 등)
- 첫 요청은 여전히 느림 (Cold Start)

## 실무 포인트

> [!tip] 언제 쓰나?
> - Spring Cache, Guava Cache 등 프레임워크를 사용할 때
> - 동일한 캐시 패턴이 여러 곳에서 반복될 때
> - 캐시 로직을 비즈니스 로직에서 분리하고 싶을 때
