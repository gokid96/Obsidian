
## 기본 개념
- **여러 계층의 캐시**를 두어 속도와 확장성을 모두 확보
- 일반적으로 L1 (로컬 메모리) → L2 (분산 캐시) → DB 순서로 조회
- CPU 캐시(L1/L2/L3)의 개념과 동일한 원리

## 계층 구조

```
[Client] → [L1: Local Cache] → [L2: Distributed Cache] → [DB]
            (Caffeine 등)        (Redis, Memcached)
            ~1ms                  ~5ms                    ~50ms+
            프로세스 내            네트워크 필요             가장 느림
            용량 작음              용량 큼                  원본 데이터
```

## 코드 예시

```java
@Service
public class MultiLayerCacheService {
    
    // L1: 로컬 캐시 (Caffeine)
    private final Cache<String, User> localCache = Caffeine.newBuilder()
        .maximumSize(1_000)
        .expireAfterWrite(5, TimeUnit.MINUTES)  // 짧은 TTL
        .build();
    
    // L2: 분산 캐시 (Redis)
    private final RedisTemplate<String, User> redisCache;
    
    public User getUser(String userId) {
        String key = "user:" + userId;
        
        // 1. L1 로컬 캐시 확인
        User user = localCache.getIfPresent(key);
        if (user != null) {
            return user;  // 가장 빠름 (~1ms)
        }
        
        // 2. L2 Redis 확인
        user = redisCache.opsForValue().get(key);
        if (user != null) {
            localCache.put(key, user);  // L1에도 저장
            return user;  // 빠름 (~5ms)
        }
        
        // 3. DB 조회
        user = userRepository.findById(userId);
        redisCache.opsForValue().set(key, user, Duration.ofMinutes(30));  // L2 저장
        localCache.put(key, user);  // L1 저장
        return user;
    }
    
    public void updateUser(String userId, User user) {
        String key = "user:" + userId;
        userRepository.save(user);
        
        // 모든 계층 무효화
        localCache.invalidate(key);
        redisCache.delete(key);
    }
}
```

```python
from cachetools import TTLCache

class MultiLayerCache:
    def __init__(self):
        # L1: 로컬 메모리 (작은 용량, 짧은 TTL)
        self.l1 = TTLCache(maxsize=1000, ttl=300)  # 5분
    
    def get(self, key: str) -> dict:
        # L1 확인
        if key in self.l1:
            return self.l1[key]
        
        # L2 확인 (Redis)
        cached = redis.get(key)
        if cached:
            data = json.loads(cached)
            self.l1[key] = data  # L1에 승격
            return data
        
        # DB 조회
        data = db.find(key)
        redis.setex(key, 1800, json.dumps(data))  # L2 저장
        self.l1[key] = data  # L1 저장
        return data
    
    def invalidate(self, key: str):
        self.l1.pop(key, None)
        redis.delete(key)
```

## L1 vs L2 비교

| 특성 | L1 (Local) | L2 (Distributed) |
|------|-----------|------------------|
| 속도 | ~1ms (메모리 직접 접근) | ~5ms (네트워크) |
| 용량 | 작음 (JVM 힙) | 큼 (수십GB) |
| 공유 | 인스턴스별 독립 | 모든 인스턴스 공유 |
| TTL | 짧게 (1~5분) | 길게 (10~60분) |
| 일관성 | 인스턴스 간 불일치 가능 | 일관적 |
| 대표 기술 | Caffeine, Guava, HashMap | Redis, Memcached |

## 주의: L1 캐시 일관성 문제

```
[Server A] L1: user:1 = {name: "Kim"}
[Server B] L1: user:1 = {name: "Kim"}

→ Server A에서 user:1 업데이트 → {name: "Lee"}
→ Server A의 L1, L2(Redis) 모두 갱신

[Server A] L1: user:1 = {name: "Lee"} ✅
[Server B] L1: user:1 = {name: "Kim"} ❌ ← stale!
```

## 실무 포인트

> [!tip] 언제 쓰나?
> - 읽기 트래픽이 매우 높은 서비스
> - Redis 호출도 줄이고 싶을 때
> - 여러 서버 인스턴스가 동일 데이터를 자주 읽을 때

> [!warning] L1 TTL은 짧게
> L1 캐시의 TTL을 짧게 잡아야 인스턴스 간 불일치를 최소화할 수 있다.
> 완벽한 일관성이 필요하면 L1을 사용하지 않거나 Pub/Sub 무효화를 구현.
