
## 기본 개념
- 서비스 시작 시 또는 주기적으로 **자주 사용되는 데이터를 미리 캐시에 로드**
- Cold Start 문제 해결 → 첫 요청부터 빠른 응답
- Cache Stampede 예방 효과

## 동작 흐름

```
[서비스 시작 / 스케줄러]
     │
     ├── 인기 상품 목록 → DB 조회 → 캐시 저장
     ├── 설정 데이터 → DB 조회 → 캐시 저장  
     └── 자주 쓰는 사용자 데이터 → DB 조회 → 캐시 저장
     │
[서비스 준비 완료] → 트래픽 수신 시작
```

## 코드 예시

### 서비스 시작 시 워밍

```java
@Component
public class CacheWarmer implements ApplicationRunner {
    
    @Autowired
    private ProductRepository productRepository;
    @Autowired
    private RedisTemplate<String, Object> cache;
    
    @Override
    public void run(ApplicationArguments args) {
        warmPopularProducts();
        warmAppConfig();
        log.info("캐시 워밍 완료");
    }
    
    private void warmPopularProducts() {
        // 인기 상품 Top 100 미리 캐싱
        List<Product> popular = productRepository.findTop100ByOrderBySalesDesc();
        for (Product p : popular) {
            cache.opsForValue().set(
                "product:" + p.getId(), 
                p, 
                Duration.ofHours(1)
            );
        }
        log.info("인기 상품 {} 건 캐시 워밍 완료", popular.size());
    }
    
    private void warmAppConfig() {
        Map<String, String> config = configRepository.findAll();
        cache.opsForHash().putAll("config:app", config);
    }
}
```

```python
# FastAPI 시작 시 캐시 워밍
from fastapi import FastAPI
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 서비스 시작 시
    await warm_caches()
    yield
    # 서비스 종료 시 정리

app = FastAPI(lifespan=lifespan)

async def warm_caches():
    # 인기 상품 캐싱
    popular_products = db.query(
        "SELECT * FROM products ORDER BY sales DESC LIMIT 100"
    )
    for product in popular_products:
        redis.setex(
            f"product:{product['id']}", 
            3600, 
            json.dumps(product)
        )
    
    # 카테고리 목록 캐싱
    categories = db.query("SELECT * FROM categories WHERE active = true")
    redis.setex("categories:all", 86400, json.dumps(categories))
    
    print(f"캐시 워밍 완료: 상품 {len(popular_products)}건, 카테고리 {len(categories)}건")
```

### 스케줄러 기반 주기적 워밍

```python
# 주기적으로 인기 데이터 갱신 (TTL 만료 전에)
from apscheduler.schedulers.background import BackgroundScheduler

scheduler = BackgroundScheduler()

@scheduler.scheduled_job('interval', minutes=25)  # TTL(30분)보다 짧은 주기
def warm_trending():
    """트렌딩 데이터는 만료 전에 미리 갱신"""
    trending = db.query("SELECT * FROM posts ORDER BY score DESC LIMIT 50")
    redis.setex("feed:trending", 1800, json.dumps(trending))

@scheduler.scheduled_job('cron', hour=0)  # 매일 자정
def warm_daily():
    """일별 데이터 미리 준비"""
    stats = db.query("SELECT * FROM daily_stats WHERE date = CURRENT_DATE")
    redis.setex("stats:today", 86400, json.dumps(stats))
```

### 이벤트 기반 워밍

```java
// 상품 업데이트 이벤트 → 연관 캐시 미리 갱신
@EventListener
public void onProductUpdated(ProductUpdatedEvent event) {
    Product product = productRepository.findById(event.getProductId());
    
    // 변경된 상품 캐시 갱신
    cache.set("product:" + product.getId(), product, Duration.ofHours(1));
    
    // 연관된 카테고리 목록도 미리 갱신
    List<Product> categoryProducts = productRepository
        .findByCategoryId(product.getCategoryId());
    cache.set(
        "category:" + product.getCategoryId() + ":products",
        categoryProducts, 
        Duration.ofHours(1)
    );
}
```

## 워밍 대상 선정 기준

| 기준 | 예시 |
|------|------|
| **접근 빈도 높음** | 인기 상품, 메인 페이지 데이터 |
| **생성 비용 높음** | 복잡한 집계 쿼리 결과 |
| **변경 빈도 낮음** | 설정값, 카테고리 목록 |
| **Cold Start 영향 큼** | 서비스 시작 직후 대량 트래픽 |

## 실무 포인트

> [!tip] 워밍 전략
> - 서비스 시작 워밍: **Readiness Probe와 연동** → 워밍 완료 후에 트래픽 수신
> - 스케줄러 워밍: TTL보다 짧은 주기로 갱신 → Stampede 방지
> - 워밍 데이터가 너무 많으면 **우선순위** 지정 (인기순, 비용순)

```yaml
# Kubernetes - 워밍 완료 후 트래픽 수신
readinessProbe:
  httpGet:
    path: /health/ready  # 캐시 워밍 완료 시 200 반환
    port: 8080
  initialDelaySeconds: 30
```

> [!warning] 주의사항
> - 워밍에 너무 오래 걸리면 배포 속도 저하 → 비동기 + 우선순위
> - 불필요한 데이터까지 워밍하면 메모리 낭비
> - DB 부하 고려: 서비스 시작 시 대량 쿼리 → DB 순간 부하
