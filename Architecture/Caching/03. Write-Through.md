
## 기본 개념
- 데이터를 쓸 때 **캐시와 DB에 동시에(동기적으로)** 저장
- 캐시가 항상 최신 데이터를 보유 → **강한 일관성**
- 쓰기 요청이 캐시를 거쳐 DB까지 완료되어야 응답

## 동작 흐름

```
[Client] → [App] → [Cache에 쓰기] → [Cache가 DB에 쓰기] → 완료 응답
                    (동기적으로 둘 다 완료될 때까지 대기)
```

## 코드 예시

```java
// Spring Cache — Write-Through
@CachePut(value = "users", key = "#user.id")
public User updateUser(User user) {
    // DB에 저장 + 캐시에도 자동 반영 (동기)
    return userRepository.save(user);
}
```

```python
# 수동 Write-Through 구현
def update_user(user_id: str, data: dict):
    # 1. DB에 저장
    db.execute(
        "UPDATE users SET name=%s, email=%s WHERE id=%s",
        data["name"], data["email"], user_id
    )
    
    # 2. 캐시에도 동기적으로 저장
    redis.setex(
        f"user:{user_id}", 
        1800,  # TTL 30분
        json.dumps(data)
    )
    
    # 둘 다 완료되어야 응답
    return data
```

```java
// Redis + Java 수동 구현
public void updateUser(String userId, User user) {
    // 트랜잭션으로 묶어서 일관성 보장
    try {
        userRepository.save(user);           // DB 쓰기
        cache.set("user:" + userId, user);   // 캐시 쓰기
    } catch (Exception e) {
        cache.delete("user:" + userId);      // 실패 시 캐시 무효화
        throw e;
    }
}
```

## 장점
- 캐시와 DB 간 **데이터 일관성이 높음**
- 읽기 시 cache miss가 적음 (쓰기 시점에 이미 캐싱)
- 데이터 유실 위험이 낮음 (DB에 즉시 반영)

## 단점
- **쓰기 지연 증가** (캐시 + DB 두 번 쓰기)
- 쓰기가 많은 서비스에서는 성능 병목
- 자주 변경되지만 잘 읽히지 않는 데이터도 캐싱 → 메모리 낭비 가능

## 실무 포인트

> [!tip] 언제 쓰나?
> - 데이터 일관성이 매우 중요한 서비스 (결제, 재고 관리)
> - 쓰기 빈도가 낮고, 읽기 빈도가 높은 경우
> - Read-Through와 조합하면 읽기/쓰기 모두 캐시가 관리

> [!warning] 주의사항
> - 캐시 쓰기 실패 시 처리 전략 필요 (롤백 or 무효화)
> - 쓰기 빈도가 높으면 [[04. Write-Behind (Write-Back)]] 고려
