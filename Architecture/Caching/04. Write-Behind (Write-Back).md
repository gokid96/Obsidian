
## 기본 개념
- 데이터를 **캐시에만 먼저 쓰고**, DB 반영은 **비동기로 나중에** 수행
- 쓰기 응답이 빠름 (캐시 쓰기만 기다리면 됨)
- 일정 주기 또는 일정량이 쌓이면 DB에 배치로 반영

## 동작 흐름

```
[Client] → [App] → [Cache에 쓰기] → 즉시 응답
                          │
                          └──(비동기)──→ [DB에 배치 쓰기]
```

## 코드 예시

```python
import threading
import time
from collections import defaultdict

class WriteBehindCache:
    def __init__(self):
        self.cache = {}
        self.dirty_keys = set()  # DB에 아직 반영 안 된 키
        self._start_flush_thread()
    
    def set(self, key: str, value: dict):
        """캐시에만 쓰고 즉시 반환"""
        self.cache[key] = value
        self.dirty_keys.add(key)  # dirty 마킹
    
    def get(self, key: str):
        return self.cache.get(key)
    
    def _flush_to_db(self):
        """주기적으로 dirty 데이터를 DB에 반영"""
        while True:
            time.sleep(5)  # 5초마다 flush
            if self.dirty_keys:
                keys_to_flush = list(self.dirty_keys)
                for key in keys_to_flush:
                    try:
                        db.save(key, self.cache[key])
                        self.dirty_keys.discard(key)
                    except Exception as e:
                        print(f"DB flush 실패: {key}, {e}")
                        # 실패한 키는 dirty에 남겨둠 → 재시도
    
    def _start_flush_thread(self):
        t = threading.Thread(target=self._flush_to_db, daemon=True)
        t.start()
```

```java
// Spring + 스케줄러 기반 Write-Behind
@Service
public class WriteBehindService {
    
    private final RedisTemplate<String, User> cache;
    private final ConcurrentLinkedQueue<String> dirtyKeys = new ConcurrentLinkedQueue<>();
    
    public void updateUser(String userId, User user) {
        // 캐시에만 쓰고 즉시 반환
        cache.opsForValue().set("user:" + userId, user);
        dirtyKeys.add(userId);
    }
    
    @Scheduled(fixedDelay = 5000) // 5초마다 DB에 반영
    public void flushToDB() {
        List<String> batch = new ArrayList<>();
        String key;
        while ((key = dirtyKeys.poll()) != null) {
            batch.add(key);
        }
        
        if (!batch.isEmpty()) {
            // 배치로 DB에 저장
            userRepository.batchUpdate(batch.stream()
                .map(id -> cache.opsForValue().get("user:" + id))
                .collect(Collectors.toList()));
        }
    }
}
```

## 장점
- **쓰기 성능이 매우 빠름** (캐시 쓰기만 기다림)
- DB 부하 감소 (배치로 모아서 쓰기)
- 같은 키에 대한 여러 번 쓰기 → 마지막 값만 DB에 반영 (write coalescing)

## 단점
- **캐시 장애 시 데이터 유실 위험** (아직 DB에 안 쓴 데이터)
- 캐시와 DB 간 일시적 불일치
- 구현 복잡도 높음 (flush 로직, 실패 처리, 재시도)
- 디버깅이 어려움

## 실무 포인트

> [!tip] 언제 쓰나?
> - 쓰기가 매우 빈번한 서비스 (좋아요 수, 조회수, 실시간 로그)
> - 약간의 데이터 유실이 허용되는 경우
> - DB 쓰기 비용을 줄이고 싶을 때

> [!danger] 데이터 유실 방지
> - Redis를 사용한다면 **AOF (Append Only File)** 활성화
> - flush 실패 시 **재시도 큐** 또는 **Dead Letter Queue** 구성
> - 중요 데이터에는 사용하지 않는 것이 안전
