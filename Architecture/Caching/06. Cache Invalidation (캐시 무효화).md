## 기본 개념
- 캐시된 데이터가 원본(DB)과 달라지면 **stale data** 문제 발생
- 캐시를 적절한 시점에 삭제/갱신하는 전략이 캐시 무효화

## 무효화 전략

### 1. TTL (Time-To-Live)
가장 단순한 방식. 일정 시간이 지나면 자동으로 캐시 만료.

```python
# Redis TTL 설정
redis.setex("user:123", 1800, json.dumps(user))  # 30분 후 자동 삭제

# 조건부 TTL — 데이터 성격에 따라 다르게
redis.setex("config:app", 86400, data)      # 설정값: 24시간
redis.setex("feed:timeline", 60, data)      # 타임라인: 1분
redis.setex("session:abc", 3600, data)      # 세션: 1시간
```

> [!tip] TTL 설정 가이드
> - 자주 변하는 데이터 → 짧은 TTL (1~5분)
> - 거의 안 변하는 데이터 → 긴 TTL (1~24시간)
> - 변경 시점이 예측 가능 → 이벤트 기반 무효화가 더 적합

### 2. Event-Based Invalidation (이벤트 기반)
데이터가 변경되면 **이벤트를 발행**하여 관련 캐시를 삭제.

```java
// 사용자 정보 변경 시 캐시 무효화
@CacheEvict(value = "users", key = "#userId")
public void updateUser(String userId, User user) {
    userRepository.save(user);
}

// 여러 캐시 동시 무효화
@Caching(evict = {
    @CacheEvict(value = "users", key = "#userId"),
    @CacheEvict(value = "userProfiles", key = "#userId")
})
public void deleteUser(String userId) {
    userRepository.deleteById(userId);
}
```

```python
# Kafka 이벤트 기반 캐시 무효화
def on_user_updated(event):
    """사용자 변경 이벤트 수신 시 캐시 삭제"""
    user_id = event["user_id"]
    redis.delete(f"user:{user_id}")
    redis.delete(f"user_profile:{user_id}")
    redis.delete(f"user_posts:{user_id}")  # 연관 캐시도 삭제
```

### 3. Version-Based (버전 기반)
데이터에 버전 번호를 부여하고, 버전이 다르면 캐시를 갱신.

```python
def get_product(product_id: str) -> dict:
    cached = redis.hgetall(f"product:{product_id}")
    
    # DB에서 현재 버전 확인 (가벼운 쿼리)
    current_version = db.query(
        "SELECT version FROM products WHERE id = %s", product_id
    )
    
    if cached and cached["version"] == str(current_version):
        return json.loads(cached["data"])  # 버전 일치 → 캐시 사용
    
    # 버전 불일치 → DB에서 새로 조회
    product = db.query("SELECT * FROM products WHERE id = %s", product_id)
    redis.hset(f"product:{product_id}", mapping={
        "data": json.dumps(product),
        "version": str(current_version)
    })
    return product
```

### 4. 패턴별 무효화 (Key Pattern)

```python
# 특정 패턴의 캐시 일괄 삭제
def invalidate_user_caches(user_id: str):
    """사용자 관련 모든 캐시 삭제"""
    keys = redis.keys(f"*:{user_id}:*")  # 패턴 매칭
    if keys:
        redis.delete(*keys)

# ⚠️ KEYS 명령은 프로덕션에서 사용 금지 (블로킹)
# 대안: SCAN 사용
def safe_invalidate(pattern: str):
    cursor = 0
    while True:
        cursor, keys = redis.scan(cursor, match=pattern, count=100)
        if keys:
            redis.delete(*keys)
        if cursor == 0:
            break
```

## Delete vs Update 전략

| 전략 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **Delete** (삭제) | 캐시 키를 삭제, 다음 읽기에서 갱신 | 단순, 안전 | 다음 읽기 시 miss |
| **Update** (갱신) | 캐시 값을 새 값으로 교체 | miss 없음 | race condition 위험 |

> [!warning] 실무에서는 Delete를 권장
> Update는 동시 요청 시 순서가 꼬여 stale data가 남을 수 있다.
> Delete 후 Cache-Aside로 다시 로드하는 것이 더 안전.

## 실무 포인트

> [!tip] 일반적인 조합
> - **TTL + Event-Based**: TTL을 안전망으로, 이벤트로 즉시 무효화
> - 이벤트 처리가 실패해도 TTL이 만료되면 결국 갱신됨

> [!danger] 주의사항
> - `redis.keys()` 는 프로덕션에서 절대 사용하지 않기 (O(N) 블로킹)
> - 연관 캐시 무효화를 빠뜨리지 않도록 체크리스트 관리
> - 분산 환경에서는 캐시 무효화 전파 지연 고려
