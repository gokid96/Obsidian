## 기본 개념
- 가장 널리 사용되는 캐싱 패턴
- **애플리케이션**이 캐시와 DB를 직접 관리한다
- 캐시에 데이터가 없을 때만(cache miss) DB에서 조회 후 캐시에 저장

## 동작 흐름

```
[Client] → [App] → 캐시 조회
                     ├── Cache Hit → 캐시에서 반환
                     └── Cache Miss → DB 조회 → 캐시에 저장 → 반환
```

## 코드 예시

```java
public User getUser(String userId) {
    // 1. 캐시에서 먼저 조회
    User user = cache.get("user:" + userId);
    
    if (user != null) {
        return user; // Cache Hit
    }
    
    // 2. Cache Miss → DB 조회
    user = userRepository.findById(userId);
    
    // 3. 캐시에 저장 (TTL 설정)
    cache.set("user:" + userId, user, Duration.ofMinutes(30));
    
    return user;
}
```

```python
# Redis + Python 예시
def get_user(user_id: str) -> dict:
    # 1. 캐시 조회
    cached = redis.get(f"user:{user_id}")
    if cached:
        return json.loads(cached)
    
    # 2. DB 조회
    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    
    # 3. 캐시 저장 (TTL 30분)
    redis.setex(f"user:{user_id}", 1800, json.dumps(user))
    
    return user
```

## 장점
- 구현이 단순하고 이해하기 쉽다
- 실제로 요청된 데이터만 캐싱 → 메모리 효율적
- 캐시 장애 시에도 DB에서 직접 조회 가능 (내결함성)

## 단점
- 첫 요청은 항상 cache miss → **Cold Start 문제**
- 캐시와 DB 간 **데이터 불일치** 가능 (DB가 변경되어도 캐시는 그대로)
- 매 요청마다 캐시 확인 + miss 시 DB 조회 + 캐시 저장 → 코드 복잡도

## 실무 포인트

> [!tip] 언제 쓰나?
> - 읽기가 많고 쓰기가 적은 서비스 (게시글 조회, 사용자 프로필 등)
> - 캐시 장애에도 서비스가 동작해야 할 때
> - TTL과 함께 사용하는 것이 일반적

> [!warning] 주의사항
> - **Cache Stampede**: 인기 키가 만료되면 동시에 수백 개 요청이 DB를 침 → [[07. Cache Stampede 방지]] 참고
> - TTL을 너무 길게 잡으면 stale data, 너무 짧으면 cache miss 증가
