
> 단일 DB일 때는 DB가 ACID를 알아서 보장해주지만, MSA에서 서비스별로 DB가 나뉘면 하나의 트랜잭션으로 묶을 수 없다. 그래서 아래 문제들이 발생한다.

---

## 단일 DB일 때

```sql
BEGIN TRANSACTION;
  UPDATE account SET balance = balance - 100000 WHERE user_id = 'A';  -- 출금
  UPDATE account SET balance = balance + 100000 WHERE user_id = 'B';  -- 입금
  INSERT INTO transfer_log (...);                                      -- 이체 기록
COMMIT;
```

이게 끝. 실패하면 자동 롤백, 중간 상태 안 보임, 규칙 체크도 DB가 해줌.

---

## MSA로 쪼개면

출금 → 계좌 서비스 DB 입금 → 상대방 계좌 서비스 DB 이체 기록 → 송금 서비스 DB

세 개가 전부 다른 DB. 하나의 트랜잭션으로 묶을 수가 없다.

---

## 발생하는 문제들

### 1. Atomicity 깨짐 → Saga로 해결

> A 출금 성공 → B 입금 실패 → 돈이 증발한 상태. 단일 DB였으면 자동 롤백인데, 이제는 직접 A한테 돈을 돌려주는 보상 트랜잭션을 만들어야 한다.
### 2. Isolation 부재 → 시맨틱 락으로 완화 -> Saga로 상태 전달

> A 출금 성공 → B 입금 처리 중 → 이 사이에 A가 잔액 조회. 돈은 빠졌는데 송금은 아직 안 된 중간 상태가 보인다. 단일 DB였으면 Isolation이 막아주는데, 이제는 시맨틱 락이나 상태 표시로 직접 처리해야 한다. 
### 3. Consistency 깨짐 → Outbox / 이벤트 기반으로 보장

> B 입금 성공 → 이체 기록 저장 실패 → 돈은 갔는데 기록이 없는 상태. 
> 나중에 분쟁 나면 증빙이 없다.
### 4. 동시성 문제 → 분산 락으로 해결

> 두 서비스가 동시에 같은 계좌에서 출금. 
> 잔액 100만원인데 각각 "100만원 있네?" 하고 70만원씩 출금하면 
> -40만원이 된다. 단일 DB였으면 락이 잡히는데, 서로 다른 DB니까 모른다.

---

## 정리

|ACID|단일 DB|MSA (DB 분리)|해결 패턴|
|---|---|---|---|
|**A** (원자성)|자동 롤백|보상 트랜잭션 직접 구현|Saga|
|**C** (일관성)|DB 제약조건|서비스 간 데이터 불일치 가능|Outbox, CDC, 이벤트 기반|
|**I** (격리성)|DB 락|중간 상태 노출|시맨틱 락, 상태 머신|
|**D** (지속성)|DB WAL|각 서비스 DB가 개별 보장|개별 DB에서 보장|

> MSA의 장점(독립 배포, 확장성, 장애 격리)을 얻는 대신 정합성은 직접 챙겨야 하는 트레이드오프.
