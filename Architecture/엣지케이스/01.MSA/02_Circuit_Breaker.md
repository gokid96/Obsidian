# Circuit Breaker 엣지케이스

## 1. Half-Open 상태 트래픽 조절 기준

| 항목 | 내용 |
|------|------|
| **문제** | Half-Open 상태에서 트래픽을 얼마나 흘릴 건지 |
| **왜 발생** | 너무 적게 흘리면 복구 확인이 느리고, 너무 많이 흘리면 아직 불안정한 서비스에 부하 |
| **해결** | 점진적 트래픽 증가(1% → 5% → 25% → 100%), 성공률 기반 자동 전환 |
| **트레이드오프** | 복구 판단이 느려질 수 있음 vs 섣부른 복구로 재장애 발생 |

## 2. Fallback 전략

| 항목 | 내용 |
|------|------|
| **문제** | Circuit Open 상태에서 사용자에게 뭘 보여줄 건지 |
| **왜 발생** | 하위 서비스 장애 시 사용자 경험을 완전히 차단할 수는 없음 |
| **해결** | 캐시된 데이터 반환, 기본값 반환, 기능 축소(graceful degradation), 사용자 안내 메시지 |
| **금융 예시** | 잔액 조회 서비스 장애 → 마지막 캐시된 잔액 + "최신 정보가 아닐 수 있습니다" 표시 |

## 3. Timeout vs Circuit Breaker vs Retry 조합

| 항목 | 내용 |
|------|------|
| **문제** | 세 가지를 무분별하게 조합하면 장애가 오히려 증폭됨 (Retry Storm) |
| **왜 발생** | Retry가 많으면 하위 서비스에 부하 가중, Circuit Breaker 없이 재시도만 하면 장애 전파 |
| **해결** | Timeout(빠른 실패) → Retry(멱등 요청만, 횟수 제한) → Circuit Breaker(반복 실패 시 차단) 순서 |
| **트레이드오프** | Retry가 많으면 하위 서비스 부하 가중, 적으면 일시적 오류에 취약 |
