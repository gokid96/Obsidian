# Event Sourcing 엣지케이스

## 1. 이벤트 스토어 무한 증가

| 항목 | 내용 |
|------|------|
| **문제** | 모든 상태 변경을 이벤트로 저장하므로 데이터가 계속 누적 |
| **왜 발생** | append-only 구조의 본질적 한계 |
| **해결** | 주기적 스냅샷 생성 → 스냅샷 이후 이벤트만 재생, 오래된 이벤트 아카이빙 |
| **트레이드오프** | 스냅샷 주기가 짧으면 저장 비용, 길면 복원 시간 증가 |

## 2. 이벤트 스키마 변경 — 업캐스팅

| 항목 | 내용 |
|------|------|
| **문제** | v1 이벤트와 v2 이벤트의 구조가 다르면 재생 시 호환성 문제 |
| **왜 발생** | 비즈니스 요구사항 변경으로 이벤트 필드가 추가/삭제/변경 |
| **해결** | 이벤트 업캐스터(v1 → v2 변환기) 체인, 이벤트 버전 필드 필수 포함 |
| **트레이드오프** | 업캐스터 체인이 길어지면 복잡도 증가, 성능 저하 |

## 3. 잘못된 이벤트 발행 후 하위 서비스가 이미 소비

| 항목 | 내용 |
|------|------|
| **문제** | Event Sourcing에서는 이벤트 수정 불가 (append-only), 하위 서비스가 이미 소비해버림 |
| **왜 발생** | 버그나 잘못된 비즈니스 로직으로 잘못된 이벤트 발행 |
| **해결** | 보정(Compensating) 이벤트 발행, 하위 서비스도 보정 이벤트를 처리할 수 있도록 설계 |
| **금융 예시** | 잘못된 금액의 입금 이벤트 발행 → 이미 잔액에 반영됨 → 차액 보정 이벤트 발행 필요 |
