# Idempotency (멱등성) 엣지케이스

## 1. 중복 판별 키 선택 문제

| 항목 | 내용 |
|------|------|
| **문제** | 요청 ID로 할 건지, 비즈니스 키로 할 건지에 따라 동작이 완전히 달라짐 |
| **왜 발생** | "같은 요청"의 정의가 모호한 경우 |
| **해결** | 클라이언트가 생성한 idempotency-key 헤더 사용 (UUID 등), 서버 측에서 해당 키로 중복 체크 |
| **금융 예시** | 사용자가 같은 사람에게 같은 금액을 진짜 두 번 송금하고 싶은 건지 vs 네트워크 재시도인지 → 요청 ID로 구분해야 함. 비즈니스 키(수신자+금액)로 하면 의도적 중복 송금이 차단됨 |

## 2. 멱등성 키 TTL 설정

| 항목 | 내용 |
|------|------|
| **문제** | 영구 보관하면 저장소 무한 증가, 너무 짧으면 지연된 재시도를 중복 처리 못함 |
| **왜 발생** | 멱등성 키 저장소에 대한 생명주기 관리 필요 |
| **해결** | 비즈니스 특성에 맞춘 TTL (결제: 24시간, 조회: 5분 등), Redis TTL 활용 |
| **트레이드오프** | TTL 내 재시도는 막을 수 있지만 TTL 이후 재시도는 새 요청으로 처리됨 |
