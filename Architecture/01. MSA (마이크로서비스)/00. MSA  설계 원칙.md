
> 핵심: "서비스를 어떻게 잘 나누고, 나눈 서비스가 독립적으로 잘 동작하게 할 것인가"

---

## 1. 단일 책임 원칙 (Single Responsibility)

하나의 서비스는 하나의 비즈니스 도메인만 담당. 예를 들면 "송금 서비스", "계좌 서비스", "알림 서비스"가 각각 분리되어야지, 송금 서비스가 알림까지 직접 처리하면 안 된다.

## 2. 서비스 자율성 (Autonomy)

각 서비스는 독립적으로 배포, 확장, 장애 격리가 가능해야 한다. 계좌 서비스가 배포 중이라고 송금 서비스까지 멈추면 안 된다. 이게 모놀리식과 가장 큰 차이.

## 3. Database per Service

서비스마다 자체 DB를 가져야 한다. DB를 공유하면 스키마 변경 시 다른 서비스에 영향을 주고, 결국 서비스 간 결합도가 올라간다. 대신 이 원칙 때문에 분산 트랜잭션 문제(Saga 등)가 생긴다.

## 4. 느슨한 결합 (Loose Coupling)

서비스 간 직접 의존을 최소화한다. 동기 호출(REST)보다는 비동기 이벤트 기반 통신을 선호하고, 한 서비스의 내부 구현 변경이 다른 서비스에 영향을 주지 않아야 한다.

## 5. 높은 응집도 (High Cohesion)

관련 있는 기능은 하나의 서비스 안에 모아야 한다. 너무 잘게 쪼개면(nano service) 네트워크 호출 비용, 운영 복잡도만 올라간다. 서비스 경계를 어디에 그을지가 MSA 설계에서 가장 어려운 부분이고, 여기서 DDD의 Bounded Context 개념이 등장한다.

## 6. API 우선 설계 (API-First)

서비스 간 통신은 잘 정의된 API 계약을 통해서만 이뤄져야 한다. 내부 구현은 감추고 인터페이스만 공개한다. API 버전 관리도 여기에 포함된다.

## 7. 장애 격리 설계 (Design for Failure)

네트워크는 항상 실패할 수 있다는 전제로 설계한다. Circuit Breaker, Timeout, Retry, Fallback, Bulkhead 패턴 등이 여기서 나온다. 하나의 서비스 장애가 전체로 전파(cascading failure)되지 않아야 한다.

## 8. 관측 가능성 (Observability)

분산 환경에서는 로그만으로 문제 추적이 불가능하다. Distributed Tracing, 중앙 집중 로깅, 메트릭 수집(p99 latency 등)이 설계 단계부터 고려되어야 한다.

## 9. 자동화 (Automation)

서비스가 수십 개가 되면 수동 배포/관리가 불가능하다. CI/CD 파이프라인, 인프라 자동화(IaC), 오토스케일링이 전제되어야 MSA가 의미 있다.

---

## 원칙 간 충돌

원칙을 나열하는 것보다 원칙 간 트레이드오프 생각

- Database per Service를 지키면 → 데이터 정합성이 어려워진다 (Saga 필요)
- 느슨한 결합을 위해 비동기 통신을 쓰면 → Eventual Consistency를 감수해야 한다
- 서비스를 너무 잘게 쪼개면 → 자율성은 좋아지지만 운영 복잡도가 폭발한다

이런 트레이드오프를 상황에 맞게 판단
