```
0. 모놀리식
   
   ↓ 서비스 커지니까 배포/확장/장애격리가 힘들어짐
1. MSA 기본 개념 (서비스별 분리)
  
 (DB를 공유하면 서비스끼리 다시 결합되어서 독립 배포/확장/장애격리가 안됨)
   ↓ 쪼갰으면 각자 DB도 분리해야지 
2. Database per Service (서비스별 DB 분리)
   
   ↓ DB가 다르면 서비스끼리 어떻게 대화하지?
3. Event-Driven Architecture (Kafka로 메시지 주고받기)
   
   ↓ 근데 DB 저장은 됐는데 메시지가 안 날아가면?
4. Transactional Messaging (문제 인식)
   
   ↓ 메시지도 같은 DB 트랜잭션에 저장하자
5. Outbox Pattern (4번의 해결책)
   
   ↓ 결제는 됐는데 재고가 없으면 어떡하지?
6. Saga Pattern (보상 트랜잭션으로 되돌리기)
  
   ↓ 같은 메시지가 2번 와서 2번 결제되면?
7. Idempotency (멱등성 - 몇 번을 해도 결과가 같게)
   
   ↓ 재시도해도 계속 실패하는 메시지는?
8. Dead Letter Queue (실패 메시지 격리)
   
   ↓ Outbox 폴링이 비효율적인데 더 좋은 방법은?
9. CDC (DB 변경 로그를 감지해서 이벤트 발행)
   
   ↓ 여기까지가 이벤트 기반 통신의 완성
   ↓ 이제 인프라 쪽 문제들
10. API Gateway (클라이언트가 서비스 주소를 다 알아야 하나?)
   
   ↓ 서비스가 100개면 주소를 어떻게 관리하지?
11. Service Discovery (서비스 자동 탐색)
   
   ↓ 결제 서비스가 느려지면 주문까지 같이 죽는데?
12. Circuit Breaker (장애 전파 차단)
   
   ↓ 여기까지가 MSA 인프라의 완성
   ↓ 이제 데이터 설계 심화
13. CQRS (읽기 트래픽이 너무 많으면 읽기/쓰기를 분리)
   
   ↓ 상태를 저장하지 말고 이벤트 자체를 기록하면?
14. Event Sourcing (이벤트 히스토리로 상태 복원)
```
