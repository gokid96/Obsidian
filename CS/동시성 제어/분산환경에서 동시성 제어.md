## 1. 분산환경에서 별도 동시성 제어

단일 서버에서는 Java의 synchronized나 userId별 Lock으로 동시성을 제어할 수 있다. 하지만 서버가 여러 대가 되면 각 서버의 메모리는 독립적이라서 서버 A의 Lock과 서버 B의 Lock은 서로를 모른다. 같은 유저 요청이 서버 A와 서버 B에 각각 들어오면 둘 다 통과해버린다.

DB 레벨(유니크 제약조건, 비관적 락)로도 해결은 되지만, 트래픽이 몰리면 모든 요청이 DB로 직행하면서 DB가 병목이 된다. DB는 스케일아웃이 어렵고 마스터가 보통 1대이기 때문에 이 병목을 DB만으로 해결하기 힘들다.

그래서 DB 앞단에 Redis 같은 외부 저장소를 두고 동시성을 제어하는 것이 분산환경의 핵심이다.

## 2. Redis 분산락

### 2.1 기본 원리

Redis의 `SET NX EX` 명령어로 락을 구현한다.

```
SET lock:user:1 "server-1" NX EX 10
```

- **NX**: 키가 없을 때만 설정 (이미 있으면 실패 → 다른 서버가 락을 잡고 있다는 의미)
- **EX 10**: 10초 후 자동 만료 (서버가 죽어서 락을 못 풀 때를 대비)

작업이 끝나면 키를 삭제해서 락을 해제한다.

### 2.2 Redisson (Java 라이브러리)

Redis 분산락을 직접 구현하면 복잡하기 때문에 Redisson 라이브러리를 주로 사용한다.

```java
RLock lock = redissonClient.getLock("lock:user:" + userId);
boolean acquired = lock.tryLock(5, 10, TimeUnit.SECONDS);
// 5초 동안 대기, 획득하면 10초 후 자동 해제

if (acquired) {
    try {
        // 임계 영역 (비즈니스 로직)
    } finally {
        lock.unlock();
    }
}
```

Redisson이 내부적으로 해주는 것:

- 락 획득/해제 원자성 보장
- 락 만료 시간 자동 연장 (watchdog 기능: 작업이 길어지면 만료 전에 자동으로 연장)
- 재진입 가능 (같은 스레드가 같은 락을 다시 획득 가능)

### 2.3 락 키 설계

락 키를 뭘로 잡느냐에 따라 동시성 제어 범위가 달라진다.

|락 키|용도|예시|
|---|---|---|
|`lock:user:{userId}`|같은 유저 중복 요청 방지|쿠폰 중복 발급, 중복 결제|
|`lock:course:{courseId}`|같은 자원 동시 수정 방지|좌석 선점, 1:1 상품 구매|
|`lock:user:{userId}:course:{courseId}`|특정 유저의 특정 자원 접근 제어|같은 유저가 같은 강좌 중복 신청|
|`lock:coupon:{couponId}`|같은 쿠폰 동시 사용 방지|쿠폰 1회 사용 제한|

### 2.4 주의사항

**락 만료 시간 설정**

- 너무 짧으면: 작업 중에 락이 풀려서 다른 요청이 통과
- 너무 길면: 서버 장애 시 오래 대기
- Redisson의 watchdog이 자동 연장해주지만, 직접 구현할 때는 주의 필요

**Redis 장애 대비**

- Redis가 죽으면 락을 잡을 수 없어서 전체 서비스에 영향
- Redis Sentinel이나 Cluster로 고가용성 확보 필요
- 최후의 방어선으로 DB 유니크 제약조건을 반드시 유지

## 3. Redis를 활용한 기타 동시성 제어

### 3.1 Redis INCR (원자적 카운터)

단순 수량 감소/증가는 분산락 없이 Redis의 원자적 연산으로 처리할 수 있다.

```
-- 쿠폰 남은 수량 감소
DECR coupon:remaining:1
-- 반환값이 0 이상이면 성공, 음수면 이미 소진 → 롤백
```

```java
Long remaining = redisTemplate.opsForValue().decrement("coupon:remaining:" + couponId);
if (remaining < 0) {
    // 소진됨 → 롤백
    redisTemplate.opsForValue().increment("coupon:remaining:" + couponId);
    throw new RuntimeException("쿠폰 소진");
}
```

- 장점: 분산락보다 빠르고 단순
- 적합: 선착순 수량 제한, 조회수, 좋아요 카운트
- 한계: 단순 숫자 연산만 가능, 복잡한 비즈니스 로직에는 부적합

### 3.2 Redis SET NX (중복 방지)

분산락처럼 잠그는 게 아니라, 단순히 "이미 처리했는지" 여부만 체크하는 용도.

```
SET processed:user:1:coupon:DISCOUNT_1000_WON "1" NX EX 60
-- 성공하면 → 처음 요청, 처리 진행
-- 실패하면 → 이미 처리됨, 거부
```

- 적합: 중복 결제 방지, 멱등성 보장, 중복 발급 방지
- 분산락과의 차이: 분산락은 "대기했다가 순서대로 처리", SET NX는 "먼저 온 하나만 성공, 나머지는 즉시 실패"

### 3.3 Redis Sorted Set (대기열/순서 보장)

요청을 순서대로 정렬해서 처리해야 할 때 사용한다.

```
-- 요청 시간을 score로 넣어서 순서 보장
ZADD queue:course:1 1709000001 "user:1"
ZADD queue:course:1 1709000002 "user:2"

-- 앞에서부터 꺼내서 처리
ZPOPMIN queue:course:1
```

- 적합: 선착순 대기열, 수강신청 순서 보장
- Kafka 대기열의 간단한 대안

## 4. 환경별 동시성 제어 조합

### 4.1 쿠폰 중복 발급 방지

| 환경              | 방식                                               |
| --------------- | ------------------------------------------------ |
| 메모리 DB (과제)     | userId별 Lock (ReentrantLock + ConcurrentHashMap) |
| 단일 서버 + DB      | DB 유니크 제약조건만으로 충분                                |
| 분산 서버 + DB      | DB 유니크 제약조건만으로 충분                                |
| 분산 서버 + DB 부하 큼 | Redis SET NX(앞단 방어) + DB 유니크 제약조건(최후 방어)         |

### 4.2 선착순 수량 제한 (20명 할인, 100석 좌석)

|환경|방식|
|---|---|
|단일 서버 + DB|원자적 업데이트 (`remaining - 1 WHERE remaining > 0`)|
|분산 서버 + DB|원자적 업데이트 (DB가 1대면 그대로 유효)|
|분산 서버 + DB 부하 큼|Redis INCR(앞단 수량 차감) + DB 원자적 업데이트(최종 확인)|

### 4.3 대규모 트래픽 (수강신청 오픈, 티켓팅)

```
요청 → [1단계] Kafka 큐: 요청 순차 정렬, 유입량 제한
     → [2단계] Redis 분산락: 같은 자원에 대해 서버 간 락
     → [3단계] 서비스 로직: 비즈니스 검증
     → [4단계] DB 레벨: 원자적 업데이트 + 유니크 제약조건
```

## 5. 단일 서버 → 분산 환경 전환 시 변경 포인트

| 단일 서버        | 분산 환경                | 이유              |
| ------------ | -------------------- | --------------- |
| synchronized | 제거 또는 Redis 분산락으로 교체 | 서버 간 공유 안 됨     |
| userId별 Lock | Redis 분산락으로 교체       | 서버 간 공유 안 됨     |
| DB 비관적 락     | 그대로 유지 가능            | DB가 1대면 여전히 동작  |
| DB 유니크 제약조건  | 그대로 유지               | 어떤 환경이든 최후의 방어선 |
| 원자적 업데이트     | 그대로 유지 가능            | DB가 1대면 여전히 동작  |

핵심: Java 레벨 동시성 제어만 Redis로 교체하면 되고, DB 레벨은 대부분 그대로 유지된다.

## 6. Redis 분산락 vs DB 락 선택 기준

|기준|Redis 분산락|DB 락|
|---|---|---|
|성능|빠름 (인메모리)|상대적으로 느림|
|일관성|Redis 장애 시 락 유실 가능|트랜잭션으로 강한 일관성|
|인프라|Redis 별도 운영 필요|추가 인프라 불필요|
|적합한 상황|DB 부하 줄여야 할 때, 트래픽 많을 때|트래픽 적을 때, 강한 정합성 필요할 때|

**결론:**
- 트래픽 적으면 → DB 락만으로 충분, Redis 불필요
- 트래픽 많으면 → Redis로 앞단 방어 + DB는 최후의 방어선
- 어떤 경우든 DB 레벨 방어(유니크 제약조건, 원자적 업데이트)는 반드시 유지
