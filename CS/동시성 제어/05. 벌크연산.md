# 05. 벌크연산 — Cascade DELETE N+1
## 1. 벌크연산이란?

보통 JPA로 엔티티를 삭제하면 Hibernate가 **엔티티 하나씩 DELETE 쿼리를 날린다.**

```sql
DELETE FROM post WHERE post_id = 1
DELETE FROM post WHERE post_id = 2
DELETE FROM post WHERE post_id = 3
...
```

벌크연산은 이걸 **한 번의 쿼리로 묶어서 처리**하는 방식이다.

```sql
DELETE FROM post WHERE folder_id IN (1, 2, 3, ...)
```

건별 처리와 벌크 처리의 차이는 데이터가 적을 땐 미미하지만, 연관 엔티티가 많아질수록 격차가 벌어진다.

---

## 2. 문제 발견 (워크스페이스,폴더 삭제)

### 코드 리뷰에서 의심

`Workspace`, `Folder` 엔티티를 열어보면 이런 패턴이 눈에 띈다.

```java
// Workspace.java
@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> folders;

@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Post> posts;

@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<WorkspaceMember> members;
```

```java
// Folder.java
@OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> children;

@OneToMany(mappedBy = "folder", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Post> posts;
```

`CascadeType.ALL + orphanRemoval = true` 는 **"부모가 자식의 생명주기를 완전히 소유한다"** 는 선언이다.

- `CascadeType.ALL` : 부모에게 한 작업(저장, 삭제 등)을 자식에게 전부 전파
- `orphanRemoval = true` : 부모 컬렉션에서 제거된 자식을 자동으로 DELETE

문제는 Hibernate가 이 CASCADE를 처리할 때 **영속성 컨텍스트에서 엔티티를 하나씩 추적하며 건별로 DELETE를 날린다**는 것이다.

`workspaceRepository.delete(workspace)` 한 줄이 내부에서 이렇게 동작한다.

```
workspace 삭제 요청
    ↓
Hibernate: "folders에 CascadeType.ALL 있네"
    ↓
folder 하나씩 삭제 전파
    ↓
Hibernate: "folder.posts에도 CascadeType.ALL 있네"
    ↓
post 하나씩 삭제 전파
    ↓
...
```

### Hibernate 로그로 확인

```yaml
logging:
  level:
    org.hibernate.SQL: DEBUG
```

실제로 워크스페이스 삭제 API를 한 번 호출하고 로그를 확인했다.

```sql
-- 게시글 건별 삭제
DELETE FROM post WHERE post_id = 1
DELETE FROM post WHERE post_id = 2
...
DELETE FROM post WHERE post_id = 50   ← 50번

-- 폴더 건별 삭제
DELETE FROM folder WHERE folder_id = 10
...
DELETE FROM folder WHERE folder_id = 29  ← 20번

-- 멤버 건별 삭제
DELETE FROM workspace_member WHERE workspace_member_id = 1
...
DELETE FROM workspace_member WHERE workspace_member_id = 5  ← 5번

-- 워크스페이스 삭제
DELETE FROM workspace WHERE workspace_id = 1  ← 1번
```

```
총 DELETE 쿼리
워크스페이스 삭제: 50 + 20 + 5 + 1 = 76번
폴더 삭제: 하위폴더 + 게시글 = 최대 71번
```

쉽게 말하면 SELECT N+1과 같은 패턴이다. SELECT N+1은 조회할 때 연관 엔티티를 건별로 SELECT하는 문제고, 여기서는 삭제할 때 연관 엔티티를 건별로 DELETE하는 문제다. 원인도 같고, 해결 방향도 같다. 쿼리를 묶어서 줄이는 것.




해결 방법으로는 


JPQL 벌크 DELETE(`@Modifying`), `deleteAllInBatch`, DB 레벨 `ON DELETE CASCADE` 등이 있다. 
### 1. JPQL 벌크 DELETE (`@Modifying`)
```java
@Modifying(clearAutomatically = true)
@Query("DELETE FROM Post p WHERE p.workspace.workspaceId = :workspaceId")
void deleteAllByWorkspaceId(@Param("workspaceId") Long workspaceId);
```
- `WHERE id IN (...)` 또는 `WHERE workspace_id = ?` 한 번에 삭제
- 영속성 컨텍스트를 우회하기 때문에 `clearAutomatically = true` 필요
- 삭제 순서를 서비스에서 **명시적으로 제어** 가능

### 2. `deleteAllInBatch`
```java
postRepository.deleteAllInBatch(posts);
```
- Spring Data JPA가 제공하는 IN절 벌크 삭제
- 삭제 대상 엔티티 목록을 서비스에서 **직접 수집**해야 함
- JPQL 방식보다 코드가 늘어남

### 3. DB 레벨 `ON DELETE CASCADE`
```sql
ALTER TABLE post
ADD CONSTRAINT fk_post_folder
FOREIGN KEY (folder_id) REFERENCES folder(folder_id)
ON DELETE CASCADE;
```
- DB가 알아서 연관 데이터 삭제
- JPA가 아예 관여 안 함 → 가장 빠름
- 단, **JPA 영속성 컨텍스트가 모름** → 삭제된 걸 모르고 캐시에 남아있을 수 있음
- JPA와 DB 동작이 분리되어 유지보수가 어려워짐




먼저 k6로 기존 삭제 동작을 측정해보고 어떤 방법이 적합한지 고민해보자.
