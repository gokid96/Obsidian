## 1. 트랜잭션

여러 쿼리를 하나의 작업 단위로 묶어서 **All or Nothing**을 보장하는 메커니즘

```sql
START TRANSACTION;
UPDATE course SET remaining = remaining - 1 WHERE course_id = 1 AND remaining > 0;
INSERT INTO enrollment (student_id, course_id) VALUES (1, 1);
COMMIT;  -- 둘 다 성공하면 확정
-- 실패 시 ROLLBACK → 둘 다 취소
```

좌석은 줄었는데 수강 등록은 안 된 어중간한 상태를 방지한다.

**트랜잭션 ≠ 동시성 제어** `@Transactional`은 "이 안의 작업이 하나라도 실패하면 전부 취소"일 뿐이다. 100명이 동시에 호출하면 트랜잭션 100개가 동시에 돌면서 각각 "좌석 남아있네 → 감소"를 하게 된다. 동시성 제어는 별도로 해야 한다.

---

## 2. ACID

트랜잭션이 보장해야 하는 4가지 속성이다.

**Atomicity (원자성)** 트랜잭션 내 작업이 전부 성공하거나 전부 실패한다. 중간 상태는 없다. 예: 좌석 감소 + 수강 등록이 하나의 단위. 하나만 성공하는 일은 없다.

**Consistency (일관성)** 트랜잭션 전후로 데이터베이스가 일관된 상태를 유지한다. 예: 잔여 좌석이 음수가 되는 상태는 허용하지 않는다.

**Isolation (격리성)** 동시에 실행되는 트랜잭션이 서로 간섭하지 않는다. 격리수준에 따라 간섭의 정도가 달라진다.

**Durability (지속성)** 커밋된 데이터는 시스템 장애(서버 다운, 정전)가 발생해도 유지된다. DB가 디스크에 기록하기 때문이다.

---

## 3. 격리수준 (Isolation Level)

동시에 실행되는 트랜잭션 간에 서로의 변경 내용을 어느 정도까지 볼 수 있는지를 정의한다. 격리수준이 높을수록 안전하지만 성능이 떨어진다.

### 3.1 발생할 수 있는 문제들

**Dirty Read** 아직 커밋되지 않은 다른 트랜잭션의 변경을 읽는 현상

```
트랜잭션 A: UPDATE course SET remaining = 29 (아직 커밋 안 함)
트랜잭션 B: SELECT remaining → 29를 읽음
트랜잭션 A: ROLLBACK → 실제로는 30인데 B는 29로 처리함
```

**Non-Repeatable Read** 같은 트랜잭션 안에서 같은 데이터를 두 번 읽었을 때 값이 달라지는 현상

```
트랜잭션 A: SELECT remaining → 30
트랜잭션 B: UPDATE remaining = 29, COMMIT
트랜잭션 A: SELECT remaining → 29 (아까는 30이었는데?)
```

**Phantom Read** 같은 조건으로 조회했을 때 결과 행 수가 달라지는 현상

```
트랜잭션 A: SELECT COUNT(*) FROM enrollment WHERE course_id = 1 → 28명
트랜잭션 B: INSERT INTO enrollment (course_id = 1), COMMIT
트랜잭션 A: SELECT COUNT(*) FROM enrollment WHERE course_id = 1 → 29명
```

### 3.2 격리수준 4단계

| 격리수준             | Dirty Read | Non-Repeatable Read | Phantom Read    | 성능    |
| ---------------- | ---------- | ------------------- | --------------- | ----- |
| Read Uncommitted | 발생         | 발생                  | 발생              | 가장 높음 |
| Read Committed   | 방지         | 발생                  | 발생              | 높음    |
| Repeatable Read  | 방지         | 방지                  | 발생 (InnoDB는 방지) | 보통    |
| Serializable     | 방지         | 방지                  | 방지              | 가장 낮음 |

**Read Uncommitted** 커밋되지 않은 데이터도 읽을 수 있다. Dirty Read가 발생하기 때문에 실무에서는 거의 사용하지 않음

**Read Committed** 커밋된 데이터만 읽는다. Oracle, PostgreSQL의 기본값이다. 매 쿼리마다 최신 커밋 값을 읽기 때문에 같은 트랜잭션 안에서 값이 바뀔 수 있음

**Repeatable Read** 트랜잭션 시작 시점의 스냅샷을 유지한다. MySQL InnoDB의 기본값이다. 같은 트랜잭션 안에서 항상 같은 값을 읽는다. InnoDB는 갭락(Gap Lock)으로 Phantom Read도 방지

**Serializable** 트랜잭션을 완전히 직렬 실행하는 것과 같은 결과를 보장한다. 가장 안전하지만 성능이 매우 낮아서 특수한 경우에만 사용한다.

## 4. Read Committed vs Repeatable Read 상세 비교

### 4.1 동작 차이

**Read Committed (RC)**

```
트랜잭션 A 시작
SELECT remaining → 30
                        트랜잭션 B: UPDATE remaining = 29, COMMIT
SELECT remaining → 29   ← 최신 커밋 값을 읽음 (값이 바뀜)
```

**Repeatable Read (RR)**

```
트랜잭션 A 시작
SELECT remaining → 30
                        트랜잭션 B: UPDATE remaining = 29, COMMIT
SELECT remaining → 30   ← 트랜잭션 시작 시점 스냅샷 유지 (값 안 바뀜)
```

### 4.2 비교 정리

| 기준         | Read Committed | Repeatable Read |
| ---------- | -------------- | --------------- |
| 읽는 값       | 매번 최신 커밋 값     | 트랜잭션 시작 시점 스냅샷  |
| 같은 데이터 재조회 | 값이 바뀔 수 있음     | 항상 같은 값         |
| 락 범위       | 좁음 (행 락만)      | 넓음 (갭락 포함)      |
| 데드락 가능성    | 낮음             | 상대적으로 높음        |
| 성능         | 상대적으로 좋음       | 상대적으로 떨어짐       |
| 적합한 상황     | 최신 값이 중요한 경우   | 일관된 읽기가 중요한 경우  |

### 4.3 언제 뭘 쓰나

**Read Committed가 적합한 경우:**

- 수강신청: 잔여 좌석의 최신 상태를 봐야 정확한 판단 가능
- 재고 차감: 현재 실제 재고를 봐야 함
- 경합이 심한 환경: 락 범위가 좁아서 데드락 가능성 낮음

**Repeatable Read가 적합한 경우:**

- 정산/보고서: 집계 중에 데이터가 바뀌면 결과가 틀어짐
- 일괄 처리: 시작 시점 기준으로 일관된 데이터 필요
- 데이터 무결성이 최우선인 경우

### 4.4 갭락 (Gap Lock)

Repeatable Read에서 Phantom Read를 방지하기 위해 InnoDB가 사용하는 락이다. 실제 행뿐만 아니라 행 사이의 "빈 공간"까지 잠근다.

```sql
SELECT * FROM enrollment WHERE course_id = 1 FOR UPDATE;
-- course_id = 1인 행뿐만 아니라, 새로운 행이 INSERT되는 것도 막음
```

- Read Committed에서는 갭락을 사용하지 않아서 락 범위가 좁다.
- Repeatable Read에서는 갭락을 사용해서 락 범위가 넓어지고, 이 때문에 데드락이 더 쉽게 발생한다.

이것이 수강신청처럼 경합이 심한 환경에서 의도적으로 Read Committed로 낮추는 이유이다.

## 5. MySQL에서 격리수준 변경

### 5.1 SQL로 변경

```sql
-- 현재 세션만 변경
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 이후 모든 새 연결에 적용
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 현재 격리수준 확인
SELECT @@transaction_isolation;
```

### 5.2 Spring Boot에서 변경

**application.yml (전역 설정)**

```yaml
spring:
  jpa:
    properties:
      hibernate:
        connection:
          isolation: 2
# 1 = READ_UNCOMMITTED
# 2 = READ_COMMITTED
# 4 = REPEATABLE_READ
# 8 = SERIALIZABLE
```

**메서드 단위로 변경**

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void enroll(Long studentId, Long courseId) {
    // 이 트랜잭션만 RC로 실행
}
```

## 6. 핵심 질문과 답변 방향

**"격리수준을 RC로 바꾼 이유?"** → 수강신청은 잔여 좌석의 최신 값을 봐야 정확한 판단이 가능하고, RR의 갭락으로 인한 데드락 가능성을 줄이기 위해 RC를 선택

**"트랜잭션 안에서 최신 값을 보는 게 항상 좋은가?"** → 항상 그런 건 아니다. 수강신청처럼 현재 상태가 중요한 경우에는 RC가 맞지만, 정산이나 보고서처럼 일관된 스냅샷이 필요한 경우에는 RR이 맞다. 상황에 따라 다르다.

**"RC와 RR의 성능 차이?"** → RC는 갭락을 사용하지 않아서 락 범위가 좁고 데드락 가능성이 낮다. 경합이 심한 환경에서는 RC가 성능상 유리. RR은 스냅샷 유지 비용이 있지만 읽기 일관성이 보장


격리수준이 높으면 안전하지만 느리고, 낮으면 빠르지만 데이터가 꼬일 수 있다. 
각 DB가 자기 환경에 맞는 기본값을 제공 하고 , 
MySQL은 안전 쪽(Repeatable Read), 
PostgreSQL은 성능 쪽(Read Committed)을 기본으로 잡고있다
