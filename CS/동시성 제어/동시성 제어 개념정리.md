## 1. 동시성 문제

여러 스레드 또는 여러 서버가 동시에 같은 자원(데이터)에 접근할 때 데이터 정합성이 깨지는 문제를 말한다.

### 대표적인 문제 유형

**Race Condition (경쟁 상태)** 두 개 이상의 스레드가 공유 자원에 동시에 접근하여, 실행 순서에 따라 결과가 달라지는 현상이다. 예: 잔여 좌석이 1인데 두 요청이 동시에 읽고 각각 성공 처리하면 좌석이 -1이 된다.

**Lost Update (갱신 손실)** 두 트랜잭션이 같은 데이터를 읽고 각각 수정하면, 먼저 수정한 값이 나중 수정에 의해 덮어써져서 사라지는 현상이다.

**Dirty Read** 아직 커밋되지 않은 다른 트랜잭션의 변경 내용을 읽는 현상이다. 해당 트랜잭션이 롤백되면 존재하지 않는 값을 기반으로 처리한 셈이 된다.

**Non-Repeatable Read** 같은 트랜잭션 안에서 같은 데이터를 두 번 읽었을 때, 그 사이에 다른 트랜잭션이 수정·커밋하여 값이 달라지는 현상이다.

**Phantom Read** 같은 트랜잭션 안에서 같은 조건으로 조회했을 때, 그 사이에 다른 트랜잭션이 행을 추가·삭제하여 결과 행 수가 달라지는 현상이다.

## 2. DB 레벨 동시성 제어

DB가 제공하는 메커니즘을 이용한 방식. 서버가 여러 대여도 같은 DB를 보고 있으면 동작한다.

### 2.1 비관적 락 (Pessimistic Lock)
충돌이 발생할 것이라 가정하고, 데이터에 접근하기 전에 미리 잠그는 방식

```sql
SELECT * FROM student WHERE student_id = 1 FOR UPDATE;
-- 이 행에 대해 다른 트랜잭션은 대기
```

- 장점: 충돌이 잦은 환경에서 확실하게 정합성 보장
- 단점: 대기 시간 발생, 동시 처리량 저하
- 적합: 수강신청, 재고 차감 등 경합이 심한 경우

### 2.2 낙관적 락 (Optimistic Lock)
충돌이 발생하지 않을 것이라 가정하고, 수정 시점에 버전을 비교하여 충돌을 감지하는 방식

```sql
-- 1단계: 읽기
SELECT remaining, version FROM course WHERE course_id = 1;
-- remaining = 5, version = 3

-- 2단계: 수정 (버전 비교)
UPDATE course SET remaining = 4, version = 4
WHERE course_id = 1 AND version = 3;
-- 영향받은 행이 0이면 → 다른 트랜잭션이 먼저 수정 → 재시도
```

- 장점: 락을 잡지 않으므로 대기 없이 성능 좋음
- 단점: 충돌이 잦으면 재시도 반복으로 비효율적
- 적합: 게시글 수정 등 경합이 낮은 경우

### 2.3 공유락 / 배타락

- **공유락 (S Lock)**: 읽기 락. 여러 트랜잭션이 동시에 획득 가능. 쓰기 불가. `SELECT ... FOR SHARE`
- **배타락 (X Lock)**: 쓰기 락. 하나의 트랜잭션만 획득. 다른 읽기/쓰기 모두 대기. `SELECT ... FOR UPDATE`

### 2.4 원자적 업데이트 (Atomic Update)

조회와 수정을 하나의 쿼리로 합쳐서 중간에 끼어들 수 없게 하는 방식. 락을 사용하지 않는다.

```sql
UPDATE course SET remaining = remaining - 1
WHERE course_id = 1 AND remaining > 0;
-- 영향받은 행이 0이면 → 이미 마감
```

- 장점: 락 없이 정합성 보장, 대기 없어 성능 좋음
- 단점: 단순한 연산(증감, 상태 변경)에만 적합
- vs 비관적 락: "줄 세워서 한 명씩" vs "줄 안 세우고 조건 맞으면 통과"
- vs 낙관적 락: "읽고 → 비교 → 재시도" vs "조건 걸고 한 방에 처리"

### 2.5 유니크 제약조건 (Unique Constraint)

DB 스키마에 유니크 인덱스를 걸어서 중복 삽입을 DB가 거부하게 만드는 방식. 락을 사용하지 않는다.

```sql
ALTER TABLE enrollment ADD UNIQUE (student_id, course_id);

INSERT INTO enrollment (student_id, course_id) VALUES (1, 1);  -- 성공
INSERT INTO enrollment (student_id, course_id) VALUES (1, 1);  -- 에러
```

- 원자적 업데이트는 UPDATE에서 "값의 안전한 수정"
- 유니크 제약조건은 INSERT에서 "중복 삽입 방지"
- 수강신청에서는 둘 다 필요 (정원 초과 방지 + 중복 신청 방지)

### 2.6 큐 기반 순차 처리

요청을 큐에 넣어서 하나씩 처리. 동시 접근 자체를 원천적으로 없앤다.

- **Kafka**: 대규모 트래픽. 강좌별 파티션으로 순차 처리
- **Redis 큐**: 간단한 구조. LPUSH/BRPOP
- **RabbitMQ**: 순서 보장과 재시도 처리

### DB 레벨 선택 기준

| 상황                             | 선택         | 이유                   |
| ------------------------------ | ---------- | -------------------- |
| 경합이 심하고 정합성이 최우선 (수강신청, 재고 차감) | 비관적 락      | 확실하게 잠가서 충돌 원천 차단    |
| 경합이 낮고 성능이 중요 (게시글 수정, 설정 변경)  | 낙관적 락      | 대기 없이 처리, 충돌 시에만 재시도 |
| 단순 숫자 증감 (좌석 감소, 조회수 증가)       | 원자적 업데이트   | 락 없이 한 쿼리로 정합성 보장    |
| 중복 삽입 방지 (중복 신청, 중복 가입)        | 유니크 제약조건   | DB가 알아서 거부, 로직 불필요   |
| 트래픽 폭주 대비 (수강신청 오픈, 선착순 이벤트)   | 큐 기반 순차 처리 | 동시 접근 자체를 없앰         |

**함께 쓰는 조합 예시:**

- 수강신청: 원자적 업데이트(정원 초과 방지) + 유니크 제약조건(중복 신청 방지) + 비관적 락(학생 단위 중복 요청 방지)
- 재고 차감: 비관적 락 또는 원자적 업데이트 + 유니크 제약조건(중복 주문 방지)
- 선착순 쿠폰: 큐 기반 순차 처리 + 유니크 제약조건(중복 발급 방지)

## 3. 애플리케이션(Java) 레벨 동시성 제어

같은 JVM(서버 한 대) 안에서 스레드 간 동시성을 제어하는 방법. 서버가 여러 대면 단독으로는 부족하다.

### 3.1 synchronized

가장 기본. 메서드나 블록에 붙이면 한 스레드만 진입.

```java
public synchronized void enroll(Long studentId, Long courseId) {
    // 한 번에 하나의 스레드만 실행
}
```

단점: 모든 요청이 한 줄로 서야 해서 성능 저하.

### 3.2 ReentrantLock

synchronized보다 유연. tryLock으로 대기 시간 설정, 공정성 설정 가능.

```java
private final Lock lock = new ReentrantLock();

public void enroll(Long studentId, Long courseId) {
    lock.lock();
    try {
        // 임계 영역
    } finally {
        lock.unlock();
    }
}
```

### 3.3 userId별 Lock

같은 유저의 요청만 순차 처리, 다른 유저는 동시 처리 가능.

```java
private final Map<Long, Lock> locks = new ConcurrentHashMap<>();

public void enroll(Long userId, Long courseId) {
    Lock lock = locks.computeIfAbsent(userId, k -> new ReentrantLock());
    lock.lock();
    try {
        // 같은 userId에 대해서만 순차 실행
    } finally {
        lock.unlock();
    }
}
```

synchronized보다 성능 좋음. 메모리 DB나 Repository 수정 불가 환경에서 유용.

### 3.4 Atomic 클래스

CAS(Compare-And-Swap) 연산으로 락 없이 원자적 값 변경.

```java
private final AtomicInteger remaining = new AtomicInteger(30);

public boolean enroll() {
    int current = remaining.get();
    if (current <= 0) return false;
    return remaining.compareAndSet(current, current - 1);
}
```

- 장점: 락 없이 매우 빠름
- 단점: 단순한 값 변경에만 적합

### 3.5 Semaphore

동시 접근 스레드 수를 제한.

```java
private final Semaphore semaphore = new Semaphore(5);

public void process() {
    semaphore.acquire();
    try {
        // 최대 5개 스레드만 동시 실행
    } finally {
        semaphore.release();
    }
}
```

### 3.6 스레드 안전 자료구조

- **ConcurrentHashMap**: 동시 읽기/쓰기 안전한 Map
- **ConcurrentLinkedQueue**: 락 없이 동작하는 큐
- **CopyOnWriteArrayList**: 읽기 많고 쓰기 적은 상황에 적합

### Java 레벨 선택 기준

| 상황                                 | 선택            | 이유                  |
| ---------------------------------- | ------------- | ------------------- |
| 간단한 임계 영역, 빠른 구현                   | synchronized  | 코드 한 줄로 끝남          |
| 대기 시간 제한, 공정성 필요                   | ReentrantLock | tryLock으로 세밀한 제어 가능 |
| 같은 유저 요청만 직렬화 (쿠폰 발급, 중복 방지)       | userId별 Lock  | 유저 간 병렬 처리로 성능 유지   |
| 단순 카운터, 플래그 변경                     | Atomic 클래스    | 락 없이 가장 빠름          |
| 동시 접근 수 제한 (커넥션 풀, API rate limit) | Semaphore     | 최대 N개만 허용           |
| 공유 데이터 저장/조회                       | 스레드 안전 자료구조   | 별도 락 없이 안전한 읽기/쓰기   |

**함께 쓰는 조합 예시:**

- 쿠폰 발급 (메모리 DB): userId별 Lock(중복 요청 직렬화) + ConcurrentHashMap(락 객체 관리)
- 실시간 카운터: AtomicInteger(값 변경) + ConcurrentHashMap(항목별 카운터 관리)

**주의:** Java 레벨 동시성 제어는 단일 서버에서만 유효하다. 서버가 여러 대면 DB 레벨이나 분산 레벨과 반드시 함께 써야 한다.

## 4. 분산 환경 동시성 제어

서버가 여러 대이면 Java 레벨 락은 의미 없다. 외부 저장소를 이용해야 한다.

### 4.1 Redis 분산락

```
SET lock:course:1 "server-1" NX EX 10
-- NX: 키가 없을 때만 설정
-- EX 10: 10초 후 자동 만료
```

**Redisson (Java 라이브러리):**

```java
RLock lock = redissonClient.getLock("lock:course:" + courseId);
lock.tryLock(5, 10, TimeUnit.SECONDS);
try {
    // 임계 영역
} finally {
    lock.unlock();
}
```

- 장점: 서버 여러 대에서 동작
- 주의: 락 만료 시간 설정이 중요

### 4.2 ZooKeeper / etcd 분산락

분산 코디네이터를 이용한 락. Redis보다 강한 일관성이지만 성능은 낮음.

### 4.3 DB 기반 분산락

락 테이블에 INSERT하면 획득, DELETE하면 해제. 추가 인프라 없이 가능하지만 성능 낮음.

### 분산 환경 선택 기준

| 상황                           | 선택               | 이유                  |
| ---------------------------- | ---------------- | ------------------- |
| 빠른 응답 필요 + 약간의 락 유실 허용       | Redis 분산락        | 성능 좋음, 대부분의 경우 충분   |
| 강한 일관성 필수 (금융, 결제)           | ZooKeeper / etcd | 락 유실 가능성 최소화        |
| 추가 인프라 없이 구현                 | DB 기반 분산락        | 별도 시스템 불필요, 단 성능 낮음 |
| 대규모 트래픽 순차 처리 (선착순, 수강신청 오픈) | Kafka 큐          | 동시 접근 자체를 제거        |

**함께 쓰는 조합 예시:**

- 수강신청 (서버 여러 대): Redis 분산락(서버 간 동기화) + 원자적 업데이트(DB 정합성) + 유니크 제약조건(중복 방지)
- 선착순 이벤트: Kafka 큐(요청 순차 처리) + Redis 분산락(컨슈머 간 동기화) + 유니크 제약조건(중복 방지)
- 결제 처리: ZooKeeper 분산락(강한 일관성) + 비관적 락(DB 정합성)

**핵심:** 분산 환경에서는 한 가지 방식만으로 충분하지 않다. 분산락(서버 간 동기화) + DB 레벨(데이터 정합성) + 유니크 제약조건(최후의 방어선)을 다층으로 구성하는 것이 일반적이다.

## 5. 레벨별 정리

|레벨|방식|적용 범위|대표 기술|
|---|---|---|---|
|Java|synchronized, ReentrantLock, userId별 Lock, Atomic|단일 서버|Java 내장|
|DB|비관적/낙관적 락, 원자적 업데이트, 유니크 제약조건|단일 DB 사용하는 모든 서버|MySQL, PostgreSQL|
|분산|분산락, 큐 기반 순차 처리|서버 여러 대|Redis, Kafka, ZooKeeper|

**판단 기준:**

- 서버 한 대, 단순 로직 → synchronized나 userId별 Lock
- 서버 한 대 이상, DB 사용 → DB 레벨 락 또는 원자적 업데이트
- 서버 여러 대, DB 병목 → 분산락 또는 큐 기반 처리
