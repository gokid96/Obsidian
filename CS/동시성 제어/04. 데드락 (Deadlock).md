## 1. 데드락

두 개 이상의 트랜잭션이 서로가 가진 락을 기다리면서 **영원히 진행하지 못하는 상태**

```
트랜잭션 A: 학생1 행 락 획득 → 강좌1 행 락 대기 중...
트랜잭션 B: 강좌1 행 락 획득 → 학생1 행 락 대기 중...
→ A는 B를 기다리고, B는 A를 기다림 → 영원히 풀리지 않음
```

일상으로 비유하면, 좁은 복도에서 두 사람이 마주보고 서서 "너 먼저 비켜" "아니 너 먼저"를 무한 반복하는 상황

---

## 2. 데드락 발생 조건

데드락은 아래 4가지 조건이 **동시에 모두** 충족될 때 발생한다. 하나라도 깨뜨리면 데드락은 발생하지 않는다.

**상호 배제 (Mutual Exclusion)** 자원(행)을 한 번에 하나의 트랜잭션만 사용할 수 있다. 배타락(X Lock)이 걸려 있으면 다른 트랜잭션은 접근 불가.

**점유 대기 (Hold and Wait)** 이미 하나의 락을 잡은 상태에서 다른 락을 추가로 요청하며 대기한다.

**비선점 (No Preemption)** 다른 트랜잭션이 가진 락을 강제로 빼앗을 수 없다. 상대가 스스로 풀어줄 때까지 기다려야 한다.

**순환 대기 (Circular Wait)** 트랜잭션 간 락 대기 관계가 원형으로 이어진다. 
A → B → A 또는 
A → B → C → A.

## 3. 데드락 발생 시나리오

### 3.1 수강신청: 락 순서가 다를 때

```
트랜잭션 A (학생1이 강좌1 신청):
1. SELECT * FROM student WHERE id = 1 FOR UPDATE  ← 학생1 락 획득
2. UPDATE course SET remaining = remaining - 1 WHERE id = 1 FOR UPDATE  ← 강좌1 락 대기...

트랜잭션 B (학생2가 강좌1 신청, 근데 로직이 강좌부터 잠금):
1. SELECT * FROM course WHERE id = 1 FOR UPDATE  ← 강좌1 락 획득
2. SELECT * FROM student WHERE id = 1 FOR UPDATE  ← 학생1 락 대기...

→ A는 강좌1을 기다리고, B는 학생1을 기다림 → 데드락
```

원인: 트랜잭션마다 락 잡는 순서가 다름 (A는 학생→강좌, B는 강좌→학생)

### 3.2 계좌 이체: 서로 다른 순서로 잠글 때
```
트랜잭션 A (계좌1 → 계좌2 이체):
1. SELECT * FROM account WHERE id = 1 FOR UPDATE  ← 계좌1 락 획득
2. SELECT * FROM account WHERE id = 2 FOR UPDATE  ← 계좌2 락 대기...

트랜잭션 B (계좌2 → 계좌1 이체):
1. SELECT * FROM account WHERE id = 2 FOR UPDATE  ← 계좌2 락 획득
2. SELECT * FROM account WHERE id = 1 FOR UPDATE  ← 계좌1 락 대기...

→ 데드락
```

원인: 같은 자원들인데 잠그는 순서가 반대

### 3.3 갭락으로 인한 데드락 (Repeatable Read)

```
트랜잭션 A:
SELECT * FROM enrollment WHERE course_id = 1 FOR UPDATE
→ course_id = 1 범위에 갭락 획득

트랜잭션 B:
SELECT * FROM enrollment WHERE course_id = 1 FOR UPDATE
→ 같은 범위에 갭락 대기...

트랜잭션 A:
INSERT INTO enrollment (student_id, course_id) VALUES (1, 1)
→ B의 갭락 범위에 INSERT 시도 → 대기...

→ A는 B를 기다리고, B는 A를 기다림 → 데드락
```

원인: Repeatable Read의 갭락이 넓은 범위를 잠그면서 서로 충돌

## 4. 데드락 예방 방법

``` markdown
가장 많이 쓰는 기법으로는 락 순서 통일 + 재시도 로직 조합
락 순서 통일은 설계 단계에서 한번 정해두면 끝이라 비용이 거의 없고,
데드락의 가장 흔한 원인인 순환대기를 제거해준다. 그래도 발생 할 수 있으니까 
@Retryable 같은 재시도 로직으로 보험을 건다. 이 두개는 거의 필수

나머지는 상황에 따라 추가한다 데드락이 반복되면 로그를 찍어서 원인을 파악하고,갭락이 문제면 격리 수준을 낮추고, 락이 너무 많으면 원자적 업데이트로 바꾸는식
```


### 4.1 락 순서 통일 (가장 중요)

모든 트랜잭션에서 락을 잡는 순서를 동일하게 정한다.

```java
// 항상 학생 먼저, 강좌 나중에
public void enroll(Long studentId, Long courseId) {
    studentRepository.findByIdForUpdate(studentId);  // 1. 학생 락
    courseRepository.decreaseRemaining(courseId);    // 2. 강좌 락
}
```

계좌 이체처럼 같은 종류의 자원이면 ID가 작은 것부터 잠근다.

```java
public void transfer(Long fromId, Long toId, int amount) {
    Long firstId = Math.min(fromId, toId);
    Long secondId = Math.max(fromId, toId);
    
    accountRepository.findByIdForUpdate(firstId);   // 항상 작은 ID 먼저
    accountRepository.findByIdForUpdate(secondId);
}
```

### 4.2 락 타임아웃 설정

일정 시간 내에 락을 획득하지 못하면 포기하고 롤백한다.

```sql
-- MySQL: 락 대기 시간 5초로 제한
SET innodb_lock_wait_timeout = 5;
```

```java
// JPA에서 타임아웃 설정
@QueryHints(@QueryHint(name = "javax.persistence.lock.timeout", value = "3000"))
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Student> findByIdForUpdate(Long id);
```

### 4.3 트랜잭션을 짧게 유지

트랜잭션 안에서 락을 잡고 있는 시간을 최소화한다. 외부 API 호출, 복잡한 연산 등은 트랜잭션 밖에서 처리한다.

```java
// 나쁜 예: 트랜잭션 안에서 외부 호출
@Transactional
public void enroll(Long studentId, Long courseId) {
    courseRepository.findByIdForUpdate(courseId);  // 락 획득
    externalApi.sendNotification(studentId);        // 외부 API 호출 (느림) → 락 오래 점유
    enrollmentRepository.save(enrollment);
}

// 좋은 예: 외부 호출은 트랜잭션 밖에서
@Transactional
public void enroll(Long studentId, Long courseId) {
    courseRepository.findByIdForUpdate(courseId);  // 락 획득
    enrollmentRepository.save(enrollment);          // 바로 처리
}
// 트랜잭션 끝난 후 알림 발송
notificationService.sendNotification(studentId);
```

### 4.4 락 개수 줄이기

여러 행에 락을 잡으면 데드락 가능성이 올라간다. 가능하면 원자적 업데이트로 락 없이 처리한다.

```sql
-- 락 2개 (데드락 가능성 있음)
SELECT * FROM student WHERE id = 1 FOR UPDATE;
SELECT * FROM course WHERE id = 1 FOR UPDATE;

-- 락 0개 (데드락 불가능)
UPDATE course SET remaining = remaining - 1 WHERE id = 1 AND remaining > 0;
```

### 4.5 격리수준 낮추기

Repeatable Read → Read Committed로 낮추면 갭락이 사라져서 갭락으로 인한 데드락을 방지할 수 있다.

## 5. 데드락 발생 시 처리

### 5.1 MySQL InnoDB 자동 감지

InnoDB는 데드락을 자동으로 감지하고, 관련 트랜잭션 중 하나를 강제 롤백한다. 비용이 적은(변경 내용이 적은) 트랜잭션이 롤백 대상이 된다.

```sql
-- 데드락 발생 시 MySQL 에러
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

### 5.2 애플리케이션에서 재시도

데드락은 완전히 예방할 수 없기 때문에, 발생 시 재시도 로직을 넣는 것이 일반적이다.

```java
@Retryable(value = DeadlockLoserDataAccessException.class, maxAttempts = 3)
@Transactional
public void enroll(Long studentId, Long courseId) {
    // 데드락 발생 시 최대 3번 재시도
}
```

### 5.3 데드락 로그 확인

```sql
-- 가장 최근 데드락 정보 확인
SHOW ENGINE INNODB STATUS;
```

데드락이 자주 발생하면 로그를 확인하고, 락 순서를 통일하거나 쿼리를 개선해야 한다.

## 6. 정리

| 예방 방법               | 효과               | 적용 난이도            |
| ------------------- | ---------------- | ----------------- |
| 락 순서 통일             | 순환 대기 제거, 가장 효과적 | 설계 시 정하면 쉬움       |
| 락 타임아웃              | 무한 대기 방지         | 설정 한 줄            |
| 트랜잭션 짧게 유지          | 락 점유 시간 최소화      | 리팩토링 필요할 수 있음     |
| 락 개수 줄이기 (원자적 업데이트) | 데드락 가능성 자체를 제거   | 단순 연산에만 가능        |
| 격리수준 낮추기 (RR → RC)  | 갭락 제거로 데드락 감소    | 설정 한 줄, 부작용 검토 필요 |
| 재시도 로직              | 데드락 발생해도 복구      | 코드 추가 필요          |

**핵심:** 데드락을 100% 예방하는 것은 불가능하다. 락 순서 통일로 가능성을 최소화하고, 발생 시 재시도로 복구하는 것이 실무 전략이다.
