## 1. 동시성 문제란?

여러 스레드 또는 여러 서버가 동시에 같은 자원(데이터)에 접근할 때 데이터 정합성이 깨지는 문제를 말한다.

### 대표적인 동시성 문제

**Race Condition (경쟁 상태)** 두 개 이상의 스레드가 공유 자원에 동시에 접근하여, 실행 순서에 따라 결과가 달라지는 현상이다. 예를 들어 잔여 좌석이 1인데 두 요청이 동시에 읽고 각각 성공 처리하면 좌석이 -1이 된다.

**Lost Update (갱신 손실)** 두 트랜잭션이 같은 데이터를 읽고 각각 수정하면, 먼저 수정한 값이 나중 수정에 의해 덮어써져서 사라지는 현상이다.

**Dirty Read** 아직 커밋되지 않은 다른 트랜잭션의 변경 내용을 읽는 현상이다. 해당 트랜잭션이 롤백되면 존재하지 않는 값을 기반으로 처리한 셈이 된다.

**Non-Repeatable Read** 같은 트랜잭션 안에서 같은 데이터를 두 번 읽었을 때, 그 사이에 다른 트랜잭션이 수정·커밋하여 값이 달라지는 현상이다.

**Phantom Read** 같은 트랜잭션 안에서 같은 조건으로 조회했을 때, 그 사이에 다른 트랜잭션이 행을 추가·삭제하여 결과 행 수가 달라지는 현상이다.

## 2. DB 레벨 동시성 제어

### 2.1 트랜잭션과 ACID

트랜잭션은 여러 쿼리를 하나의 작업 단위로 묶어 All or Nothing을 보장하는 메커니즘이다.

- **Atomicity (원자성)**: 트랜잭션 내 작업이 전부 성공하거나 전부 실패한다.
- **Consistency (일관성)**: 트랜잭션 전후로 데이터베이스가 일관된 상태를 유지한다.
- **Isolation (격리성)**: 동시에 실행되는 트랜잭션이 서로 간섭하지 않는다.
- **Durability (지속성)**: 커밋된 데이터는 시스템 장애가 발생해도 유지된다.

### 2.2 격리 수준 (Isolation Level)

격리 수준은 동시에 실행되는 트랜잭션 간에 어느 정도까지 서로의 변경 내용을 볼 수 있는지를 정의한다.

|격리 수준|Dirty Read|Non-Repeatable Read|Phantom Read|성능|
|---|---|---|---|---|
|Read Uncommitted|발생|발생|발생|가장 높음|
|Read Committed|방지|발생|발생|높음|
|Repeatable Read|방지|방지|발생 (InnoDB는 방지)|보통|
|Serializable|방지|방지|방지|가장 낮음|

**Read Committed vs Repeatable Read 비교**

- Read Committed: 매 쿼리마다 커밋된 최신 값을 읽는다. 같은 트랜잭션 안에서 값이 바뀔 수 있다. 락 범위가 좁아 경합이 적고 성능이 좋다. 수강신청처럼 최신 상태가 중요한 경우에 적합하다.
- Repeatable Read: 트랜잭션 시작 시점의 스냅샷을 유지한다. 같은 트랜잭션 안에서 항상 같은 값을 읽는다. MySQL InnoDB 기본값이다. 갭락으로 인해 락 범위가 넓어지고 데드락 가능성이 높아진다. 정산이나 보고서처럼 일관된 읽기가 중요한 경우에 적합하다.

**MySQL에서 격리 수준 변경 방법**

```sql
-- 세션 단위
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 글로벌 단위
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

Spring Boot에서는 application.yml로 설정 가능하다.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        connection:
          isolation: 2  # 1=READ_UNCOMMITTED, 2=READ_COMMITTED, 4=REPEATABLE_READ, 8=SERIALIZABLE
```

### 2.3 락 (Lock)

#### 비관적 락 (Pessimistic Lock)

충돌이 발생할 것이라 가정하고, 데이터에 접근하기 전에 미리 잠그는 방식이다.

```sql
SELECT * FROM student WHERE student_id = 1 FOR UPDATE;
-- 이 행에 대해 다른 트랜잭션은 대기
```

- 장점: 충돌이 잦은 환경에서 확실하게 정합성을 보장한다.
- 단점: 대기 시간이 발생하고, 동시 처리량이 떨어진다.
- 적합한 상황: 수강신청, 재고 차감 등 경합이 심한 경우

#### 낙관적 락 (Optimistic Lock)

충돌이 발생하지 않을 것이라 가정하고, 수정 시점에 버전을 비교하여 충돌을 감지하는 방식이다.

```sql
-- 1단계: 읽기
SELECT remaining, version FROM course WHERE course_id = 1;
-- remaining = 5, version = 3

-- 2단계: 수정 (버전 비교)
UPDATE course SET remaining = 4, version = 4
WHERE course_id = 1 AND version = 3;
-- 영향받은 행이 0이면 → 다른 트랜잭션이 먼저 수정한 것 → 재시도
```

- 장점: 락을 잡지 않으므로 대기가 없고 성능이 좋다.
- 단점: 충돌이 잦으면 재시도가 반복되어 오히려 비효율적이다.
- 적합한 상황: 게시글 수정 등 동시에 같은 데이터를 건드릴 확률이 낮은 경우

#### 공유락 / 배타락

- 공유락 (Shared Lock, S Lock): 읽기 락. 여러 트랜잭션이 동시에 공유락을 획득할 수 있다. 공유락이 걸린 행에 쓰기는 불가능하다. `SELECT ... FOR SHARE`로 사용한다.
- 배타락 (Exclusive Lock, X Lock): 쓰기 락. 하나의 트랜잭션만 획득할 수 있다. 배타락이 걸린 행에 다른 읽기/쓰기 모두 대기한다. `SELECT ... FOR UPDATE`로 사용한다.

#### 데드락 (Deadlock)

두 개 이상의 트랜잭션이 서로가 가진 락을 기다리면서 영원히 진행하지 못하는 상태이다.

**발생 예시:**

1. 트랜잭션 A: 학생1 행에 락 획득 → 강좌1 행 락 대기
2. 트랜잭션 B: 강좌1 행에 락 획득 → 학생1 행 락 대기
3. A는 B를 기다리고, B는 A를 기다림 → 영원히 풀리지 않음

**예방 방법:**

- 락 순서를 통일한다 (항상 학생 → 강좌 순서로 잠금)
- 락 타임아웃을 설정한다
- 트랜잭션을 짧게 유지한다
- MySQL InnoDB는 데드락을 자동 감지하고 한쪽 트랜잭션을 롤백한다

### 2.4 락을 사용하지 않는 방식

#### 원자적 업데이트 (Atomic Update)

조회와 수정을 하나의 쿼리로 합쳐서 중간에 다른 요청이 끼어들 수 없게 하는 방식이다.

```sql
UPDATE course SET remaining = remaining - 1
WHERE course_id = 1 AND remaining > 0;
-- 영향받은 행이 0이면 → 이미 마감
```

- 장점: 락 없이도 정합성을 보장하고, 대기가 없어 성능이 좋다.
- 단점: 단순한 연산(증감, 상태 변경)에만 적합하다.
- 비관적 락과의 차이: 비관적 락은 "줄 세워서 한 명씩", 원자적 업데이트는 "줄 안 세우고 조건에 맞으면 통과"

#### 유니크 제약조건 (Unique Constraint)

DB 스키마에 유니크 인덱스를 걸어서 중복 삽입 자체를 DB가 거부하게 만드는 방식이다.

```sql
ALTER TABLE enrollment ADD UNIQUE (student_id, course_id);

-- 중복 INSERT 시도 시 DB가 자동으로 거부
INSERT INTO enrollment (student_id, course_id) VALUES (1, 1);  -- 성공
INSERT INTO enrollment (student_id, course_id) VALUES (1, 1);  -- 에러 발생
```

- 장점: 애플리케이션 로직과 무관하게 DB가 중복을 차단한다.
- 적합한 상황: 중복 신청, 중복 가입 방지 등

**원자적 업데이트 vs 유니크 제약조건:**

- 원자적 업데이트는 UPDATE에서 "값의 안전한 수정"을 보장
- 유니크 제약조건은 INSERT에서 "중복 삽입 방지"를 보장
- 수강신청에서는 둘 다 필요하다 (원자적 업데이트로 정원 초과 방지 + 유니크 제약조건으로 중복 신청 방지)

#### 큐 기반 순차 처리

요청을 바로 처리하지 않고 큐에 넣어서 하나씩 처리하는 방식이다. 동시 접근 자체를 원천적으로 없앤다.

- Kafka: 대규모 트래픽에 적합. 강좌별 파티션으로 순차 처리 가능
- Redis 큐: 간단한 구조에서 LPUSH/BRPOP으로 구현
- RabbitMQ: 순서 보장과 재시도 처리가 잘 되어 있음

## 3. 애플리케이션(Java) 레벨 동시성 제어

같은 JVM(서버 한 대) 안에서 스레드 간 동시성을 제어하는 방법이다. 서버가 여러 대인 환경에서는 단독으로는 부족하다.

### 3.1 synchronized

가장 기본적인 방식. 메서드나 블록에 붙이면 한 스레드만 진입할 수 있다.

```java
public synchronized void enroll(Long studentId, Long courseId) {
    // 한 번에 하나의 스레드만 실행
}
```

- 단점: 모든 요청이 한 줄로 서야 해서 성능이 떨어진다.

### 3.2 ReentrantLock

synchronized보다 유연한 락. tryLock으로 대기 시간 설정, 공정성 설정 등이 가능하다.

```java
private final Lock lock = new ReentrantLock();

public void enroll(Long studentId, Long courseId) {
    lock.lock();
    try {
        // 임계 영역
    } finally {
        lock.unlock();
    }
}
```

### 3.3 userId별 Lock

같은 유저의 요청만 순차 처리하고, 다른 유저는 동시에 처리할 수 있게 하는 방식이다.

```java
private final Map<Long, Lock> locks = new ConcurrentHashMap<>();

public void enroll(Long userId, Long courseId) {
    Lock lock = locks.computeIfAbsent(userId, k -> new ReentrantLock());
    lock.lock();
    try {
        // 같은 userId에 대해서만 순차 실행
    } finally {
        lock.unlock();
    }
}
```

- synchronized보다 성능이 좋다: 다른 유저 간에는 병렬 처리가 가능하기 때문
- 메모리 DB나 Repository를 수정할 수 없는 환경에서 유용하다

### 3.4 Atomic 클래스

CAS(Compare-And-Swap) 연산을 이용해 락 없이 원자적으로 값을 변경한다.

```java
private final AtomicInteger remaining = new AtomicInteger(30);

public boolean enroll() {
    int current = remaining.get();
    if (current <= 0) return false;
    return remaining.compareAndSet(current, current - 1);
}
```

- 장점: 락 없이 동작하므로 매우 빠르다.
- 단점: 단순한 값 변경에만 적합하다.

### 3.5 Semaphore

동시에 접근할 수 있는 스레드 수를 제한한다.

```java
private final Semaphore semaphore = new Semaphore(5); // 최대 5개 동시 처리

public void process() {
    semaphore.acquire();
    try {
        // 최대 5개 스레드만 동시 실행
    } finally {
        semaphore.release();
    }
}
```

### 3.6 스레드 안전 자료구조

자료구조 자체가 내부적으로 동시성을 처리한다.

- ConcurrentHashMap: 동시 읽기/쓰기가 안전한 Map
- ConcurrentLinkedQueue: 락 없이 동작하는 큐
- CopyOnWriteArrayList: 읽기가 많고 쓰기가 적은 상황에 적합한 List

## 4. 분산 환경 동시성 제어

서버가 여러 대이면 Java 레벨 락은 의미가 없다. 서버 간 공유 가능한 외부 저장소를 이용해야 한다.

### 4.1 Redis 분산락

Redis를 이용해 서버 간 공유 락을 구현하는 방식이다.

**기본 원리:**

```
SET lock:course:1 "server-1" NX EX 10
-- NX: 키가 없을 때만 설정 (이미 있으면 실패)
-- EX 10: 10초 후 자동 만료 (서버 죽었을 때 락이 영원히 안 풀리는 것 방지)
```

**Redisson (Java 라이브러리):**

```java
RLock lock = redissonClient.getLock("lock:course:" + courseId);
lock.tryLock(5, 10, TimeUnit.SECONDS); // 5초 대기, 10초 후 자동 해제
try {
    // 임계 영역
} finally {
    lock.unlock();
}
```

- 장점: 서버가 여러 대여도 동작한다.
- 주의점: 락 만료 시간 설정이 중요하다. 너무 짧으면 작업 중에 풀리고, 너무 길면 장애 시 오래 대기한다.

### 4.2 ZooKeeper / etcd 분산락

분산 코디네이터를 이용한 락. Redis보다 강한 일관성을 보장하지만 성능은 상대적으로 떨어진다.

### 4.3 DB 기반 분산락

별도의 락 테이블을 만들어서 행을 INSERT하면 락 획득, DELETE하면 락 해제하는 방식이다. 추가 인프라 없이 구현 가능하지만 성능이 낮다.

## 5. 스케일아웃 시 DB 확장 전략

### 5.1 마스터-레플리카 (Master-Replica)

- 마스터: 쓰기 담당 (INSERT, UPDATE, DELETE)
- 레플리카: 읽기 담당 (SELECT)
- CQRS 관점에서 수강신청/취소는 마스터로, 수강 목록 조회는 레플리카로 라우팅한다.
- 주의: 복제 지연(Replication Lag)이 있어서, 쓰기 직후 읽기는 마스터에서 해야 할 수 있다.

### 5.2 샤딩 (Sharding)

데이터를 여러 DB로 분산시키는 방식이다. 예를 들어 강좌 ID를 기준으로 강좌 1~1000은 DB-A, 1001~2000은 DB-B로 분리하면 쓰기 부하를 분산할 수 있다.

- 장점: 쓰기 부하를 분산할 수 있다.
- 단점: 여러 샤드에 걸친 트랜잭션이나 조인이 어려워진다.

### 5.3 CQRS (Command Query Responsibility Segregation)

읽기와 쓰기를 분리하는 패턴이다.

**단순 CQRS:** 마스터/레플리카 분리, 읽기 쓰기 라우팅만 다르게 한다. 이벤트 없이 구현 가능하다.

**CQRS + 이벤트 드리븐:** 쓰기 시 이벤트를 발행하고, 읽기용 저장소를 별도로 구성한다. 복잡하지만 확장성이 높다.

## 6. 레벨별 정리

|레벨|방식|적용 범위|대표 기술|
|---|---|---|---|
|애플리케이션 (Java)|synchronized, ReentrantLock, userId별 Lock, Atomic 클래스|단일 서버|Java 내장|
|DB|비관적 락, 낙관적 락, 원자적 업데이트, 유니크 제약조건|단일 DB 사용하는 모든 서버|MySQL, PostgreSQL|
|분산|분산락, 큐 기반 순차 처리|서버 여러 대 + DB 여러 대|Redis, Kafka, ZooKeeper|

**핵심 판단 기준:**

- 서버 한 대, 단순한 로직 → synchronized나 userId별 Lock
- 서버 한 대 이상, DB 사용 → DB 레벨 락 또는 원자적 업데이트
- 서버 여러 대, DB 병목 → 분산락 또는 큐 기반 처리
- 읽기 부하 큼 → 마스터/레플리카 분리 (CQRS)
- 쓰기 부하 큼 → 샤딩

## 7. 핵심 흐름

**1단계: 단일 서버에서 어떻게 했냐?** → 동시성 제어 방법 선택과 이유, DB 선택 이유, 격리수준 설정 이유

**2단계: 서버 여러 대가 되면?** → 분산락, 큐 기반 처리, DB 병목 해결 (레플리카, 샤딩)
