## 1단계: 요구사항 확인

> 바로 설계에 들어가지 말고, 먼저 확인한다.

### 기능 요구사항

- **핵심 기능**: 쓰기? 읽기? 둘 다?
- **DAU**: 몇 명이 쓰는 서비스인가? 
- **읽기/쓰기 비율**: 읽기 중심인가, 쓰기 중심인가?
- **데이터 특성**: 텍스트? 이미지? 동영상?

### 비기능 요구사항 _(추가)_

- **가용성(Availability)**: 몇 나인(99.9%? 99.99%?)을 보장해야 하는가?
- **지연 시간(Latency)**: 읽기/쓰기 각각 몇 ms 이내여야 하는가?
- **정합성(Consistency)**: 강한 일관성이 필요한가, 최종 일관성으로 충분한가?
- **실시간성**: 웹소켓/SSE가 필요한가?
- **보안/규제**: 인증, 암호화, GDPR/개인정보 규제 등

> **왜 중요한가?** 비기능 요구사항에 따라 설계가 완전히 달라진다.
> 
> - 읽기 9 : 쓰기 1 → 읽기 최적화에 집중
> - 99.99% 가용성 → 다중 리전, 페일오버 필수
> - 강한 일관성 → 분산 트랜잭션 or 단일 리더 복제

## 2단계: 규모 추정

> 요구사항에서 숫자를 뽑는다. (86,400초 ≈ 10만으로 계산)

| 항목              | 공식                                                 |
| --------------- | -------------------------------------------------- |
| **초당 쓰기 (QPS)** | 하루 총 쓰기(하루 1명당 10건 * DAU 1,000만) ÷ 86,400 = 1,000건 |
| **초당 읽기**       | 초당 쓰기(1,000) × 읽기10/쓰기1 비율 = 10,000건               |
| **피크 QPS**      | 평균 QPS × 2~5배 _(추가)_                               |
| **총 데이터 수**     | 하루 쓰기(1억) × 365 × 서비스 연수(10년) = 3,650억건            |
| **저장 용량**       | 총 데이터(3,650억) × 데이터 하나 크기(100byte) = 35.5TB        |
| **네트워크 대역폭**    | QPS × 응답 크기 _(추가)_                                 |
**1단계:** 500만 × 50 = 2억 5천만 (하루 총 건수) 
**2단계:** 2억 5천만 ÷ 10만 = 2,500 (초당 쓰기) 
**3단계:** 2,500 × 2 = 5,000 (초당 읽기)

1000만 X 10  1억 / 10만  = 1000QPS
읽기QPS 1000X5 = 5000


> **이 결과로 판단하는 것들**
> 
> - 캐시가 필요한가?
> - DB 샤딩이 필요한가?
> - 서버를 몇 대 둘 것인가?
> - CDN이 필요한가? _(대역폭 기반 판단)_

### 예시: URL 단축기

```
DAU 1,000만 × 하루 10건 = 1억 건/일
쓰기 QPS: 1억 ÷ 100,000 ≈ 1,000
피크 쓰기 QPS: 1,000 × 3 = 3,000
읽기 QPS: 1,000 × 10 = 10,000 (읽기:쓰기 = 10:1)
10년 총 데이터: 1억 × 365 × 10 = 3,650억 건
저장 용량: 3,650억 × 100byte = 36.5TB
```

## 3단계: 개략적 설계

### 3-1. API 정의

핵심 API를 먼저 명확하게 정의한다.

- **쓰기 API**: `POST` — 뭘 받아서 뭘 저장하는지
- **읽기 API**: `GET` — 뭘 조회해서 뭘 반환하는지
- **인증**: API Key, OAuth 2.0, JWT 등 _(추가)_
- **Rate Limiting**: API별 요청 제한 정책 _(추가)_

### 3-2. 데이터베이스 선택 _(추가)_

| 기준           | RDB (MySQL, PostgreSQL) | NoSQL (DynamoDB, Cassandra, MongoDB) |
| ------------ | ----------------------- | ------------------------------------ |
| **데이터 구조**   | 관계가 복잡하고 정규화 필요         | 단순 key-value, 문서형, 비정형               |
| **정합성**      | ACID 트랜잭션 필요            | 최종 일관성으로 충분                          |
| **확장 방식**    | 수직 확장 우선, 샤딩은 복잡        | 수평 확장이 기본 설계                         |
| **읽기/쓰기 패턴** | 복잡한 JOIN, 집계 쿼리         | 단순 조회, 대량 쓰기                         |
| **대표 사례**    | 결제, 주문, 사용자 계정          | 로그, 채팅, 피드, 세션                       |

> 하나만 고르는 게 아니라 **폴리글랏 퍼시스턴스**(용도별 DB 혼용)도 고려한다.

### 3-3. 컴포넌트 배치

기본 흐름을 그린다.

```
클라이언트 → CDN (정적) → 로드밸런서 → API Gateway → 웹서버 → 캐시 → DB
```

필요에 따라 추가한다.

| 컴포넌트                      | 언제 추가하는가                                  |
| ------------------------- | ----------------------------------------- |
| **캐시 (Redis)**            | 읽기가 많고, 같은 데이터를 반복 조회할 때                  |
| **메시지 큐 (Kafka, SQS)**    | 쓰기 작업이 무겁거나 비동기 처리가 필요할 때                 |
| **CDN**                   | 이미지, 동영상 등 정적 콘텐츠 전송이 필요할 때               |
| **로드밸런서**                 | 서버를 여러 대로 확장할 때                           |
| **API Gateway**           | 인증, Rate Limiting, 라우팅을 중앙에서 처리할 때 _(추가)_ |
| **검색 엔진 (Elasticsearch)** | 전문 검색, 자동 완성이 필요할 때 _(추가)_                |
| **객체 스토리지 (S3)**          | 이미지, 파일 등 대용량 비정형 데이터 저장 시 _(추가)_         |

## 4단계: 상세 설계 (트레이드오프)

> 가장 중요한 부분을 깊이 파고든다.

### 접근법

1. **선택지를 나란히 놓는다** — A 방식 vs B 방식
2. **각각의 장단점을 설명한다**
3. **하나를 선택하고 근거를 말한다**
4. **필요하면 혼합 전략을 제안한다**

### 트레이드오프 예시

|주제|선택지 A|선택지 B|
|---|---|---|
|URL 단축|해시 후 충돌 해소 (충돌 가능, 예측 어려움)|base-62 변환 (충돌 없음, 예측 가능)|
|리다이렉션|301 영구 (캐싱됨, 추적 불가)|302 임시 (매번 서버 경유, 추적 가능)|
|뉴스 피드|팬아웃 온 라이트 (쓰기 무겁고, 읽기 빠름)|팬아웃 온 리드 (쓰기 가볍고, 읽기 느림)|
|데이터 정합성|강한 일관성 (느리지만 정확)|최종 일관성 (빠르지만 일시적 불일치) _(추가)_|
|ID 생성|UUID (충돌 거의 없음, 정렬 불가)|Snowflake (시간 정렬 가능, 단일 장애점 주의) _(추가)_|

## 5단계: 운영 고려사항 _(추가)_

> 설계만으로는 부족하다. 운영까지 고려해야 완성이다.

### 5-1. 장애 대응 (Fault Tolerance)

|전략|설명|
|---|---|
|**서킷 브레이커**|실패가 반복되면 호출을 차단해서 장애 전파 방지|
|**재시도 + 지수 백오프**|일시적 오류에 대해 간격을 늘려가며 재시도|
|**페일오버**|주 서버 장애 시 대기 서버로 자동 전환|
|**그레이스풀 디그레이데이션**|일부 기능을 포기하고 핵심 기능만 유지|
|**타임아웃 설정**|응답 없는 요청이 리소스를 무한 점유하지 않도록 제한|
|**벌크헤드 패턴**|서비스별로 리소스를 격리해서 한 곳의 장애가 전체로 퍼지지 않게 함|

### 5-2. 모니터링 & 관측성

|영역|도구 예시|목적|
|---|---|---|
|**메트릭**|Prometheus, Grafana|QPS, 지연 시간, 에러율 등 수치 추적|
|**로깅**|ELK Stack, Loki|이벤트 기록, 디버깅|
|**분산 트레이싱**|Jaeger, Zipkin|요청이 여러 서비스를 거치는 경로 추적|
|**알림**|PagerDuty, Slack 연동|임계값 초과 시 즉시 알림|

> 핵심 지표: **에러율, p99 지연 시간, QPS, 서버 리소스 사용률**

## 자주 나오는 빌딩 블록 정리

|개념|한 줄 설명|
|---|---|
|**캐시 (Cache)**|자주 조회되는 데이터를 메모리에 올려 빠르게 응답|
|**로드밸런서**|요청을 여러 서버에 분산|
|**메시지 큐**|비동기 작업 처리 (쓰기 부하 완화)|
|**CDN**|정적 콘텐츠를 사용자 가까운 서버에서 전송|
|**샤딩**|데이터를 쪼개서 여러 DB에 나눠 저장 (쓰기 분산, 용량 확장)|
|**복제 (Replication)**|같은 데이터를 여러 DB에 복사 (읽기 분산, 장애 대비)|
|**CQRS**|쓰기 모델과 읽기 모델을 분리해서 각각 최적화|
|**안정 해시**|서버 추가/제거 시 데이터 재배치 최소화|
|**블룸 필터**|"이미 존재하는가?"를 DB 조회 없이 빠르게 확인|
|**Rate Limiter**|과도한 요청을 제한해서 서버 보호|
|**서킷 브레이커**|장애 전파를 차단 _(추가)_|
|**Saga 패턴**|분산 트랜잭션을 보상 트랜잭션으로 처리 _(추가)_|
|**이벤트 소싱**|상태 대신 이벤트를 저장해서 히스토리 추적 _(추가)_|
|**사이드카 패턴**|서비스 옆에 프록시를 붙여 로깅, 인증 등을 분리 _(추가)_|

> **복제 vs 샤딩 vs CQRS**
> 
> - **복제** = 복사 (같은 데이터, 여러 DB)
> - **샤딩** = 분할 (다른 데이터, 여러 DB)
> - **CQRS** = 읽기/쓰기 분리 (모델 자체를 다르게 설계)
> - 이 셋은 조합해서 쓸 수 있다.
