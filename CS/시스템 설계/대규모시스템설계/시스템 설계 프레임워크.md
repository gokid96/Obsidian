

> 어떤 시스템이 나와도 이 순서는 똑같다. 
> **요구사항 → 규모 추정 → 개략적 설계 → 상세 설계**

---

## 1단계: 요구사항 확인

> 바로 설계에 들어가지 말고, 먼저 확인한다.

- **핵심 기능**: 쓰기? 읽기? 둘 다?
- **DAU**: 몇 명이 쓰는 서비스인가?
- **읽기/쓰기 비율**: 읽기 중심인가, 쓰기 중심인가?
- **데이터 특성**: 텍스트? 이미지? 동영상?
- **제약 조건**: 만료, 삭제, 실시간성, 정합성 등

> [!tip] 왜 중요한가? 제약 조건에 따라 설계가 완전히 달라진다. 
> 예: 읽기 9 : 쓰기 1이면 → 읽기 최적화에 집중 
> 예: 실시간성이 필요하면 → 웹소켓 고려

---

## 2단계: 규모 추정

> 요구사항에서 규모 추정. (86,400초 ≈ 10만으로 계산)

|항목|공식|
|---|---|
|**초당 쓰기 (QPS)**|하루 총 쓰기 ÷ 86,400|
|**초당 읽기**|초당 쓰기 × 읽기/쓰기 비율|
|**총 데이터 수**|하루 쓰기 × 365 × 서비스 연수|
|**저장 용량**|총 데이터 × 데이터 하나 크기|

> [!tip] 이 결과로 판단하는 것들
> 
> - 캐시가 필요한가?
> - DB 샤딩이 필요한가?
> - 서버를 몇 대 둘 것인가?

### 예시: URL 단축기

```
DAU 1,000만 × 하루 10건 = 1억 건/일
쓰기 QPS: 1억 ÷ 100,000 ≈ 1,000
읽기 QPS: 1,000 × 10 = 10,000 (읽기:쓰기 = 10:1)
10년 총 데이터: 1억 × 365 × 10 = 3,650억 건
저장 용량: 3,650억 × 100byte = 36.5TB
```

## 3단계: 개략적 설계

### 3-1. API 정의

핵심 API를 먼저 명확하게 정의

- **쓰기 API**: `POST` — 뭘 받아서 뭘 저장하는지
- **읽기 API**: `GET` — 뭘 조회해서 뭘 반환하는지

### 3-2. 컴포넌트 배치

기본 흐름을 그린다.

```
클라이언트 → 로드밸런서 → 웹서버 → DB
```

필요에 따라 추가한다.

|컴포넌트|언제 추가하는가|
|---|---|
|**캐시 (Redis)**|읽기가 많고, 같은 데이터를 반복 조회할 때|
|**메시지 큐**|쓰기 작업이 무겁거나 비동기 처리가 필요할 때|
|**CDN**|이미지, 동영상 등 정적 콘텐츠 전송이 필요할 때|
|**로드밸런서**|서버를 여러 대로 확장할 때|

## 4단계: 상세 설계 (트레이드오프)

> 가장 중요한 부분을 깊이 파고든다.

### 접근법

1. **선택지를 나란히 놓는다** — A 방식 vs B 방식
2. **각각의 장단점을 설명한다**
3. **하나를 선택하고 근거를 말한다**
4. **필요하면 혼합 전략을 제안한다**

### 트레이드오프 예시

|주제|선택지 A|선택지 B|
|---|---|---|
|URL 단축|해시 후 충돌 해소 (충돌 가능, 예측 어려움)|base-62 변환 (충돌 없음, 예측 가능)|
|리다이렉션|301 영구 (캐싱됨, 추적 불가)|302 임시 (매번 서버 경유, 추적 가능)|
|뉴스 피드|팬아웃 온 라이트 (쓰기 무겁고, 읽기 빠름)|팬아웃 온 리드 (쓰기 가볍고, 읽기 느림)|

## 자주 나오는 빌딩 블록 정리

| 개념                   | 한 줄 설명                               |
| -------------------- | ------------------------------------ |
| **캐시 (Cache)**       | 자주 조회되는 데이터를 메모리에 올려 빠르게 응답          |
| **로드밸런서**            | 요청을 여러 서버에 분산                        |
| **메시지 큐**            | 비동기 작업 처리 (쓰기 부하 완화)                 |
| **CDN**              | 정적 콘텐츠를 사용자 가까운 서버에서 전송              |
| **샤딩**               | 데이터를 쪼개서 여러 DB에 나눠 저장 (쓰기 분산, 용량 확장) |
| **복제 (Replication)** | 같은 데이터를 여러 DB에 복사 (읽기 분산, 장애 대비)     |
| **CQRS**             | 쓰기 모델과 읽기 모델을 분리해서 각각 최적화            |
| **안정 해시**            | 서버 추가/제거 시 데이터 재배치 최소화               |
| **블룸 필터**            | "이미 존재하는가?"를 DB 조회 없이 빠르게 확인         |
| **Rate Limiter**     | 과도한 요청을 제한해서 서버 보호                   |

> [!important] 복제 vs 샤딩 vs CQRS
> 
> - **복제** = 복사 (같은 데이터, 여러 DB)
> - **샤딩** = 분할 (다른 데이터, 여러 DB)
> - **CQRS** = 읽기/쓰기 분리 (모델 자체를 다르게 설계)
> - 이 셋은 조합해서 쓸 수 있다.
