**1단계: 요구사항 확인** 질문합니다.
- 핵심 기능이 뭔가요? (쓰기? 읽기? 둘 다?)
- DAU가 얼마인가요?
- 읽기와 쓰기 비율은 어떤가요?
- 데이터 특성은 뭔가요? (텍스트? 이미지? 동영상?)
- 특별한 제약 조건이 있나요? (만료, 삭제, 실시간성 등)

**2단계: 규모 추정** 요구사항에서 나온 숫자로 암산합니다.
- 초당 쓰기 = 하루 총 쓰기 ÷ 86,400 (암산은 ÷ 10만)
- 초당 읽기 = 초당 쓰기 × 읽기쓰기 비율
- 총 데이터 = 하루 쓰기 × 365 × 연수
- 저장 용량 = 총 데이터 × 데이터 하나 크기

이 결과로 "캐시가 필요한가", "DB 샤딩이 필요한가", "서버를 몇 대 둘 건가"를 판단

**3단계: 개략적 설계** 핵심 API를 먼저 정의합니다.
- 쓰기 API: POST 요청으로 뭘 받아서 뭘 저장하는지
- 읽기 API: GET 요청으로 뭘 조회해서 뭘 반환하는지

그다음 주요 컴포넌트를 배치합니다.
- 클라이언트 → 로드밸런서 → 웹서버 → DB
- 필요하면 캐시, 메시지 큐, CDN 추가

**4단계: 핵심 컴포넌트 상세 설계** 면접관과 합의해서 가장 중요한 부분을 깊이 파고듭니다.
- 여기서 트레이드오프 비교가 나옵니다
- 선택지를 나란히 놓고 장단점을 설명합니다
- 하나를 선택하고 "왜 이걸 선택했는지" 근거를 말합니다

---
**요구사항 → 규모 추정 → 개략적 설계(API + 컴포넌트) → 상세 설계(트레이드오프)**
