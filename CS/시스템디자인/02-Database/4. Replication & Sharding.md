
**레플리케이션(Replication):** 같은 데이터를 여러 DB에 복제하여 가용성과 읽기 성능을 높이는 것
**샤딩(Sharding):** 데이터를 쪼개서 여러 DB에 분산 저장하여 용량과 쓰기 성능을 높이는 것

---


단일 DB는 반드시 한계에 도달한다. 트래픽이 늘어나면 읽기 부하를, 데이터가 늘어나면 저장 용량을, 장애 상황에서는 가용성을 해결해야 한다. 레플리케이션과 샤딩은 DB 계층의 **스케일 아웃 전략**이며, 시스템 설계에서 DB 확장 문제가 나오면 반드시 등장한다.

---

## Replication (복제)

### 핵심 아이디어

같은 데이터를 가진 DB를 여러 대 두는 것이다.

```
[Primary (Master)]  ──복제──→  [Replica 1 (Slave)]
                    ──복제──→  [Replica 2 (Slave)]
                    ──복제──→  [Replica 3 (Slave)]
```

### 왜 필요한가

1. **읽기 성능 향상**: 읽기 요청을 여러 Replica에 분산
2. **고가용성(HA)**: Primary가 죽어도 Replica가 승격하여 서비스 지속
3. **지리적 분산**: 사용자와 가까운 Replica에서 읽기 → 지연 시간 감소

---

### Master-Slave (Primary-Replica) 구조

가장 일반적인 레플리케이션 구조다.

```
쓰기(INSERT/UPDATE/DELETE) → [Primary] ──복제──→ [Replica 1]
읽기(SELECT)               → [Replica 1]        [Replica 2]
                           → [Replica 2]        [Replica 3]
                           → [Replica 3]
```

**규칙**: 쓰기는 Primary에만, 읽기는 Replica에서 처리한다.

**장점**:

- 읽기 부하를 Replica에 분산하여 Primary 부담 감소
- 대부분의 웹 서비스는 읽기가 80~90%이므로 효과가 크다
- Replica 추가만으로 읽기 성능을 선형적으로 확장 가능

**한계**:

- 쓰기는 여전히 Primary 한 대에 집중 → 쓰기 병목 해결 불가
- Primary 장애 시 Replica 승격(Failover) 과정이 필요

### Master-Master (Multi-Primary) 구조

여러 노드가 모두 쓰기를 받을 수 있는 구조다.

```
[Primary A] ←──복제──→ [Primary B]
  ↑ 쓰기                  ↑ 쓰기
```

**장점**: 쓰기 부하도 분산 가능, 지리적으로 분산된 쓰기 처리

**한계**: 양쪽에서 같은 데이터를 동시에 수정하면 **쓰기 충돌(Write Conflict)**이 발생한다. 충돌 해결 전략이 복잡하고, 데이터 정합성 유지가 어렵다.

**시스템 설계에서의 의미**: 대부분의 서비스는 Master-Slave로 충분하다. Master-Master는 글로벌 서비스에서 지역별 쓰기 지연을 줄여야 할 때 고려하며, 충돌 해결 비용을 감수해야 한다.

---
### 복제 방식

#### 동기 복제 (Synchronous)
```
[클라이언트] → [Primary] ──쓰기──→ [Replica에 복제 완료] → COMMIT 응답
```

Primary가 Replica에 복제가 완료된 것을 확인한 후에야 클라이언트에 응답한다.

- 장점: 데이터 유실 없음. Primary가 죽어도 Replica에 최신 데이터 보장
- 단점: Replica 응답을 기다려야 하므로 **쓰기 지연 증가**. Replica가 느리면 전체가 느려짐

#### 비동기 복제 (Asynchronous)
```
[클라이언트] → [Primary] → COMMIT 응답 (즉시)
                         ──나중에 복제──→ [Replica]
```

Primary가 쓰기를 완료하면 바로 응답하고, Replica에는 비동기로 복제한다.

- 장점: 쓰기 성능이 빠름. Replica 상태에 영향받지 않음
- 단점: Primary 장애 시 아직 복제되지 않은 데이터 유실 가능 (**Replication Lag**)

#### 반동기 복제 (Semi-Synchronous)

최소 1개의 Replica에 복제되면 응답한다. 동기와 비동기의 절충안.

**시스템 설계에서의 의미**: 금융/결제 → 동기 복제 (데이터 유실 불가), SNS/로그 → 비동기 복제 (성능 우선). 이것이 **데이터 안전성 vs 쓰기 성능 트레이드오프**다.

---

### Replication Lag (복제 지연)

비동기 복제에서 Primary와 Replica 사이에 데이터 차이가 생기는 현상이다.

```
시점 1: Primary에 새 글 작성 완료
시점 2: 사용자가 바로 새로고침 → Replica에서 읽기 → 아직 복제 안 됨 → "글이 없다?!"
시점 3: 0.5초 후 Replica에 복제 완료 → 이제 보임
```

#### 해결 전략

**Read-After-Write Consistency**: 자기가 쓴 데이터는 Primary에서 읽는다.

```
쓰기 직후 자신의 데이터 조회 → Primary에서 읽기
그 외 일반 읽기 → Replica에서 읽기
```

**Monotonic Read**: 한 사용자의 요청이 항상 같은 Replica로 가도록 고정한다. 최신 데이터를 본 후 과거 데이터를 보는 현상을 방지한다.

---

### Failover (장애 복구)

Primary가 죽었을 때 Replica 중 하나를 Primary로 승격하는 과정이다.

```
정상 상태:
[Primary] → [Replica 1] → [Replica 2]

Primary 장애:
[Primary ❌] → [Replica 1 🔺 새 Primary로 승격] → [Replica 2]
                              ↑
                      다른 Replica들이 새 Primary를 바라봄
```

**자동 Failover 과정**:

1. 헬스체크로 Primary 장애 감지
2. 가장 최신 데이터를 가진 Replica 선택
3. 해당 Replica를 Primary로 승격
4. 나머지 Replica들의 복제 대상 변경
5. 애플리케이션의 DB 연결 대상 변경 (DNS 또는 프록시 사용)

**문제점**: 비동기 복제 중이었다면 승격된 Replica에 최신 데이터가 없을 수 있다 → 데이터 유실 가능. 이것이 동기 vs 비동기 복제 선택의 핵심 고려 사항이다.

---

## Sharding (샤딩)

### 핵심 아이디어

데이터를 **특정 기준(Shard Key)**으로 쪼개서 여러 DB에 분산 저장하는 것이다.

```
레플리케이션: 같은 데이터를 복사         → 읽기 확장
샤딩:       다른 데이터를 나눠서 저장    → 쓰기 + 용량 확장
```

```
전체 사용자 데이터:
[Shard 1: user_id 1~1000000]
[Shard 2: user_id 1000001~2000000]
[Shard 3: user_id 2000001~3000000]
```

### 왜 필요한가

- 단일 DB의 저장 용량 한계 돌파
- 쓰기 부하 분산 (레플리케이션으로 해결 불가능한 부분)
- 인덱스 크기 축소 → 각 샤드의 쿼리 성능 향상

---

### Shard Key 선택

샤딩에서 **가장 중요한 결정**이 Shard Key 선택이다. 잘못 선택하면 특정 샤드에 데이터가 몰리는 **핫스팟(Hotspot)** 문제가 발생한다.

#### 좋은 Shard Key의 조건

1. **균등 분산**: 데이터가 샤드에 고르게 분포
2. **쿼리 효율성**: 자주 사용하는 쿼리가 단일 샤드에서 처리 가능
3. **확장 용이성**: 샤드 추가 시 재분배가 수월

#### 예시

```
❌ 나쁜 Shard Key: 가입 날짜
→ 최근 샤드에 신규 사용자가 몰림 (핫스팟)
→ 오래된 샤드는 거의 사용되지 않음

❌ 나쁜 Shard Key: 국가
→ 한국 샤드에 대부분의 데이터가 몰림 (불균등)

✅ 좋은 Shard Key: user_id (해시)
→ 해시 함수로 균등 분산
→ 사용자별 쿼리가 단일 샤드에서 처리됨
```

---

### 샤딩 전략

#### Range-Based Sharding (범위 기반)

Shard Key의 값 범위로 분할한다.

```
Shard 1: user_id 1 ~ 1,000,000
Shard 2: user_id 1,000,001 ~ 2,000,000
Shard 3: user_id 2,000,001 ~ 3,000,000
```

- 장점: 범위 쿼리(BETWEEN)에 효율적, 구현이 단순
- 단점: 특정 범위에 데이터가 몰릴 수 있음 (핫스팟)

#### Hash-Based Sharding (해시 기반)

Shard Key에 해시 함수를 적용하여 분배한다.

```
shard_number = hash(user_id) % 샤드_수

hash(12345) % 3 = 0 → Shard 0
hash(67890) % 3 = 1 → Shard 1
hash(11111) % 3 = 2 → Shard 2
```

- 장점: 데이터가 균등하게 분산됨
- 단점: 범위 쿼리가 모든 샤드를 조회해야 함, 샤드 추가 시 대량 데이터 재배치 필요

#### Directory-Based Sharding (디렉터리 기반)

별도의 매핑 테이블(Lookup Table)이 어떤 데이터가 어느 샤드에 있는지를 관리한다.

```
[Lookup Table]
user_id 12345 → Shard 2
user_id 67890 → Shard 1
user_id 11111 → Shard 3
```

- 장점: 유연한 분배 가능, 샤드 이동 용이
- 단점: Lookup Table 자체가 SPOF이자 병목이 될 수 있음

---

### Consistent Hashing

Hash-Based Sharding의 치명적 단점을 해결하는 기법이다.

**문제**: 일반 해시에서 샤드를 추가/제거하면 거의 모든 데이터의 위치가 바뀐다.

```
hash(key) % 3 → 샤드 0, 1, 2
hash(key) % 4 → 대부분의 키가 다른 샤드로 이동 (대규모 재배치)
```

**Consistent Hashing 해결**: 해시 공간을 원형(ring)으로 만들고, 샤드 추가/제거 시 **인접한 데이터만 이동**한다.

```
        Shard A
       /       \
  Key 1    Hash Ring    Key 3
       \       /
        Shard B
       /       \
  Key 2         Key 4
       \       /
        Shard C

Shard D 추가 시: Shard C의 일부 데이터만 Shard D로 이동
(나머지 샤드의 데이터는 그대로)
```

**시스템 설계에서의 의미**: Consistent Hashing은 DynamoDB, Cassandra, 캐시 시스템(Memcached) 등에서 핵심적으로 사용된다. 자세한 내용은 [[Consistent Hashing]]에서 다룬다.

---

### 샤딩의 문제점

#### 1. Cross-Shard JOIN 불가

데이터가 여러 샤드에 분산되어 있으므로 JOIN이 매우 어렵거나 불가능하다.

```sql
-- user_id로 샤딩했는데 다른 테이블과 JOIN 필요
SELECT u.name, o.total
FROM users u JOIN orders o ON u.id = o.user_id
-- users와 orders가 같은 샤드에 있어야만 효율적
```

**해결**: 비정규화, 같은 Shard Key로 관련 테이블을 함께 샤딩(Co-located Sharding), 또는 애플리케이션 레벨에서 조합.

#### 2. Cross-Shard 트랜잭션

여러 샤드에 걸친 트랜잭션은 2PC나 Saga 패턴이 필요하다. [[Transaction & ACID]]에서 다룬 분산 트랜잭션의 복잡성이 그대로 적용된다.

#### 3. 데이터 리밸런싱

특정 샤드에 데이터가 쏠리면 리밸런싱이 필요하다. 운영 중 리밸런싱은 서비스 중단 없이 처리해야 하므로 매우 어렵다.

#### 4. 핫스팟

특정 사용자(예: 유명인)의 데이터가 있는 샤드에 요청이 집중되는 현상.

**해결**: 핫 키를 더 세분화하거나, 캐시 레이어로 흡수한다.

## 레플리케이션 + 샤딩 조합

실무에서는 두 기법을 함께 사용한다.

```
[Shard 1]                    [Shard 2]                    [Shard 3]
  Primary ──→ Replica 1        Primary ──→ Replica 1        Primary ──→ Replica 1
           ──→ Replica 2                ──→ Replica 2                ──→ Replica 2
  (user 1~100만)              (user 100만~200만)            (user 200만~300만)
```

각 샤드 내에서 레플리케이션으로 읽기 확장 + 고가용성을 확보하고, 샤드 간에는 데이터를 분산하여 쓰기 확장 + 용량 확장을 달성한다.

---

## 샤딩 전에 고려할 것

샤딩은 복잡도를 크게 높이므로 **최후의 수단**이다. 그 전에:

```
1. 인덱스 최적화 → 아직 안 했으면 먼저
2. 쿼리 최적화 → 불필요한 풀스캔 제거
3. 캐시 도입 → Redis로 읽기 부하 흡수
4. 읽기 레플리카 추가 → 읽기 분산
5. 수직 확장 (Scale Up) → 더 좋은 서버로 교체
6. 그래도 안 되면 → 샤딩
```

## 시스템 설계와의 연결 포인트

|개념|시스템 설계에서의 활용|
|---|---|
|Master-Slave|읽기 분산, 가장 기본적인 DB 확장|
|동기 vs 비동기 복제|데이터 안전성 vs 성능 트레이드오프|
|Replication Lag|Read-After-Write Consistency 전략|
|Failover|고가용성(HA) 설계|
|Shard Key 선택|핫스팟 방지, 쿼리 효율성|
|Consistent Hashing|샤드 추가/제거 시 최소 재배치|
|Cross-Shard 문제|비정규화, Saga 패턴 필요성|
|레플리케이션 + 샤딩|실무 DB 아키텍처의 완성형|

## 핵심 요약

> 레플리케이션은 같은 데이터를 복제하여 읽기 성능과 가용성을 높이고, 샤딩은 데이터를 분할하여 쓰기 성능과 저장 용량을 확장한다. 레플리케이션의 핵심 트레이드오프는 동기 vs 비동기(안전성 vs 성능)이고, 샤딩의 핵심은 Shard Key 선택(균등 분산 vs 쿼리 효율성)이다. 실무에서는 둘을 조합하되, 샤딩은 복잡도가 매우 높으므로 인덱스 → 캐시 → 레플리카 → 스케일 업을 먼저 시도한 후 최후의 수단으로 사용한다.
