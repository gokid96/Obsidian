
트랜잭션은 **하나의 논리적 작업 단위로 묶인 DB 연산들의 집합**이며, ACID는 트랜잭션이 지켜야 할 4가지 속성이다.

---

"은행 송금 중에 서버가 죽으면 돈이 사라지나?"라는 질문의 답이 트랜잭션에 있다. 시스템 설계에서 데이터 정합성을 보장하는 근본 메커니즘이 트랜잭션이며, 분산 환경에서 ACID를 완벽히 지키기 어렵다는 한계가 [[CAP Theorem]]과 NoSQL 선택의 출발점이 된다.

---

## 트랜잭션이란

### 핵심 예시: 계좌 이체

A가 B에게 10만 원을 보내는 작업:

```sql
-- 이 두 작업은 반드시 함께 성공하거나 함께 실패해야 한다
BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100000 WHERE user = 'A';  -- 1. A에서 출금
  UPDATE accounts SET balance = balance + 100000 WHERE user = 'B';  -- 2. B에 입금
COMMIT;
```

만약 1번은 성공했는데 2번 전에 서버가 죽으면? 트랜잭션이 없다면 A의 돈은 빠져나갔는데 B에게 도착하지 않는 상황이 발생한다. 트랜잭션은 이런 일이 **절대 일어나지 않도록** 보장한다.

### 트랜잭션의 상태

```
BEGIN → [Active] → COMMIT → [Committed] ✅ 모든 변경 확정
                 → ROLLBACK → [Aborted] ❌ 모든 변경 취소 (원래 상태로)
```

## ACID 속성

### A — Atomicity (원자성)

**"전부 아니면 전무 (All or Nothing)"**

트랜잭션 내 연산은 모두 성공하거나 모두 실패한다. 중간 상태는 존재하지 않는다.

```
✅ 1. A 출금 성공 + 2. B 입금 성공 → COMMIT (둘 다 반영)
❌ 1. A 출금 성공 + 2. B 입금 실패 → ROLLBACK (A 출금도 취소)
```

**구현 방식**: DB는 변경 전 상태를 **Undo 로그**에 기록한다. 실패 시 이 로그를 역순으로 실행하여 원래 상태로 복원한다.

**시스템 설계에서의 의미**: 마이크로서비스 환경에서는 하나의 트랜잭션이 여러 서비스에 걸칠 수 있다. 이때 원자성을 보장하기 위해 **Saga 패턴**이나 **보상 트랜잭션**을 사용한다.

---
### C — Consistency (일관성)

**"트랜잭션 전후로 DB의 무결성 제약 조건이 항상 만족된다"**

```
제약 조건: balance >= 0 (잔고는 음수가 될 수 없다)

A 잔고: 50000원
A가 100000원 송금 시도 → balance = -50000 → 제약 위반 → ROLLBACK
```

일관성은 DB 제약 조건(NOT NULL, UNIQUE, CHECK, FK)과 애플리케이션 로직이 함께 보장한다.

**시스템 설계에서의 의미**: 분산 시스템에서는 "일관성"의 의미가 달라진다. ACID의 일관성은 단일 DB 내 제약 조건이지만, 분산 시스템의 일관성(CAP의 C)은 여러 노드 간 데이터 동기화를 의미한다. 이 차이를 명확히 구분해야 한다.

---
### I — Isolation (격리성)

**"동시에 실행되는 트랜잭션들이 서로 영향을 주지 않는다"**

두 사람이 동시에 같은 계좌에서 출금하면 어떻게 되는가?

```
A 잔고: 100000원

트랜잭션 1: 50000원 출금     트랜잭션 2: 70000원 출금
읽기: 잔고 = 100000          읽기: 잔고 = 100000
쓰기: 잔고 = 50000           쓰기: 잔고 = 30000

격리성 없으면: 최종 잔고 30000 (총 120000원 출금됨 — 잔고 초과!)
격리성 있으면: 트랜잭션 1 완료 후 트랜잭션 2 실행 → 잔고 부족으로 ROLLBACK
```

#### 격리 수준 (Isolation Level)

완벽한 격리(Serializable)는 성능이 낮다. 그래서 DB는 격리 수준을 단계적으로 제공한다.

| 격리 수준            | Dirty Read | Non-Repeatable Read | Phantom Read | 성능    |
| ---------------- | ---------- | ------------------- | ------------ | ----- |
| Read Uncommitted | 발생         | 발생                  | 발생           | 가장 빠름 |
| Read Committed   | ✅ 방지       | 발생                  | 발생           | 빠름    |
| Repeatable Read  | ✅ 방지       | ✅ 방지                | 발생           | 보통    |
| Serializable     | ✅ 방지       | ✅ 방지                | ✅ 방지         | 가장 느림 |

**각 문제 설명:**

- **Dirty Read**: 다른 트랜잭션이 아직 커밋하지 않은 데이터를 읽는 것
- **Non-Repeatable Read**: 같은 행을 두 번 읽었는데 중간에 다른 트랜잭션이 수정하여 값이 달라짐
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 중간에 다른 트랜잭션이 행을 추가/삭제하여 결과 행 수가 달라짐

**시스템 설계에서의 의미**: 대부분의 서비스는 **Read Committed**(PostgreSQL 기본) 또는 **Repeatable Read**(MySQL InnoDB 기본)를 사용한다. Serializable은 동시 처리 성능이 너무 떨어져서 거의 사용하지 않는다. 격리 수준 선택이 **동시성 vs 정합성 트레이드오프**다.

---
### D — Durability (지속성)

**"커밋된 트랜잭션의 결과는 영구적으로 보존된다"**

커밋 후 서버가 꺼지거나 디스크 장애가 발생해도 데이터는 유실되지 않는다.

**구현 방식**: 커밋 시 **WAL(Write-Ahead Log)**에 먼저 기록한다. 장애 복구 시 WAL을 재실행(replay)하여 데이터를 복원한다.

```
1. 트랜잭션 실행
2. WAL에 변경 내용 기록 (디스크에 즉시 쓰기)
3. COMMIT 응답
4. 실제 데이터 파일에 반영 (나중에 비동기로)

→ 3번 이후 서버가 죽어도 WAL에서 복구 가능
```

**시스템 설계에서의 의미**: WAL은 DB 레플리케이션의 기반이기도 하다. Primary 서버의 WAL을 Replica에 전송하여 데이터를 동기화한다. 이 개념은 [[Replication & Sharding]]에서 다시 등장한다.

## 락 (Lock) 메커니즘

격리성을 구현하기 위해 DB는 락을 사용한다.

### 락의 종류

| 락                       | 설명                       | 호환성               |
| ----------------------- | ------------------------ | ----------------- |
| Shared Lock (S Lock)    | 읽기 락. 여러 트랜잭션이 동시에 읽기 가능 | S-S 호환 ✅          |
| Exclusive Lock (X Lock) | 쓰기 락. 하나의 트랜잭션만 접근 가능    | S-X, X-X 모두 비호환 ❌ |

```
트랜잭션 1: SELECT → S Lock 획득 (다른 읽기 허용)
트랜잭션 2: SELECT → S Lock 획득 ✅ (동시 읽기 가능)
트랜잭션 3: UPDATE → X Lock 필요 → 대기 ❌ (S Lock 해제될 때까지)
```

### 데드락 (Deadlock)

두 트랜잭션이 서로가 가진 락을 기다리면서 영원히 진행하지 못하는 상태.

```
트랜잭션 1: A 행 락 획득 → B 행 락 대기...
트랜잭션 2: B 행 락 획득 → A 행 락 대기...
→ 서로 무한 대기 = 데드락
```

**해결 방법**: DB가 데드락을 감지하면 하나의 트랜잭션을 강제 ROLLBACK한다. 애플리케이션에서는 재시도 로직을 구현해야 한다.

**시스템 설계에서의 의미**: 데드락은 분산 시스템의 [[Concurrency (Lock, Race Condition)]]에서도 동일하게 발생하며, 분산 락(Redis Lock, ZooKeeper Lock)을 사용할 때 특히 주의해야 한다.

### 낙관적 락 vs 비관적 락

| 방식                  | 접근                       | 적합한 상황         |
| ------------------- | ------------------------ | -------------- |
| 비관적 락 (Pessimistic) | 데이터를 읽을 때 미리 락을 건다       | 충돌이 자주 발생하는 경우 |
| 낙관적 락 (Optimistic)  | 락 없이 작업하고, 커밋 시 충돌을 확인한다 | 충돌이 드문 경우      |

```sql
-- 비관적 락: SELECT FOR UPDATE
SELECT balance FROM accounts WHERE user = 'A' FOR UPDATE;
-- → 다른 트랜잭션이 이 행에 접근 불가

-- 낙관적 락: 버전 번호 활용
UPDATE accounts SET balance = 50000, version = 2
WHERE user = 'A' AND version = 1;
-- → version이 1이 아니면 (누군가 먼저 수정했으면) 업데이트 실패 → 재시도
```

**시스템 설계에서의 의미**: 읽기가 많고 충돌이 드문 서비스(상품 조회 등)는 낙관적 락이 성능에 유리하다. 금융처럼 충돌이 치명적인 경우에는 비관적 락을 사용한다.

## 분산 환경에서의 트랜잭션

단일 DB에서는 ACID가 자연스럽게 보장되지만, 서비스가 커져서 DB가 분리되면 문제가 복잡해진다.

### 2PC (Two-Phase Commit)

여러 DB에 걸친 트랜잭션을 원자적으로 처리하는 프로토콜.

```
[코디네이터]
    Phase 1 (Prepare): "커밋할 준비 됐어?"
        → [DB A]: "준비 완료"
        → [DB B]: "준비 완료"
    Phase 2 (Commit): "모두 커밋해"
        → [DB A]: COMMIT
        → [DB B]: COMMIT
```

**한계**: 코디네이터가 SPOF, 모든 참여자가 응답할 때까지 대기(블로킹), 성능 저하. 대규모 분산 시스템에서는 거의 사용하지 않는다.

### Saga 패턴

각 서비스가 로컬 트랜잭션을 실행하고, 실패 시 **보상 트랜잭션**으로 되돌린다.

```
주문 생성 → 결제 처리 → 재고 차감 → 배송 요청

만약 재고 차감 실패:
배송 요청 ← 취소 (보상)
재고 차감 ← 원복 (보상)
결제 처리 ← 환불 (보상)
주문 생성 ← 취소 (보상)
```

**시스템 설계에서의 의미**: 마이크로서비스 아키텍처에서 서비스 간 트랜잭션은 Saga 패턴이 사실상 표준이다. 완벽한 ACID 대신 **최종 일관성(Eventual Consistency)**을 받아들이는 것이 핵심 트레이드오프다.

## ACID vs BASE

대규모 분산 시스템에서 ACID를 완벽히 지키기 어려워지면서 등장한 대안이 BASE다.

|속성|ACID|BASE|
|---|---|---|
|풀네임|Atomicity, Consistency, Isolation, Durability|Basically Available, Soft state, Eventually consistent|
|일관성|강한 일관성 (즉시 반영)|최종 일관성 (시간이 지나면 일치)|
|가용성|일관성 우선|가용성 우선|
|적합한 DB|RDB (MySQL, PostgreSQL)|NoSQL (Cassandra, DynamoDB)|
|적합한 서비스|금융, 결제, 재고|SNS 피드, 추천, 로그|

**시스템 설계에서의 의미**: "이 데이터는 ACID가 필요한가, BASE로 충분한가?"가 DB 선택과 아키텍처를 결정하는 핵심 질문이다. 하나의 시스템 안에서도 도메인별로 다를 수 있다 — 결제는 ACID, 좋아요 카운트는 BASE.

## 시스템 설계와의 연결 포인트

| 트랜잭션 개념      | 시스템 설계에서의 활용      |
| ------------ | ----------------- |
| 원자성          | Saga 패턴, 보상 트랜잭션  |
| 격리 수준        | 동시성 vs 정합성 트레이드오프 |
| WAL          | 레플리케이션, 장애 복구     |
| 데드락          | 분산 락, 재시도 전략      |
| 낙관적/비관적 락    | 워크로드별 동시성 제어 전략   |
| 2PC vs Saga  | 분산 트랜잭션 설계        |
| ACID vs BASE | DB 선택, 일관성 모델 결정  |

## 핵심 요약

> 트랜잭션은 ACID(원자성, 일관성, 격리성, 지속성)를 통해 데이터 정합성을 보장하는 메커니즘이다. 단일 DB에서는 자연스럽게 작동하지만, 분산 환경에서는 ACID를 완벽히 지키기 어려워 Saga 패턴과 최종 일관성(BASE)이라는 트레이드오프를 받아들여야 한다. 격리 수준과 락 전략은 동시성과 정합성 사이의 균형점을 결정하며, 이 판단이 시스템의 성능과 안정성을 좌우한다.
