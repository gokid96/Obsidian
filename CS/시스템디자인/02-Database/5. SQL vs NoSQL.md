
**SQL(관계형 DB)** 은 정해진 스키마와 테이블 관계 위에서 ACID를 보장하는 DB이고, 
**NoSQL(비관계형 DB)** 은 유연한 스키마와 수평 확장을 우선으로 설계된 DB의 총칭이다.

---

## 왜 알아야 하는가

시스템 설계에서 "DB를 뭘 쓸 것인가?"는 가장 먼저 나오는 질문 중 하나다. 이 선택에 따라 데이터 모델, 일관성 수준, 확장 전략, 쿼리 패턴이 모두 달라진다. 정답은 없고 **워크로드 특성에 따른 트레이드오프**만 있다.

---

## SQL (관계형 데이터베이스)

### 대표 DB
MySQL, PostgreSQL, Oracle, SQL Server, MariaDB

### 핵심 특성

#### 1. 고정 스키마 (Schema)

테이블 구조를 먼저 정의하고, 그 구조에 맞는 데이터만 저장할 수 있다.
```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(200) UNIQUE,
    age INT
);
-- age에 문자열을 넣으면 → 에러
-- email 없이 INSERT하면 → 에러 (UNIQUE 제약은 아니지만 구조 강제)
```

**장점**: 데이터 무결성 보장, 스키마가 곧 문서화 
**단점**: 스키마 변경(ALTER TABLE)이 대규모 테이블에서 매우 비용이 큼

#### 2. 관계 (Relationship)

테이블 간 관계를 Foreign Key로 명시적으로 정의한다.

```sql
-- users와 orders는 1:N 관계
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT REFERENCES users(id),  -- FK
    product VARCHAR(200),
    total INT
);

-- JOIN으로 관계 데이터 조회
SELECT u.name, o.product, o.total
FROM users u JOIN orders o ON u.id = o.user_id;
```

#### 3. ACID 트랜잭션

[[Transaction & ACID]]에서 다룬 원자성, 일관성, 격리성, 지속성을 기본 보장한다. 금융, 결제 등 데이터 정합성이 핵심인 도메인에서 필수적이다.
#### 4. SQL 쿼리 언어

수십 년간 검증된 표준 쿼리 언어다. 복잡한 집계, 서브쿼리, 윈도우 함수 등 강력한 데이터 처리가 가능하다.

```sql
-- 월별 매출 상위 5개 상품
SELECT product, SUM(total) as revenue
FROM orders
WHERE created_at >= '2025-01-01'
GROUP BY product
ORDER BY revenue DESC
LIMIT 5;
```

### SQL DB의 한계

- **수평 확장이 어렵다**: JOIN, 트랜잭션이 여러 노드에 걸치면 복잡도가 급증
- **스키마 변경 비용**: 수억 행 테이블에 컬럼 추가는 몇 시간~며칠 소요 가능
- **쓰기 확장 한계**: 레플리케이션으로 읽기는 확장되지만 쓰기는 단일 Primary에 의존

## NoSQL (비관계형 데이터베이스)

### "NoSQL"의 의미

"No SQL"이 아니라 **"Not Only SQL"**이다. SQL을 부정하는 것이 아니라 SQL만으로 해결할 수 없는 문제를 위한 대안이라는 뜻이다.

### NoSQL의 4가지 유형

#### 1. Key-Value Store

가장 단순한 구조. 키로 값을 저장하고 조회한다.

```
key: "user:12345"  →  value: "{name: 홍길동, age: 25}"
key: "session:abc" →  value: "{user_id: 12345, expires: ...}"
```

- **대표 DB**: Redis, DynamoDB, Memcached
- **적합한 용도**: 캐싱, 세션 저장, 실시간 리더보드, Rate Limiting 카운터
- **특징**: O(1) 조회, 매우 빠름, 구조가 단순해서 수평 확장 용이

#### 2. Document Store

JSON/BSON 형태의 문서를 저장한다. Key-Value의 확장으로, 값(Value) 내부를 쿼리할 수 있다.

```json
// users 컬렉션의 문서
{
  "_id": "12345",
  "name": "홍길동",
  "email": "hong@mail.com",
  "orders": [
    {"product": "노트북", "total": 1500000},
    {"product": "마우스", "total": 30000}
  ],
  "address": {
    "city": "서울",
    "district": "강남"
  }
}
```

- **대표 DB**: MongoDB, CouchDB
- **적합한 용도**: 콘텐츠 관리, 사용자 프로필, 상품 카탈로그 (스키마가 유동적인 데이터)
- **특징**: 유연한 스키마(Schemaless), 문서 내 중첩 데이터로 JOIN 불필요, 비정규화 친화적

#### 3. Wide-Column Store

행마다 다른 컬럼을 가질 수 있는 구조다. 대규모 데이터의 빠른 쓰기와 읽기에 최적화되어 있다.

```
Row Key: "user:12345"
  Column Family "profile": {name: "홍길동", age: 25}
  Column Family "activity": {last_login: "2025-02-13", login_count: 142}

Row Key: "user:67890"
  Column Family "profile": {name: "김영희", age: 30, nickname: "kim"}
  -- activity가 없어도 됨 (유연한 구조)
```

- **대표 DB**: Cassandra, HBase, ScyllaDB
- **적합한 용도**: 시계열 데이터, IoT 센서 데이터, 로그 수집, 대규모 분석
- **특징**: 쓰기 최적화(LSM Tree 기반), 샤딩 내장, 수평 확장에 강함

#### 4. Graph DB

노드(Node)와 관계(Edge)로 데이터를 표현한다.

```
(홍길동) --[친구]--> (김영희)
(홍길동) --[좋아요]--> (게시글 A)
(김영희) --[작성]--> (게시글 A)
```

- **대표 DB**: Neo4j, Amazon Neptune
- **적합한 용도**: 소셜 네트워크, 추천 시스템, 사기 탐지, 지식 그래프
- **특징**: 관계 탐색이 매우 빠름. SQL에서 여러 번 JOIN해야 할 것을 한 번의 그래프 순회로 처리

## 핵심 비교

|항목|SQL|NoSQL|
|---|---|---|
|스키마|고정 (엄격)|유연 (Schemaless)|
|데이터 모델|테이블 + 행 + 열|문서, Key-Value, 컬럼, 그래프|
|관계|JOIN으로 표현|비정규화(내장)로 표현|
|트랜잭션|ACID 기본 보장|보통 BASE (일부 ACID 지원)|
|확장 방식|수직 확장 중심 (수평 어려움)|수평 확장 중심 (샤딩 내장)|
|쿼리|표준 SQL (강력한 집계)|DB마다 다른 쿼리 방식|
|일관성|강한 일관성|최종 일관성 (설정 가능)|
|성숙도|수십 년 검증|상대적으로 새로움|

## 선택 기준: 언제 SQL, 언제 NoSQL

### SQL을 선택하는 경우

- **데이터 정합성이 핵심**: 금융, 결제, 재고, ERP
- **복잡한 쿼리/집계가 필요**: 리포팅, 분석, 다중 테이블 JOIN
- **데이터 구조가 명확하고 안정적**: 스키마 변경이 드문 경우
- **트랜잭션이 중요**: 여러 테이블에 걸친 원자적 작업
- **팀이 SQL에 익숙**: 생태계, 도구, 인력이 풍부

### NoSQL을 선택하는 경우

- **대규모 수평 확장 필요**: 수억~수십억 행, 수천 TPS 이상의 쓰기
- **스키마가 자주 변경**: 스타트업 초기, 빠른 이터레이션
- **비정규화된 데이터 모델이 자연스러움**: 문서 하나로 완결되는 데이터
- **특정 접근 패턴에 최적화**: Key 기반 조회, 시계열, 그래프 탐색
- **가용성 > 일관성**: 잠깐의 데이터 불일치를 허용할 수 있는 경우

### 실무에서의 현실

대부분의 시스템은 **SQL과 NoSQL을 함께** 사용한다 (Polyglot Persistence).

```
[사용자 서비스]    → PostgreSQL (프로필, 인증 — 정합성 중요)
[상품 카탈로그]    → MongoDB (다양한 상품 속성 — 유연한 스키마)
[세션/캐시]       → Redis (빠른 조회 — Key-Value)
[활동 로그]       → Cassandra (대량 쓰기 — Wide-Column)
[추천 시스템]     → Neo4j (관계 탐색 — Graph)
[검색]           → Elasticsearch (전문 검색 — Document)
```

**시스템 설계에서의 의미**: "이 데이터의 특성이 뭔가?"를 먼저 파악하고, 그에 맞는 DB를 선택하는 것이 핵심이다. 하나의 DB로 모든 것을 해결하려는 것이 오히려 잘못된 설계다.

## 깊이 비교: 확장성

### SQL의 확장

```
읽기 확장: Primary-Replica 레플리케이션 → 비교적 쉬움
쓰기 확장: 샤딩 → 매우 어려움 (JOIN, FK, 트랜잭션 문제)
```

샤딩하면 [[Replication & Sharding]]에서 다룬 Cross-Shard JOIN, 분산 트랜잭션 문제가 모두 발생한다. Vitess(YouTube가 MySQL 샤딩을 위해 개발)나 Citus(PostgreSQL 샤딩 확장) 같은 미들웨어가 필요하다.

### NoSQL의 확장

```
읽기 확장: 레플리케이션 → 쉬움
쓰기 확장: 샤딩 내장 → 비교적 쉬움 (JOIN이 없으므로)
```

NoSQL은 처음부터 샤딩을 고려하고 설계되었다. Cassandra는 Consistent Hashing으로 자동 분산, MongoDB는 Config Server로 샤드를 관리한다. JOIN이 없고 비정규화를 전제로 하기 때문에 Cross-Shard 문제가 적다.

## 깊이 비교: 인덱스 구조

|SQL (대부분 B+Tree)|NoSQL|
|---|---|
|범위 쿼리에 강함|DB마다 다름|
|읽기/쓰기 균형|Key-Value: 해시 인덱스 (O(1) 조회)|
||Wide-Column: LSM Tree (쓰기 최적화)|
||Document: B-Tree + 추가 인덱스|

[[Index (B-Tree)]]에서 다룬 B-Tree vs LSM Tree의 차이가 바로 SQL vs NoSQL(Wide-Column) 선택의 기술적 근거 중 하나다.

## NewSQL: SQL과 NoSQL의 장점을 합치려는 시도

전통적 SQL의 ACID + NoSQL의 수평 확장을 모두 제공하려는 DB들이 등장했다.

- **대표 DB**: Google Spanner, CockroachDB, TiDB, YugabyteDB
- **특징**: 분산 환경에서도 ACID 트랜잭션 지원, 자동 샤딩, SQL 인터페이스
- **트레이드오프**: 성숙도가 낮고, 운영 복잡도가 높을 수 있으며, 지연 시간이 전통 SQL보다 높을 수 있음

**시스템 설계에서의 의미**: "SQL의 정합성도 필요하고 대규모 확장도 필요하다"는 요구사항에서 NewSQL이 선택지가 될 수 있다. 다만 아직은 특수한 경우에 한정된다.

## 시스템 설계 면접에서의 접근법

DB 선택 질문이 나왔을 때의 사고 프레임워크:

```
1. 데이터 특성 파악
   - 구조가 명확한가? (SQL) vs 유동적인가? (NoSQL)
   - 관계가 중요한가? (SQL/Graph) vs 독립적인가? (NoSQL)

2. 접근 패턴 파악
   - 복잡한 쿼리/집계? (SQL)
   - Key 기반 단순 조회? (Key-Value)
   - 대량 쓰기? (Wide-Column)
   - 관계 탐색? (Graph)

3. 규모와 확장 요구
   - 현재 규모로 단일 서버 충분? (SQL)
   - 대규모 수평 확장 필수? (NoSQL)

4. 일관성 요구 수준
   - 강한 일관성 필수? (SQL)
   - 최종 일관성 허용? (NoSQL)

5. 운영 역량
   - SQL 운영 경험이 풍부? (SQL)
   - 특정 NoSQL 운영 경험? (해당 NoSQL)
```

## 시스템 설계와의 연결 포인트

|개념|시스템 설계에서의 활용|
|---|---|
|SQL의 ACID|금융/결제 도메인 DB 선택|
|NoSQL의 유연한 스키마|빠른 이터레이션, 다양한 데이터 형태|
|Key-Value Store|캐싱, 세션, Rate Limiting|
|Document Store|콘텐츠 관리, 상품 카탈로그|
|Wide-Column|로그, 시계열, IoT|
|Graph DB|소셜 네트워크, 추천|
|Polyglot Persistence|도메인별 최적 DB 조합|
|NewSQL|ACID + 수평 확장이 모두 필요한 경우|

## 핵심 요약

> SQL은 고정 스키마, ACID 트랜잭션, 강력한 쿼리 언어로 데이터 정합성이 중요한 도메인에 적합하고, NoSQL은 유연한 스키마, 수평 확장, 특화된 데이터 모델로 대규모 분산 환경에 적합하다. 둘 중 하나가 우월한 것이 아니라, 데이터 특성과 접근 패턴에 따라 선택이 달라지며, 실무에서는 여러 DB를 조합하여 사용하는 Polyglot Persistence가 일반적이다.
