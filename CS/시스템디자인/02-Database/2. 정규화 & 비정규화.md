**정규화(Normalization)** 데이터 중복을 제거하기 위해 테이블을 쪼개는 것이고, 
**비정규화(Denormalization)** 읽기 성능을 위해 의도적으로 중복을 허용하는 것이다.

---

## 왜 알아야 하는가

시스템 설계에서 DB 스키마를 어떻게 잡느냐에 따라 읽기/쓰기 성능, 데이터 정합성, 확장 전략이 모두 달라진다. 
정규화와 비정규화는 **데이터 정합성 vs 읽기 성능** 
사이의 트레이드오프 이며, 이 판단을 내리지 못하면 설계가 무너진다.

---

## 정규화 (Normalization)

### 핵심 목표
- 데이터 중복 제거
- 데이터 무결성(정합성) 보장
- 이상 현상(Anomaly) 방지

### 이상 현상이란?

정규화하지 않은 테이블에서 발생하는 문제들이다.

**예시: 정규화되지 않은 주문 테이블**

|order_id|customer_name|customer_email|product|price|
|---|---|---|---|---|
|1|홍길동|hong@mail.com|노트북|1500000|
|2|홍길동|hong@mail.com|마우스|30000|
|3|김영희|kim@mail.com|키보드|80000|

**삽입 이상**: 고객 정보만 등록하고 싶은데 주문 없이는 불가능 
**수정 이상**: 홍길동의 이메일이 바뀌면 2개 행 모두 수정해야 함. 하나만 수정하면 데이터 불일치 **삭제 이상**: 김영희의 주문을 삭제하면 고객 정보도 함께 사라짐

### 정규화 단계

#### 제1정규형 (1NF)

**규칙**: 모든 컬럼의 값이 원자값(하나의 값)이어야 한다.

```mysql
❌ 위반
| id | name   | phone                |
|----|--------|----------------------|
| 1  | 홍길동  | 010-1111, 010-2222   |  ← 하나의 셀에 여러 값

✅ 1NF 적용
| id | name   | phone      |
|----|--------|------------|
| 1  | 홍길동  | 010-1111   |
| 1  | 홍길동  | 010-2222   |
```

#### 제2정규형 (2NF)

**규칙**: 1NF + 부분 함수 종속 제거. 기본키의 일부에만 의존하는 컬럼을 분리한다.

```mysql

❌ 위반 (복합키: student_id + course_id)
| student_id | course_id | student_name | grade |
|------------|-----------|--------------|-------|
student_name은 student_id에만 의존 → 부분 종속

✅ 2NF 적용 → 테이블 분리
[students] student_id, student_name
[grades]  student_id, course_id, grade
```

#### 제3정규형 (3NF)

**규칙**: 2NF + 이행적 함수 종속 제거. A → B → C 관계에서 A → C 직접 종속을 제거한다.

``` mysql
❌ 위반
| employee_id | department_id | department_name |
|-------------|---------------|-----------------|
employee_id → department_id → department_name (이행적 종속)

✅ 3NF 적용 → 테이블 분리
[employees]   employee_id, department_id
[departments] department_id, department_name
```

### 실무에서는 어디까지?

대부분의 서비스는 **3NF까지만** 적용한다. BCNF, 4NF, 5NF도 이론적으로 존재하지만 실무에서 그 이상으로 가는 경우는 드물다. 3NF면 대부분의 이상 현상이 해결된다.

## 비정규화 (Denormalization)

### 왜 필요한가

정규화된 테이블은 데이터를 가져올 때 **JOIN이 많아진다**.

```sql
-- 정규화된 구조에서 주문 내역 조회
SELECT o.order_id, c.name, c.email, p.product_name, p.price
FROM orders o
JOIN customers c ON o.customer_id = c.id
JOIN products p ON o.product_id = p.id
JOIN shipping s ON o.shipping_id = s.id;
```

테이블이 작을 때는 문제없지만, 각 테이블이 수백만~수천만 행이 되면 JOIN 비용이 급격히 증가한다. 특히 **샤딩된 환경에서는 서로 다른 서버에 있는 테이블을 JOIN하는 것 자체가 불가능하거나 매우 비효율적**이다.

### 비정규화 기법

#### 1. 중복 컬럼 추가

자주 함께 조회되는 데이터를 같은 테이블에 중복 저장한다.
```
정규화:
[orders] order_id, customer_id, product_id
[customers] customer_id, customer_name

비정규화:
[orders] order_id, customer_id, customer_name, product_id
                                ↑ 중복 저장
```
JOIN 없이 orders 테이블만 조회하면 된다.

#### 2. 파생 컬럼 추가

매번 계산하는 대신 결과를 미리 저장한다.
```sql
-- 정규화: 매 조회마다 계산
SELECT customer_id, COUNT(*) as order_count FROM orders GROUP BY customer_id;

-- 비정규화: customers 테이블에 order_count 컬럼 추가
[customers] customer_id, customer_name, order_count
```

#### 3. 테이블 병합

자주 함께 조회되는 1:1 관계 테이블을 하나로 합친다.
```
정규화:
[users] user_id, name, email
[profiles] user_id, bio, avatar_url

비정규화:
[users] user_id, name, email, bio, avatar_url
```

#### 4. 요약 테이블 (Summary Table)

복잡한 집계 쿼리의 결과를 별도 테이블에 미리 저장한다.
```sql
-- 매일 밤 배치로 집계
[daily_sales_summary]
| date       | total_orders | total_revenue | avg_order_value |
|------------|-------------|---------------|-----------------|
| 2025-02-12 | 15000       | 450000000     | 30000           |
```

**시스템 설계에서의 의미**: 대시보드나 분석 페이지에서 실시간으로 수천만 행을 집계하는 대신, 미리 계산된 요약 테이블을 조회하면 응답 시간이 극적으로 줄어든다.

---

## 정규화 vs 비정규화 트레이드오프

|항목|정규화|비정규화|
|---|---|---|
|데이터 중복|없음|있음 (의도적)|
|데이터 정합성|높음 (한 곳만 수정)|낮음 (여러 곳 동시 수정 필요)|
|읽기 성능|JOIN 필요 → 느릴 수 있음|JOIN 불필요 → 빠름|
|쓰기 성능|빠름 (한 곳만 쓰기)|느림 (여러 곳에 쓰기)|
|저장 공간|효율적|중복으로 더 많이 사용|
|스케일 아웃|JOIN이 샤딩을 어렵게 만듦|샤딩 친화적|

## 시스템 설계에서의 판단 기준

### 정규화가 적합한 경우

- 데이터 정합성이 핵심인 서비스 (금융, 결제, 재고 관리)
- 쓰기가 읽기보다 많거나 비슷한 워크로드
- 데이터 규모가 크지 않아 JOIN 비용이 문제되지 않는 경우

### 비정규화가 적합한 경우

- 읽기가 압도적으로 많은 서비스 (SNS 피드, 뉴스, 상품 목록)
- 응답 시간이 매우 중요한 경우 (실시간 대시보드)
- 샤딩이 필요한 대규모 시스템 (JOIN을 피해야 함)
- 데이터의 약간의 불일치를 허용할 수 있는 경우

### 실무에서의 접근

대부분의 시스템은 **정규화로 시작하고, 병목이 생기는 지점만 선택적으로 비정규화**한다. 처음부터 비정규화하면 데이터 정합성 관리가 어려워진다.

```
1단계: 3NF로 설계 → 깨끗한 데이터 구조
2단계: 서비스 운영하면서 느린 쿼리 식별
3단계: 해당 쿼리에 인덱스 최적화 시도
4단계: 인덱스로 해결 안 되면 해당 부분만 비정규화
5단계: 캐시(Redis 등)로 보완
```

---

## 비정규화와 정합성 유지 전략

비정규화하면 같은 데이터가 여러 곳에 존재하므로, 동기화가 필요하다.

### 애플리케이션 레벨

데이터 변경 시 관련된 모든 테이블을 함께 업데이트한다. 코드가 복잡해지고, 실수하면 불일치가 발생한다.

### 트리거 (DB Trigger)

DB 레벨에서 자동으로 중복 데이터를 갱신한다. 로직이 DB에 숨어있어 관리가 어려울 수 있다.

### 이벤트 기반 비동기 갱신

데이터 변경 시 이벤트를 발행하고, 소비자가 중복 데이터를 갱신한다. 약간의 지연(최종 일관성)이 생기지만, 시스템 결합도가 낮다.

```
[주문 서비스] → 이벤트: "고객 이름 변경" → [메시지 큐] → [소비자: orders 테이블 갱신]
```

**시스템 설계에서의 의미**: 이 패턴은 나중에 [[Transaction & ACID]]의 일관성 개념, [[Cache Strategy]]의 캐시 무효화, 그리고 분산 시스템의 최종 일관성과 직접 연결된다.

## NoSQL과의 관계

NoSQL DB는 기본적으로 **비정규화된 구조를 전제**로 설계되었다.

```json
// MongoDB 문서 예시 — 비정규화된 구조
{
  "order_id": 1,
  "customer": {
    "name": "홍길동",
    "email": "hong@mail.com"
  },
  "products": [
    {"name": "노트북", "price": 1500000},
    {"name": "마우스", "price": 30000}
  ]
}
```

하나의 문서 안에 관련 데이터를 모두 내장(embed)하므로 JOIN이 필요 없다. 이것이 NoSQL이 수평 확장(샤딩)에 유리한 이유 중 하나다. 자세한 비교는 [[SQL vs NoSQL]]에서 다룬다.

## 시스템 설계와의 연결 포인트

|개념|시스템 설계에서의 활용|
|---|---|
|정규화|데이터 정합성이 중요한 핵심 도메인|
|비정규화|읽기 성능 최적화, 샤딩 친화적 설계|
|JOIN 비용|샤딩 환경에서 JOIN 회피 → 비정규화 또는 NoSQL|
|요약 테이블|대시보드, 분석 쿼리 최적화|
|정합성 유지|이벤트 기반 비동기 갱신 → 최종 일관성|
|정규화 → 비정규화 순서|실무 설계 접근법|

## 핵심 요약

> 정규화는 중복을 제거하여 데이터 정합성을 보장하고, 비정규화는 중복을 허용하여 읽기 성능을 얻는다. 실무에서는 정규화로 시작하고 병목 지점만 선택적으로 비정규화하며, 대규모 시스템에서는 샤딩과의 호환성 때문에 비정규화가 필수적으로 요구된다. 이 둘의 트레이드오프를 이해하는 것이 DB 스키마 설계의 핵심이다.
