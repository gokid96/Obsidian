
**클라이언트(요청하는 쪽)**와 **서버(응답하는 쪽)**가 네트워크를 통해 역할을 나누어 통신하는 구조다.

---

## 왜 알아야 하는가

시스템 설계의 모든 아키텍처는 클라이언트-서버 구조의 확장이다. 단일 서버에서 시작해서 로드밸런서, 캐시, 메시지 큐, 마이크로서비스로 발전하는 과정을 이해하려면 가장 기본이 되는 이 구조부터 잡아야 한다.

---

## 기본 구조

```
[클라이언트]                    [서버]
 브라우저, 앱,     ── 요청 ──>   웹 서버, API 서버
 다른 서버 등      <── 응답 ──   DB 접근, 비즈니스 로직 처리
```

핵심은 **역할 분리**다. 클라이언트는 사용자 인터페이스와 요청 전송을 담당하고, 서버는 데이터 저장·처리·비즈니스 로직을 담당한다.

---

## 클라이언트의 종류

클라이언트는 브라우저만이 아니다.

- **브라우저**: 가장 일반적인 클라이언트. HTML/CSS/JS를 렌더링
- **모바일 앱**: iOS, Android 앱이 API 서버와 통신
- **데스크톱 앱**: Slack, VS Code 등
- **다른 서버**: 서버 A가 서버 B에게 요청하면, A는 B의 클라이언트다
- **IoT 디바이스**: 센서, 스마트 기기 등

**시스템 설계에서의 의미**: 클라이언트 종류에 따라 API 설계가 달라진다. 브라우저는 CORS 제약이 있고, 모바일은 네트워크가 불안정할 수 있으며, 서버 간 통신은 내부 네트워크에서 이루어지므로 보안 정책이 다르다.

---

## 단일 서버에서 시작하기

시스템 설계 문제는 보통 가장 단순한 구조에서 시작해서 점진적으로 확장한다.

### Stage 1: 모든 것이 한 서버

```
[클라이언트] → [서버 1대: 웹 서버 + 앱 로직 + DB]
```

소규모 서비스는 이것으로 충분하다. 하지만 트래픽이 늘어나면 한계에 부딪힌다.

**병목 지점**: CPU, 메모리, 디스크 I/O, 네트워크 대역폭 중 하나가 먼저 한계에 도달한다. 여기서 **스케일 업**(서버 사양 향상)을 할지 **스케일 아웃**(서버 추가)을 할지 결정해야 한다.

### Stage 2: 웹 서버와 DB 분리

```
[클라이언트] → [웹/앱 서버] → [DB 서버]
```

가장 먼저 하는 분리다. 이유:

- 웹 서버와 DB는 리소스 사용 패턴이 다르다 (웹: CPU/메모리, DB: 디스크 I/O)
- 각각 독립적으로 스케일링할 수 있다
- DB 서버가 죽어도 웹 서버는 캐시된 데이터로 일부 응답 가능

### Stage 3: 로드밸런서 + 다중 서버

```
                    ┌→ [웹 서버 1] ─→
[클라이언트] → [LB] ├→ [웹 서버 2] ─→ [DB]
                    └→ [웹 서버 3] ─→
```

트래픽이 더 늘어나면 웹 서버를 여러 대로 스케일 아웃하고, 앞에 로드밸런서(LB)를 둔다. 이것이 가능한 전제 조건이 [[HTTP]]의 **Stateless** 특성이다.

### Stage 4: 캐시, CDN, 메시지 큐 추가

```
[클라이언트] → [CDN] (정적 파일)
		            → [LB] → [웹 서버들] → [캐시(Redis)] → [DB]
		                                → [메시지 큐] → [워커 서버들]
```

이 단계부터 본격적인 시스템 설계 영역이다. 각 컴포넌트를 왜 추가하는지, 어떤 문제를 해결하는지를 아는 것이 핵심이다.

## Thin Client vs Thick Client

### Thin Client (씬 클라이언트)

클라이언트는 화면 렌더링만 하고, 모든 로직은 서버에서 처리한다.
- 예: 전통적인 서버 사이드 렌더링(SSR), 터미널 기반 앱
- 장점: 클라이언트 업데이트 없이 서버만 배포하면 됨
- 단점: 서버 부하 집중, 네트워크 의존도 높음

### Thick Client (씩 클라이언트)

클라이언트가 상당한 로직을 직접 처리한다.
- 예: React/Vue SPA, 네이티브 모바일 앱
- 장점: 서버 부하 분산, 오프라인 일부 동작 가능, 반응성 좋음
- 단점: 클라이언트 업데이트 배포 복잡 (특히 모바일)

**시스템 설계에서의 의미**: 어디에 로직을 두느냐에 따라 서버 비용, 확장 전략, 캐싱 전략이 달라진다. SPA는 정적 파일을 CDN에서 서빙하고 API만 서버에서 처리하므로 서버 부하가 줄어든다.

## 서버 간 통신 패턴

시스템이 커지면 서버들 사이에서도 클라이언트-서버 관계가 생긴다.

### 동기 통신 (Synchronous)
```
[서비스 A] --요청--> [서비스 B]
[서비스 A] <--응답-- [서비스 B]
```

A가 B의 응답을 기다린다. HTTP/REST, gRPC가 대표적이다.
- 장점: 단순하고 직관적
- 단점: B가 느리면 A도 느려진다. B가 죽으면 A도 영향 받는다 (강한 결합)

### 비동기 통신 (Asynchronous)

```
[서비스 A] --메시지--> [메시지 큐] --메시지--> [서비스 B]
```

A는 메시지를 큐에 넣고 바로 다른 일을 한다. B는 자기 속도로 메시지를 소비한다.

- 장점: 서비스 간 결합도가 낮다. B가 잠시 죽어도 큐에 메시지가 쌓여있으므로 복구 후 처리 가능
- 단점: 즉각적인 응답이 필요한 경우에는 부적합. 디버깅이 복잡

**시스템 설계에서의 의미**: "이 통신은 동기여야 하는가, 비동기여야 하는가?"는 시스템 설계에서 자주 나오는 트레이드오프 질문이다. 결제 처리는 동기(즉시 결과 필요), 이메일 발송은 비동기(지연 허용)가 적합하다.

## Peer-to-Peer (P2P)와의 비교

클라이언트-서버와 대비되는 모델이 P2P다.

```
클라이언트-서버:  [클라이언트들] ──→ [중앙 서버]
P2P:           [노드] ←→ [노드] ←→ [노드]  (모두가 클라이언트이자 서버)
```

- P2P 예시: BitTorrent, 블록체인, WebRTC 영상통화
- 장점: 중앙 서버 없이 확장 가능, 단일 장애점(SPOF) 없음
- 단점: 일관성 유지 어려움, 보안 복잡

대부분의 웹 서비스는 클라이언트-서버 모델을 기반으로 설계한다. P2P는 특수한 요구사항에서만 사용된다.

## 주요 설계 고려 사항

### 단일 장애점 (SPOF: Single Point of Failure)

시스템에서 하나가 죽으면 전체가 멈추는 지점이다.

```
[클라이언트] → [서버 1대] → [DB 1대]
                 ↑ SPOF       ↑ SPOF
```

해결 방법: 각 계층을 **이중화(Redundancy)**한다. 서버는 로드밸런서 뒤에 여러 대, DB는 레플리케이션, 로드밸런서 자체도 이중화.

### Stateless 설계의 중요성

서버가 상태를 갖지 않아야 스케일 아웃이 자유롭다.

```
❌ Stateful: 세션 데이터가 서버 메모리에 있으면
   → 사용자가 항상 같은 서버로 가야 함 (Sticky Session)
   → 해당 서버가 죽으면 세션 유실

✅ Stateless: 세션 데이터를 외부 저장소(Redis 등)에 두면
   → 어떤 서버가 요청을 받아도 동일하게 처리
   → 서버 추가/제거가 자유로움
```

### 수평 확장 vs 수직 확장

|구분|수직 확장 (Scale Up)|수평 확장 (Scale Out)|
|---|---|---|
|방법|더 좋은 하드웨어로 교체|서버 대수 추가|
|한계|물리적 한계 존재|이론상 무한 확장|
|복잡도|낮음 (코드 변경 없음)|높음 (분산 시스템 고려)|
|장애 대응|SPOF 위험|일부 서버 장애 시 나머지가 처리|
|비용|고사양 서버는 기하급수적으로 비쌈|저사양 다수가 비용 효율적|

## 시스템 설계와의 연결 포인트

|개념|시스템 설계에서의 활용|
|---|---|
|역할 분리 (클라이언트/서버)|마이크로서비스 아키텍처의 기본 원리|
|서버-DB 분리|독립적 스케일링의 출발점|
|Stateless 서버|스케일 아웃의 전제 조건|
|SPOF 제거|고가용성(HA) 설계의 핵심|
|동기 vs 비동기 통신|서비스 간 결합도와 성능 트레이드오프|
|Thin vs Thick Client|CDN 활용, 서버 부하 분산 전략|
|단계적 확장|시스템 설계 면접의 전형적 접근법|
