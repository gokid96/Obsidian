인터넷에서 데이터가 출발지에서 목적지까지 **어떻게 쪼개지고, 어떤 경로로, 어떤 규칙으로 전달되는지**를 정의하는 프로토콜 체계다.

---

## 왜 알아야 하는가

HTTP, DNS, 데이터베이스 통신, 메시지 큐 — 이 모든 것이 TCP/IP 위에서 동작한다. 시스템 설계에서 "지연 시간이 왜 높은지", "연결이 왜 끊기는지", "UDP를 쓸지 TCP를 쓸지" 같은 판단은 TCP/IP의 동작 원리를 알아야 가능하다.

---

## TCP/IP 4계층 모델

OSI 7계층이 이론적 모델이라면, TCP/IP 4계층은 **실제 인터넷이 동작하는 모델**이다.

```
[4] 애플리케이션 계층  → HTTP, DNS, FTP, SMTP
[3] 전송 계층          → TCP, UDP
[2] 인터넷 계층        → IP, ICMP
[1] 네트워크 접근 계층  → Ethernet, Wi-Fi
```

**데이터가 내려갈 때**: 각 계층에서 헤더를 붙인다 (캡슐화) 
**데이터가 올라갈 때**: 각 계층에서 헤더를 벗긴다 (역캡슐화)
```
[HTTP 요청 데이터]
→ [TCP 헤더 | HTTP 데이터]           ← 세그먼트
→ [IP 헤더 | TCP 헤더 | HTTP 데이터]  ← 패킷
→ [Ethernet 헤더 | IP | TCP | HTTP | Ethernet 트레일러]  ← 프레임
```

## IP (Internet Protocol)

### 역할
출발지에서 목적지까지 패킷을 **라우팅(경로 설정)**하는 것이 IP의 역할이다.

### 핵심 특성

- **비연결형**: 패킷마다 독립적으로 라우팅된다. 같은 요청의 패킷이라도 서로 다른 경로로 갈 수 있다.
- **비신뢰성**: 패킷이 도착하는지, 순서가 맞는지 보장하지 않는다. 그건 TCP의 역할이다.

### IP 주소

- **IPv4**: 32비트, `192.168.1.1` 형태. 약 43억 개로 부족해지고 있다.
- **IPv6**: 128비트, `2001:0db8:85a3::8a2e:0370:7334` 형태. 사실상 무한.

**시스템 설계에서의 의미**: 서버가 늘어나면 IP 관리가 복잡해진다. 사설 IP(10.x.x.x, 172.16.x.x, 192.168.x.x)와 공인 IP를 구분하고, NAT(Network Address Translation)로 사설 네트워크 뒤의 서버들이 외부와 통신한다. VPC(Virtual Private Cloud) 설계 시 서브넷과 IP 대역을 나누는 것이 여기에 해당한다.

## TCP (Transmission Control Protocol)

### 역할

IP 위에서 **신뢰성 있는 데이터 전송**을 보장한다.

### TCP의 3가지 보장

1. **데이터 도착 보장**: 패킷이 유실되면 재전송한다
2. **순서 보장**: 패킷에 시퀀스 번호를 붙여서 도착 순서가 뒤바뀌어도 올바른 순서로 재조립한다
3. **무결성 보장**: 체크섬으로 데이터가 변조되지 않았는지 확인한다

### 3-Way Handshake (연결 수립)

TCP는 데이터를 보내기 전에 먼저 연결을 수립한다.
```
[클라이언트]              [서버]
    --- SYN ---------->          1. "연결하고 싶어"
    <-- SYN + ACK -----          2. "알겠어, 나도 준비됐어"
    --- ACK ---------->          3. "확인, 시작하자"
```

이 과정이 끝나야 실제 데이터 전송이 시작된다. 즉, **최소 1.5 RTT(Round Trip Time)**가 연결 수립에만 소요된다.

**시스템 설계에서의 의미**: 매 요청마다 연결을 새로 맺으면 Handshake 오버헤드가 크다. 그래서 HTTP/1.1의 Keep-Alive(연결 재사용), HTTP/2의 멀티플렉싱, 그리고 데이터베이스의 **커넥션 풀링**이 존재한다.

### 4-Way Handshake (연결 종료)

```
[클라이언트]              [서버]
    --- FIN ---------->          1. "나 보낼 거 다 보냈어"
    <-- ACK -----------          2. "알겠어"
    <-- FIN -----------          3. "나도 다 보냈어"
    --- ACK ---------->          4. "확인, 종료"
```

종료도 비용이 든다. 그래서 커넥션 풀링으로 연결을 재사용하는 것이 성능에 유리하다.

### 흐름 제어 (Flow Control)

수신자가 처리할 수 있는 속도보다 빠르게 데이터를 보내면 패킷이 유실된다. TCP는 **슬라이딩 윈도우** 방식으로 수신자의 처리 능력에 맞춰 전송 속도를 조절한다.

**시스템 설계에서의 의미**: 이 개념은 나중에 메시지 큐의 **백프레셔(backpressure)** 개념과 동일한 원리다. 소비자가 느리면 생산자가 속도를 줄여야 시스템이 안정된다.

### 혼잡 제어 (Congestion Control)

네트워크 전체가 혼잡할 때 전송 속도를 줄이는 메커니즘이다. Slow Start로 시작해서 점진적으로 속도를 올리고, 패킷 유실이 감지되면 속도를 급격히 줄인다.

**시스템 설계에서의 의미**: 서비스 초기 접속 시 TCP가 Slow Start 상태이므로 처음 몇 개의 요청은 느릴 수 있다. CDN이 사용자와 가까운 곳에 서버를 두는 이유 중 하나가 이미 Warm-up된 TCP 연결을 활용하기 위해서다.

## UDP (User Datagram Protocol)

### TCP와의 비교

|항목|TCP|UDP|
|---|---|---|
|연결 수립|3-Way Handshake 필요|연결 없음, 바로 전송|
|신뢰성|도착 보장, 순서 보장, 재전송|보장 없음|
|속도|상대적으로 느림 (오버헤드)|빠름 (가벼움)|
|용도|HTTP, DB 통신, 파일 전송|DNS 조회, 실시간 스트리밍, 게임, VoIP|

### UDP를 쓰는 이유
 신뢰성보다 **속도와 실시간성**이 중요할 때 UDP를 쓴다. 영상 통화에서 1초 전 프레임을 재전송받는 것보다 최신 프레임을 바로 보여주는 게 낫다.

**시스템 설계에서의 의미**
- DNS 조회는 UDP를 사용한다 (작은 데이터, 빠른 응답 필요)
- HTTP/3의 QUIC 프로토콜은 UDP 위에 신뢰성을 자체 구현하여 TCP의 장점 + UDP의 속도를 결합했다
- 실시간 채팅, 라이브 스트리밍 시스템을 설계할 때 TCP vs UDP 선택이 트레이드오프 포인트가 된다

## 포트 (Port)

IP 주소가 "어떤 컴퓨터인지"를 식별한다면, 포트는 **"그 컴퓨터의 어떤 프로세스인지"**를 식별한다.
```
192.168.1.1:80   → 웹 서버 (HTTP)
192.168.1.1:443  → 웹 서버 (HTTPS)
192.168.1.1:3306 → MySQL
192.168.1.1:6379 → Redis
```

**잘 알려진 포트**: 80(HTTP), 443(HTTPS), 22(SSH), 53(DNS), 3306(MySQL), 5432(PostgreSQL), 6379(Redis), 27017(MongoDB)

**시스템 설계에서의 의미**: 방화벽과 보안 그룹 설정에서 어떤 포트를 열고 닫을지가 보안 아키텍처의 기본이다. 예를 들어 DB 포트(3306)는 외부에 절대 열지 않고, 내부 네트워크에서만 접근 가능하게 한다.

## 커넥션 풀링 (Connection Pooling)

TCP 연결 수립/종료 비용이 크기 때문에, 미리 여러 개의 연결을 만들어두고 재사용하는 패턴이다.

```
[애플리케이션 서버]
    ├── 연결 1 ──→ [DB]
    ├── 연결 2 ──→ [DB]     ← 미리 만들어둔 연결 풀
    ├── 연결 3 ──→ [DB]
    └── 연결 4 ──→ [DB]

요청이 오면 풀에서 연결을 빌려 쓰고, 끝나면 반환한다.
```

**시스템 설계에서의 의미**: 서버를 스케일 아웃하면 각 서버마다 커넥션 풀을 갖게 되므로, DB 입장에서는 연결 수가 급증한다. 서버 10대 × 풀 크기 50 = 500개 연결. 이 문제를 해결하기 위해 **PgBouncer** 같은 커넥션 프록시를 두기도 한다.

## 시스템 설계와의 연결 포인트

|TCP/IP 개념|시스템 설계에서의 활용|
|---|---|
|3-Way Handshake|커넥션 풀링, Keep-Alive의 필요성|
|TCP 신뢰성|DB 통신, API 호출 등 데이터 정합성이 중요한 곳|
|UDP 경량성|DNS, 실시간 스트리밍, HTTP/3(QUIC)|
|흐름 제어|백프레셔, 메시지 큐 소비 속도 조절|
|혼잡 제어 / Slow Start|CDN 필요성, 초기 응답 지연 이해|
|포트|방화벽/보안 그룹 설계|
|커넥션 풀링|스케일 아웃 시 DB 연결 관리|
|IP 주소 / 서브넷|VPC 설계, 네트워크 격리|

## 핵심 요약

> TCP/IP는 인터넷 통신의 기반이다. TCP는 신뢰성(도착·순서·무결성 보장)을 제공하지만 연결 수립 비용이 크고, UDP는 신뢰성을 포기하는 대신 속도를 얻는다. 이 트레이드오프를 이해해야 커넥션 풀링, CDN 배치, 프로토콜 선택(TCP vs UDP vs QUIC), 스케일 아웃 시 연결 관리 같은 시스템 설계 판단을 내릴 수 있다.
