클라이언트(브라우저)와 서버가 데이터를 주고받기 위한 **요청-응답 기반의 통신 규약(프로토콜)**이다.

---

## 왜 알아야 하는가

시스템 설계에서 모든 통신의 출발점이 HTTP다. 로드밸런서가 어떤 요청을 어디로 보낼지, 캐시를 언제 적용할지, API를 어떻게 설계할지 — 이 모든 판단의 기반이 HTTP 동작 원리에 있다.

---

## 핵심 개념

### 1. 요청-응답 모델 (Request-Response)

HTTP는 항상 **클라이언트가 먼저 요청**하고, **서버가 응답**하는 구조다. 서버가 먼저 클라이언트에게 데이터를 보내는 것은 기본 HTTP로는 불가능하다.

```
[클라이언트] --요청(Request)--> [서버]
[클라이언트] <--응답(Response)-- [서버]
```

### 2. Stateless (무상태)

HTTP는 각 요청이 독립적이다. 서버는 이전 요청을 기억하지 않는다. 즉, 요청 A를 보낸 후 요청 B를 보내도 서버 입장에서 둘은 아무 관계가 없다.

**시스템 설계에서의 의미**: Stateless이기 때문에 서버를 여러 대로 **스케일 아웃**할 수 있다. 어떤 서버가 요청을 받아도 결과가 동일하기 때문이다. 만약 Stateful이라면 같은 사용자의 요청이 항상 같은 서버로 가야 하므로 확장이 어려워진다.

**그렇다면 로그인 상태는?**: HTTP 자체는 무상태이므로, 상태 유지가 필요하면 **쿠키, 세션, JWT** 같은 별도 메커니즘을 사용한다.

### 3. HTTP 메서드

| 메서드    | 목적        | 특징                 |
| ------ | --------- | ------------------ |
| GET    | 데이터 조회    | 본문(body) 없음, 캐싱 가능 |
| POST   | 데이터 생성    | 본문에 데이터 포함         |
| PUT    | 데이터 전체 수정 | 해당 리소스를 완전히 대체     |
| PATCH  | 데이터 부분 수정 | 변경할 필드만 전송         |
| DELETE | 데이터 삭제    |                    |

**멱등성(Idempotency)**: GET, PUT, DELETE는 멱등하다 — 같은 요청을 여러 번 보내도 결과가 동일하다. POST는 멱등하지 않다 — 같은 요청을 보낼 때마다 새로운 리소스가 생성될 수 있다. 시스템 설계에서 재시도(retry) 전략을 짤 때 멱등성 여부가 중요하다.

### 4. HTTP 상태 코드

외울 필요 없이 **범위별 의미**만 알면 된다.

- **2xx — 성공**: 200 OK, 201 Created, 204 No Content
- **3xx — 리다이렉션**: 301 영구 이동, 302 임시 이동, 304 Not Modified(캐시 사용)
- **4xx — 클라이언트 에러**: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests(Rate Limiting)
- **5xx — 서버 에러**: 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

**시스템 설계에서의 의미**: 429는 Rate Limiting이 동작했다는 의미이고, 502/503은 로드밸런서 뒤의 서버에 문제가 있을 때 자주 보인다. 장애 대응 시 상태 코드를 기준으로 서킷 브레이커를 동작시키기도 한다.

### 5. HTTP 헤더

요청과 응답에 메타데이터를 담는 영역이다. 시스템 설계에서 자주 등장하는 헤더들:

- `Content-Type`: 데이터 형식 (application/json, text/html 등)
- `Authorization`: 인증 토큰 (Bearer token 등)
- `Cache-Control`: 캐싱 정책 (max-age, no-cache, no-store)
- `ETag / If-None-Match`: 캐시 유효성 검증 → 304 응답과 연결
- `Host`: 어떤 도메인으로 요청했는지 (리버스 프록시가 이걸 보고 라우팅)

### 6. HTTP 요청의 전체 구조

```
POST /api/users HTTP/1.1          ← 요청 라인 (메서드, 경로, 버전)
Host: example.com                  ← 헤더 시작
Content-Type: application/json
Authorization: Bearer abc123
                                   ← 빈 줄 (헤더와 본문 구분)
{"name": "홍길동", "age": 25}      ← 본문 (Body)
```

## HTTP 버전 변화

### HTTP/1.1
- 하나의 TCP 연결에서 요청을 하나 보내고 응답을 받아야 다음 요청을 보낼 수 있다 (Head-of-Line Blocking)
- Keep-Alive로 연결 재사용은 가능하지만, 동시 처리에 한계가 있다
### HTTP/2
- **멀티플렉싱**: 하나의 TCP 연결에서 여러 요청/응답을 동시에 처리
- **헤더 압축**: 반복되는 헤더를 압축하여 오버헤드 감소
- **서버 푸시**: 클라이언트가 요청하기 전에 서버가 필요한 리소스를 미리 전송 가능
### HTTP/3
- TCP 대신 **QUIC(UDP 기반)** 사용
- TCP의 Head-of-Line Blocking 문제를 프로토콜 수준에서 해결
- 연결 수립이 더 빠름 (0-RTT 가능)

**시스템 설계에서의 의미**: 대규모 트래픽을 처리할 때 HTTP/2 이상을 사용하면 같은 서버 자원으로도 더 많은 동시 요청을 처리할 수 있다. CDN이나 로드밸런서 설정 시 어떤 HTTP 버전을 지원할지가 성능에 영향을 준다.

## HTTPS

HTTP + **TLS(Transport Layer Security)** = HTTPS

데이터를 암호화하여 중간에서 도청하거나 변조할 수 없게 한다. 현재 거의 모든 서비스가 HTTPS를 기본으로 사용한다.

**동작 흐름 (TLS Handshake 간략화)**:

1. 클라이언트가 서버에 연결 요청
2. 서버가 인증서(공개키 포함)를 전달
3. 클라이언트가 인증서를 검증하고, 대칭키를 생성하여 공개키로 암호화해서 전송
4. 이후 양쪽이 대칭키로 데이터를 암호화하여 통신

**시스템 설계에서의 의미**: TLS 종료(termination)를 어디서 할 것인가가 설계 포인트다. 보통 로드밸런서나 리버스 프록시에서 TLS를 처리하고, 내부 서버 간 통신은 HTTP로 하여 성능 부담을 줄인다.

## REST API와 HTTP

REST는 HTTP를 활용한 API 설계 스타일이다. 별도의 프로토콜이 아니라 **HTTP 메서드와 URL을 의미 있게 조합하는 규칙**이다.

```
GET    /users       → 사용자 목록 조회
GET    /users/1     → 사용자 1번 조회
POST   /users       → 사용자 생성
PUT    /users/1     → 사용자 1번 정보 전체 수정
DELETE /users/1     → 사용자 1번 삭제
```

**시스템 설계에서의 의미**: API 게이트웨이는 이 URL 패턴을 보고 어떤 마이크로서비스로 라우팅할지 결정한다. Rate Limiting도 엔드포인트별로 다르게 설정하는 경우가 많다.

## 시스템 설계와의 연결 포인트

| HTTP 개념                     | 시스템 설계에서의 활용               |
| --------------------------- | -------------------------- |
| Stateless                   | 서버 스케일 아웃의 전제 조건           |
| 캐시 헤더 (Cache-Control, ETag) | CDN 캐싱, 브라우저 캐싱 전략         |
| 상태 코드 (429, 5xx)            | Rate Limiting, 서킷 브레이커 트리거 |
| 멱등성                         | 재시도 전략, 메시지 큐 중복 처리        |
| HTTPS / TLS 종료              | 로드밸런서 설계, 보안 아키텍처          |
| HTTP/2 멀티플렉싱                | 동시 처리 성능 최적화               |
| Host 헤더                     | 리버스 프록시 라우팅                |

> HTTP는 무상태 요청-응답 프로토콜이다. 무상태이기 때문에 스케일 아웃이 가능하고, 멱등성과 상태 코드는 장애 대응과 재시도 전략의 기반이 되며, 캐시 헤더는 CDN과 캐싱 계층 설계에 직접 활용된다.
