사람이 읽을 수 있는 도메인 이름(example.com)을 컴퓨터가 이해하는 **IP 주소(93.184.216.34)**로 변환해주는 시스템

---
## 왜 알아야 하는가

HTTP 요청이 서버에 도달하려면 먼저 도메인이 IP로 변환되어야 한다. DNS는 이 과정을 담당하며, 시스템 설계에서는 **로드밸런싱, 장애 대응, CDN 라우팅, 글로벌 트래픽 분산**의 첫 번째 제어 지점으로 활용.

---

## 핵심 개념

### 1. DNS 조회 흐름

브라우저에 `www.example.com`을 입력하면 다음 순서로 IP를 찾는다:

```
1. 브라우저 캐시 확인 → 있으면 바로 사용
2. OS 캐시 확인 (/etc/hosts 포함)
3. Local DNS Resolver (ISP 또는 설정된 DNS 서버, 예: 8.8.8.8)
4. Root Name Server → ".com은 어디서 관리하는지" 알려줌
5. TLD Name Server (.com) → "example.com은 어디서 관리하는지" 알려줌
6. Authoritative Name Server → "example.com의 IP는 93.184.216.34" 최종 응답
```

**핵심 포인트**: 매번 이 전체 과정을 거치지 않는다. 각 단계마다 **캐시**가 존재하며, TTL(Time To Live) 동안은 캐시된 결과를 사용한다.

### 2. DNS 레코드 타입

| 레코드   | 역할                 | 예시                                |
| ----- | ------------------ | --------------------------------- |
| A     | 도메인 → IPv4 주소      | example.com → 93.184.216.34       |
| AAAA  | 도메인 → IPv6 주소      | example.com → 2606:2800:220:1:... |
| CNAME | 도메인 → 다른 도메인 (별칭)  | www.example.com → example.com     |
| NS    | 해당 도메인을 관리하는 네임서버  | example.com → ns1.example.com     |
| MX    | 메일 서버 지정           | example.com → mail.example.com    |
| TXT   | 텍스트 정보 (인증, SPF 등) | 도메인 소유 확인, 이메일 인증                 |

**시스템 설계에서 자주 쓰이는 것**: A 레코드와 CNAME이 핵심이다. 
A 레코드는 로드밸런서의 IP를 가리키고, 
CNAME은 CDN 도메인을 가리키는 데 사용된다.
CNAME은 **“여기 말고 저 공식 주소로 가세요”** 라는 위임 같은 거임.

### 3. TTL (Time To Live)

DNS 응답이 캐시에 유지되는 시간(초 단위)이다.
- **TTL이 길면** (예: 86400초 = 24시간): DNS 조회 횟수가 줄어 성능이 좋지만, IP가 변경되었을 때 전파가 느리다
- **TTL이 짧으면** (예: 60초): IP 변경이 빠르게 반영되지만, DNS 조회 부하가 증가한다

**시스템 설계에서의 의미**: 서버 마이그레이션이나 장애 대응 시 TTL을 미리 낮춰두면 IP 전환이 빠르다. 평소에는 긴 TTL로 성능을 챙기고, 변경 예정 시 사전에 TTL을 줄이는 전략을 쓴다.

## DNS 기반 로드밸런싱

하나의 도메인에 여러 IP를 등록하면 DNS 수준에서 트래픽을 분산할 수 있다.

### Round Robin DNS
```
example.com → 10.0.0.1
example.com → 10.0.0.2
example.com → 10.0.0.3
```
요청마다 다른 IP를 순서대로 반환한다.

**장점**: 단순하고 추가 인프라 불필요 **한계**: 서버의 부하 상태를 모른다. 특정 서버가 죽어도 계속 해당 IP를 반환할 수 있다. 캐시 때문에 실제 분산이 균등하지 않다.

→ 그래서 실무에서는 DNS 로드밸런싱만 단독으로 쓰지 않고, **L4/L7 로드밸런서와 함께** 사용한다.

### 지리 기반 DNS (GeoDNS)

클라이언트의 위치에 따라 가장 가까운 서버의 IP를 반환한다.

```
한국 사용자 → 서울 서버 IP
미국 사용자 → 버지니아 서버 IP
```

**시스템 설계에서의 의미**: 글로벌 서비스에서 지연 시간(latency)을 줄이기 위해 사용한다. CDN도 이 원리로 동작한다. AWS의 Route 53, Cloudflare DNS 등이 이 기능을 제공한다.

---

## DNS와 장애 대응

### DNS Failover

헬스체크를 통해 서버가 죽었는지 감지하고, 죽은 서버의 IP를 DNS 응답에서 제거한다.

```
정상 상태: example.com → 10.0.0.1, 10.0.0.2
장애 발생: example.com → 10.0.0.2 (10.0.0.1 제거)
```

**한계**: TTL 때문에 즉각적인 전환이 불가능하다. 클라이언트가 캐시된 IP를 계속 사용할 수 있으므로, TTL 동안은 장애가 지속될 수 있다. 이것이 DNS 기반 장애 대응의 근본적 한계다.

### DNS 자체의 장애

DNS 서버가 죽으면 도메인 자체가 해석되지 않아 서비스 전체가 중단된다. 그래서:

- Authoritative NS를 **최소 2대 이상** 운영한다
- 서로 다른 네트워크/지역에 분산 배치한다
- 클라우드 DNS 서비스(Route 53, Cloud DNS 등)는 이를 자동으로 처리한다

## DNS 캐싱 계층

```
[브라우저 캐시] → 가장 빠름, TTL 동안 유지
       ↓
[OS 캐시] → /etc/hosts 파일 포함
       ↓
[Local DNS Resolver 캐시] → ISP나 사내 DNS 서버
       ↓
[실제 DNS 조회] → Root → TLD → Authoritative
```

**시스템 설계에서의 의미**: DNS 캐싱은 시스템 전체 캐싱 전략의 첫 번째 레이어다. 나중에 [[Cache Strategy]]를 공부할 때, HTTP 캐시 → CDN 캐시 → 애플리케이션 캐시와 함께 DNS 캐시도 전체 캐싱 체인의 일부로 이해하면 된다.

---

## DNS와 CDN의 관계

CDN을 사용할 때 보통 CNAME 레코드로 연결한다:

```
static.example.com → CNAME → d1234.cloudfront.net
```

사용자가 `static.example.com`에 접속하면:

1. DNS가 CNAME을 따라 CDN 도메인으로 이동
2. CDN의 DNS가 사용자와 가장 가까운 엣지 서버 IP를 반환 (GeoDNS)
3. 사용자는 가까운 엣지 서버에서 콘텐츠를 받음

이 흐름을 이해하면 나중에 시스템 설계에서 "정적 파일은 CDN으로 서빙한다"는 말이 구체적으로 어떤 의미인지 알 수 있다.

## 실무에서 자주 쓰는 DNS 도구

- `nslookup example.com` — 도메인의 IP 확인
- `dig example.com` — 상세한 DNS 조회 결과 (레코드 타입, TTL 등)
- `dig +trace example.com` — Root부터 전체 조회 과정 추적
