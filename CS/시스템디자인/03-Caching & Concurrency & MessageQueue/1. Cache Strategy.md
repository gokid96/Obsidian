
캐시는 **자주 사용되는 데이터를 빠른 저장소에 미리 복사해두고, 원본 저장소에 접근하지 않고 빠르게 응답하는 기법**이다.

---

## 왜 알아야 하는가

시스템 설계에서 "느리다"는 문제의 가장 흔한 해결책이 캐시다. DB 쿼리가 느린 것, API 응답이 느린 것, 같은 연산을 반복하는 것 — 이 모든 병목을 캐시로 완화할 수 있다. 
인덱스 최적화 다음으로 시도하는 성능 개선 수단이며, 스케일 아웃 전에 캐시만으로 해결되는 경우가 많다.

---

## 캐시가 빠른 이유

```
DB 조회 (디스크):       ~1-10ms
Redis 조회 (메모리):    ~0.1-0.5ms
로컬 캐시 (앱 메모리):  ~0.001ms (마이크로초)
```

핵심은 **저장 매체의 속도 차이**다. 디스크보다 메모리가, 네트워크를 타는 것보다 로컬이 빠르다.

---

## 캐싱 계층 (Multi-Layer Caching)

실제 시스템에서는 캐시가 여러 계층에 존재한다.

```
[브라우저 캐시] → 가장 빠름, 사용자 기기에 저장
      ↓
[CDN 캐시] → 사용자와 가까운 엣지 서버
      ↓
[API Gateway / 리버스 프록시 캐시] → Nginx, Varnish
      ↓
[애플리케이션 캐시] → 로컬 메모리 (HashMap 등)
      ↓
[분산 캐시] → Redis, Memcached
      ↓
[DB 쿼리 캐시] → DB 내부 캐시
      ↓
[DB (원본)]
```

요청이 상위 계층에서 처리될수록 빠르고, DB까지 도달하는 요청이 적을수록 시스템 전체 성능이 좋다.

**시스템 설계에서의 의미**: "이 데이터는 어느 계층에서 캐시하는 것이 적절한가?"가 설계 포인트다. 정적 파일은 CDN, 세션은 Redis, DB 쿼리 결과는 애플리케이션 캐시가 적합하다.

---

## 캐시 읽기 전략

### 1. Cache-Aside (Lazy Loading)

가장 일반적인 패턴이다. 애플리케이션이 직접 캐시와 DB를 관리한다.

```
읽기:
1. 캐시에서 조회
2. 캐시에 있으면 (Cache Hit) → 바로 반환
3. 캐시에 없으면 (Cache Miss) → DB에서 조회 → 캐시에 저장 → 반환

[앱] → [캐시] → Hit? → 반환
              → Miss? → [DB] → 캐시에 저장 → 반환
```

- **장점**: 실제로 요청되는 데이터만 캐시됨 (메모리 효율적), 구현이 단순
- **단점**: 첫 요청은 항상 Cache Miss (Cold Start), 캐시와 DB 간 데이터 불일치 가능
- **적합한 경우**: 읽기가 많고, 모든 데이터를 캐시할 필요 없는 일반적인 상황

### 2. Read-Through

캐시 시스템이 DB 조회까지 대신 처리한다. 애플리케이션은 캐시만 바라본다.

```
[앱] → [캐시] → Miss? → 캐시가 직접 [DB] 조회 → 캐시에 저장 → 반환
```

- **장점**: 애플리케이션 코드가 단순 (캐시만 호출)
- **단점**: 캐시 시스템이 DB 접근 로직을 알아야 함
- **적합한 경우**: 캐시 라이브러리가 이 기능을 제공하는 경우

---

## 캐시 쓰기 전략

데이터가 변경될 때 캐시를 어떻게 갱신할 것인가의 문제다. **이것이 캐시에서 가장 어려운 부분**이다.

### 1. Write-Through

쓰기 시 캐시와 DB에 **동시에** 기록한다.

```
[앱] → 쓰기 → [캐시] + [DB] 동시 기록 → 완료
```

- **장점**: 캐시와 DB가 항상 일치 (강한 일관성)
- **단점**: 쓰기가 느림 (두 곳에 기록), 읽히지 않을 데이터도 캐시에 저장됨
- **적합한 경우**: 데이터 정합성이 중요하고, 쓰기 후 바로 읽기가 빈번한 경우

### 2. Write-Back (Write-Behind)

쓰기 시 **캐시에만** 기록하고, DB에는 나중에 비동기로 반영한다.

```
[앱] → 쓰기 → [캐시] → 완료 (빠름)
                     → 나중에 비동기로 [DB]에 반영
```

- **장점**: 쓰기 성능 매우 빠름, DB 부하 감소
- **단점**: 캐시 장애 시 아직 DB에 반영되지 않은 데이터 유실 가능
- **적합한 경우**: 쓰기가 매우 빈번하고, 약간의 데이터 유실을 감수할 수 있는 경우 (조회수, 좋아요 등)

### 3. Write-Around

쓰기 시 **DB에만** 기록하고, 캐시는 갱신하지 않는다.

```
[앱] → 쓰기 → [DB]에만 기록
      읽기 → [캐시] Miss → [DB] 조회 → 캐시에 저장
```

- **장점**: 한 번 쓰고 거의 안 읽히는 데이터가 캐시를 차지하지 않음
- **단점**: 쓰기 직후 읽기가 오면 Cache Miss 발생 (Replication Lag과 비슷한 문제)
- **적합한 경우**: 쓰기 후 즉시 읽기가 드문 경우 (로그 데이터 등)

---

## 쓰기 전략 비교

|전략|쓰기 속도|일관성|데이터 유실 위험|적합한 상황|
|---|---|---|---|---|
|Write-Through|느림|강함|없음|정합성 중요|
|Write-Back|매우 빠름|약함|있음|쓰기 빈번, 유실 허용|
|Write-Around|보통|보통|없음|쓰기 후 읽기 드문 경우|

## 캐시 무효화 (Cache Invalidation)

> "컴퓨터 과학에서 어려운 것 두 가지: 캐시 무효화와 이름 짓기" — Phil Karlton

캐시에 있는 데이터가 더 이상 유효하지 않을 때 어떻게 처리할 것인가의 문제다.

### TTL (Time To Live)

일정 시간이 지나면 캐시를 자동으로 삭제한다.

```
SET user:12345 "{name: 홍길동}" EX 3600   -- 3600초(1시간) 후 만료
```

- TTL이 짧으면: 데이터가 신선하지만 Cache Miss 증가 → DB 부하 증가
- TTL이 길면: Cache Hit 높지만 오래된(stale) 데이터를 제공할 수 있음

**시스템 설계에서의 의미**: TTL 설정은 **데이터 신선도 vs 캐시 효율** 트레이드오프다. 사용자 프로필은 TTL 1시간, 환율 정보는 TTL 1분처럼 데이터 특성에 따라 다르게 설정한다.

### 이벤트 기반 무효화

데이터가 변경되면 해당 캐시를 즉시 삭제하거나 갱신한다.

```
사용자 이름 변경 → 이벤트 발행 → 캐시에서 user:12345 삭제
다음 조회 시 Cache Miss → DB에서 새 데이터 로드 → 캐시에 저장
```

TTL보다 정확하지만 구현이 복잡하다. 어떤 캐시 키를 무효화해야 하는지 추적하는 것이 어렵다.

### 삭제 vs 갱신

- **삭제 (Invalidation)**: 캐시에서 키를 삭제하고, 다음 읽기 시 새로 로드. 더 안전하고 단순
- **갱신 (Update)**: 캐시의 값을 직접 새 값으로 교체. 빠르지만 레이스 컨디션 위험

대부분의 경우 **삭제가 더 안전**하다. 동시에 여러 곳에서 캐시를 갱신하면 마지막 쓰기가 이기는 문제(Last Write Wins)가 발생할 수 있기 때문이다.

---

## 캐시 문제 패턴

### 1. Cache Stampede (Thundering Herd)

인기 있는 캐시 키의 TTL이 만료되는 순간, 수많은 요청이 동시에 DB로 몰리는 현상.

```
TTL 만료 → 1000개 요청이 동시에 Cache Miss → DB에 1000개 쿼리 → DB 과부하
```

**해결 방법**:

- **Lock**: 하나의 요청만 DB에서 데이터를 가져오고, 나머지는 캐시가 갱신될 때까지 대기
- **TTL Jitter**: 만료 시간에 랜덤 값을 추가하여 동시 만료 방지 (TTL + random(0, 60))
- **사전 갱신**: TTL 만료 전에 백그라운드에서 미리 갱신

### 2. Cache Penetration

**존재하지 않는 데이터**에 대한 반복 요청. 캐시에도 DB에도 없으므로 매번 DB까지 도달한다.

```
GET user:999999999 → 캐시 Miss → DB 조회 → 없음 → 캐시에 아무것도 저장 안 함
→ 다음 요청도 같은 과정 반복 → DB 부하
```

**해결 방법**:

- **Null 캐싱**: 존재하지 않는 키에 대해 빈 값을 짧은 TTL로 캐시
- **Bloom Filter**: 데이터 존재 여부를 빠르게 판별하는 확률적 자료구조. "확실히 없다"를 O(1)로 판단

### 3. Cache Breakdown

하나의 **핫 키**(매우 인기 있는 데이터)가 만료될 때 대량의 요청이 DB를 직접 타격.

Cache Stampede와 유사하지만, 특정 핫 키 하나에 집중된다는 차이가 있다.

**해결 방법**: 핫 키에는 TTL을 두지 않거나, 매우 길게 설정하고 이벤트 기반으로 갱신한다.

## 캐시 교체 정책 (Eviction Policy)

캐시 메모리가 가득 찼을 때 어떤 데이터를 제거할 것인가.

|정책|방식|특징|
|---|---|---|
|LRU (Least Recently Used)|가장 오래 전에 사용된 것 제거|가장 일반적, Redis 기본값|
|LFU (Least Frequently Used)|가장 적게 사용된 것 제거|인기도 기반, 구현 복잡|
|FIFO (First In First Out)|먼저 들어온 것 먼저 제거|단순하지만 효율 낮음|
|Random|랜덤 제거|구현 가장 단순|
|TTL-based|만료 시간 기준 제거|TTL과 함께 사용|

**시스템 설계에서의 의미**: 대부분 **LRU**를 사용하면 무난하다. 특수한 접근 패턴(소수의 인기 아이템이 대부분의 트래픽을 차지하는 경우)에서는 LFU가 더 효율적일 수 있다.

## 로컬 캐시 vs 분산 캐시

### 로컬 캐시

애플리케이션 서버의 메모리에 저장한다.

```
[서버 1: 로컬 캐시] ← 자기만 접근 가능
[서버 2: 로컬 캐시] ← 자기만 접근 가능
[서버 3: 로컬 캐시] ← 자기만 접근 가능
```

- **장점**: 네트워크 호출 없음, 가장 빠름
- **단점**: 서버마다 캐시가 달라 데이터 불일치, 서버 재시작 시 캐시 소멸, 메모리 낭비(동일 데이터 중복)
- **적합한 경우**: 변경이 드문 설정 데이터, 짧은 TTL로 불일치 허용 가능한 경우

### 분산 캐시

Redis, Memcached 같은 외부 캐시 서버를 사용한다.

```
[서버 1] ─→
[서버 2] ─→ [Redis 클러스터] ← 모든 서버가 같은 캐시 공유
[서버 3] ─→
```

- **장점**: 모든 서버가 같은 캐시를 공유 (일관성), 대용량 캐시 가능, 서버와 독립적으로 확장
- **단점**: 네트워크 지연 존재 (~0.5ms), 캐시 서버 장애 시 영향 범위가 큼
- **적합한 경우**: 대부분의 서비스. 스케일 아웃된 환경에서는 사실상 필수

### 조합 사용

```
[서버] → [로컬 캐시 (L1)] → [Redis (L2)] → [DB]

L1: 매우 자주 접근하는 데이터, 짧은 TTL (10초)
L2: 일반적인 캐시 데이터, 중간 TTL (10분)
```

---

## Redis vs Memcached

|항목|Redis|Memcached|
|---|---|---|
|데이터 구조|String, Hash, List, Set, Sorted Set 등 다양|String only (Key-Value)|
|영속성|RDB/AOF로 디스크 저장 가능|없음 (순수 메모리)|
|레플리케이션|지원|미지원|
|클러스터링|Redis Cluster|클라이언트 샤딩|
|용도|캐시 + 세션 + 메시지 큐 + 리더보드 등 다목적|순수 캐싱 특화|

**시스템 설계에서의 의미**: 대부분의 경우 **Redis**를 선택하면 된다. 단순 캐싱만 필요하고 최대 성능이 필요한 극단적인 경우에 Memcached를 고려한다.

---

## CDN 캐시

정적 파일(이미지, JS, CSS, 영상)을 사용자와 가까운 엣지 서버에 캐시한다.

```
한국 사용자 → [서울 CDN 엣지] → Cache Hit → 바로 반환
                              → Cache Miss → [미국 원본 서버] → 응답 + 엣지에 캐시
```

[[DNS]]에서 다룬 GeoDNS가 사용자를 가장 가까운 엣지 서버로 안내하고, [[HTTP]]의 Cache-Control 헤더가 CDN의 캐싱 정책을 제어한다.

## 시스템 설계와의 연결 포인트

|캐시 개념|시스템 설계에서의 활용|
|---|---|
|Cache-Aside|가장 일반적인 캐시 패턴|
|Write-Through / Write-Back|쓰기 전략에 따른 정합성 vs 성능|
|TTL|데이터 신선도 vs 캐시 효율 트레이드오프|
|Cache Stampede|대규모 트래픽 환경의 장애 방지|
|Cache Penetration|악의적 요청 방어 (Bloom Filter)|
|LRU|캐시 메모리 관리 기본 정책|
|로컬 vs 분산 캐시|스케일 아웃 환경의 캐시 아키텍처|
|CDN|정적 콘텐츠 캐싱, 글로벌 지연 시간 감소|

## 핵심 요약

> 캐시는 느린 저장소의 데이터를 빠른 저장소에 복사하여 성능을 높이는 기법이다. 읽기 전략(Cache-Aside, Read-Through)과 쓰기 전략(Write-Through, Write-Back, Write-Around)의 조합이 일관성과 성능 사이의 트레이드오프를 결정한다. 캐시 무효화(TTL, 이벤트 기반)가 가장 어려운 문제이며, Cache Stampede, Penetration 같은 장애 패턴을 미리 이해하고 방어해야 한다. 대부분의 시스템에서 Redis 기반 분산 캐시 + CDN 조합이 표준이다.
