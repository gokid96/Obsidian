## 1. 개요
복합 인덱스로 RDS CPU가 31% → 19.4%로 줄었지만 EC2 CPU 73.8%, HikariCP Pending 54로 앞단 병목은 그대로였다.
원인은 쿼리 속도가 아니라 요청량 자체가 커넥션 풀(size=10)의 처리 한계를 초과하고 있었고 쿼리를 더 개선해도 Pending이 크게 줄지 않아서 근본 해결은 캐싱으로 DB 접근 횟수를 줄이고, 스케일아웃으로 처리량을 늘리는 것이다. 다만 그 전에 DB 접근이 발생했을 때의 비용을 최소화해두고, 캐시 미스 상황에서도 DB가 버틸 수 있는 기반을 만들어놓자
## 2. 커버링 인덱스

> 쿼리 실행에 필요한 모든 컬럼이 인덱스 안에 포함되어, 
> 실제 테이블을 읽지 않아도 되는 인덱스

일반/복합 인덱스는 어떤 행이 필요한지 찾아준다. 하지만 찾은 행마다 실제 데이터를 읽으러 테이블 페이지로 이동하는 과정이 남아있다.

```
인덱스: workspace_id | folder_id | (행 주소)
        1              NULL        → 페이지 3
        1              NULL        → 페이지 7

① 인덱스에서 조건에 맞는 행 주소 수집
② 주소마다 테이블 페이지로 이동해서 데이터 읽음  ← 랜덤 I/O
```

SELECT하는 컬럼을 인덱스 안에 다 넣으면 ②가 사라진다. 이를 커버링 인덱스라고 한다.
