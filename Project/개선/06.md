
### 현재 흐름 (동기 방식)

```
클라이언트 → POST /api/v1/email/send
                    ↓
             DB에 인증번호 저장
                    ↓
         AWS SES API 호출 (네트워크 I/O)
                    ↓  ← 여기서 스레드가 멈춰서 기다림 (보통 100~300ms)
         SES 응답 수신 완료
                    ↓
             200 OK 응답 반환
```

톰캣은 기본적으로 스레드풀(기본 200개)로 요청을 처리하는데, 응답을 기다리는 동안 해당 스레드는 아무것도 못 하고 점유함











회원가입 시 이메일 인증번호를 발송하는 `sendVerificationCode()`는 이렇게 동작한다.
```java
@Transactional
public void sendVerificationCode(String email) {
    verificationRepository.deleteByEmail(email);   // DB 커넥션 획득
    verificationRepository.save(verification);     // DB 저장

    sendEmail(email, code);  // ← AWS SES API 호출 (동기 블로킹)
                             //   트랜잭션이 열린 채로 외부 네트워크 대기
}
```

문제는 `@Transactional`이 열린 상태에서 `sesV2Client.sendEmail()`을 호출한다는 것이다.

---

### 두 가지 자원이 동시에 묶인다

**① 톰캣 스레드**
톰캣은 스레드풀(기본 200개)로 요청을 처리한다. `sendEmail()`은 외부 네트워크 I/O라서 SES가 응답할 때까지 해당 스레드는 아무것도 못 하고 점유된 채 대기한다. SES 응답 시간은 보통 100~300ms 수준이다.

**② DB 커넥션**
`@Transactional`이 붙어 있으면 메서드가 끝날 때까지 DB 커넥션을 잡고 있는다. 즉 SES 응답을 기다리는 100~300ms 동안 DB 커넥션도 함께 점유된다. HikariCP 기본 커넥션풀은 10개다. 스레드 200개보다 커넥션 10개가 훨씬 빨리 고갈된다.

```
스레드 점유 시간  : DB 저장(~5ms) + SES 대기(~200ms) + 트랜잭션 커밋(~5ms)
커넥션 점유 시간  : 위와 동일 (트랜잭션 종료까지)

→ SES 대기 200ms 동안 스레드 + 커넥션 둘 다 묶임
````

---

### 실제로 어떤 일이 일어나나

회원가입 요청이 10개만 동시에 들어와도 커넥션 10개가 전부 SES 대기 상태로 묶힐 수 있다. 이 순간 로그인, 게시글 조회, 워크스페이스 조회 등 **DB를 쓰는 모든 API가 커넥션을 못 받아서 대기 상태**가 된다. 회원가입 트래픽이 서비스 전체를 멈추는 구조다.

물론 회원가입이 동시에 10개씩 들어오는 서비스가 많지는 않다. 지금 당장 문제가 터지는 게 아니라 트래픽이 늘어나는 순간 가장 먼저 터질 수 있는 지점이라는 것이다.

### 이미지 업로드

`ImageService.upload()`도 동일한 패턴이다.
```java
public String upload(MultipartFile file, String folder) {
    s3Client.putObject(request, RequestBody.fromBytes(file.getBytes()));
    // ↑ Cloudflare R2에 동기 블로킹 업로드
    // 이미지는 이메일보다 훨씬 크고 업로드 시간도 길다
    return publicUrl + "/" + fileName;
}
```

차이가 있다면 이메일은 발송 결과를 응답에 안 담아도 되지만, 이미지는 업로드 후 URL을 즉시 응답으로 반환해야 하고 클라이언트가 그 URL을 게시글에 바로 써야 하기 때문에 단순 `@Async`로는 해결이 안 되고 다른 접근이 필요하다.
