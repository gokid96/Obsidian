## 1. 개요

이전 글에서 쿼리 수를 262번 → 8번으로 줄였지만 500ms 이하 비율은 45%에 머물렀다. 쿼리 수가 줄었는데도 왜 아직 느린 걸까?

자주 조회되는 쿼리라면 인덱스를 타고 있어야 한다. EXPLAIN으로 실제 실행 계획을 확인해봤다.

---

## 2. 인덱스란

DB는 조건에 맞는 행을 찾을 때 기본적으로 테이블 전체를 훑는다(Full Scan). 인덱스는 책의 목차처럼 특정 컬럼 값으로 행의 위치를 빠르게 찾을 수 있게 해주는 자료구조다.

### JPA가 자동으로 만들어주는 인덱스

JPA에서 `@ManyToOne`으로 연관관계를 선언하면 MySQL이 해당 FK 컬럼에 인덱스를 자동으로 생성한다.

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "workspace_id")
private Workspace workspace;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "parent_id")
private Folder parent;
```

위 선언만으로 MySQL은 아래 인덱스를 자동 생성한다.

```sql
-- folder 테이블
INDEX FKxxx (workspace_id)
INDEX FKyyy (parent_id)

-- post 테이블
INDEX FKaaa (workspace_id)
INDEX FKbbb (folder_id)
```

즉 우리 서비스는 별도로 인덱스를 만들지 않았어도 FK 인덱스가 이미 존재한다. 그런데 EXPLAIN을 찍어보니 여전히 느렸다. 이유가 뭘까.

### 단일 인덱스 vs 복합 인덱스

자동 생성된 FK 인덱스는 **단일 인덱스**다. 단일 인덱스는 해당 컬럼 하나에만 효율적이다.
```sql
-- workspace_id = 6 AND parent_id IS NULL
-- workspace_id 인덱스로 접근하면? → workspace_id=6인 행 전체를 읽은 뒤 parent_id IS NULL 필터링
-- parent_id 인덱스로 접근하면?   → parent_id=null인 행 전체를 읽은 뒤 workspace_id=6 필터링
```

두 컬럼을 동시에 조건으로 쓴다면 **복합 인덱스**가 필요하다.

```sql
-- 복합 인덱스: workspace_id + parent_id를 묶어서 인덱스 구성
INDEX(workspace_id, parent_id)
-- → workspace_id=6 AND parent_id=null 인 행으로 바로 이동
```

## 3. EXPLAIN 분석

MySQL의 `EXPLAIN`은 쿼리가 실제로 어떤 방식으로 실행되는지 보여준다. 핵심은 세 가지 컬럼이다.

|컬럼|의미|
|---|---|
|`type`|접근 방식. `ALL`은 Full Scan, `ref`/`range`는 인덱스 사용|
|`key`|실제로 사용된 인덱스|
|`rows`|읽은 행 수 (적을수록 좋음)|

### 3-1. 루트 폴더 조회

```sql
EXPLAIN SELECT * FROM folder WHERE workspace_id = 6 AND parent_id IS NULL;
```

```
type  : ref
key   : FKe35ll2wiaegk1t0soxk82v8wb  (parent_id FK 인덱스)
rows  : 130
Extra : Using where
````

`type = ref`라 Full Scan은 아니다. 그런데 `rows = 130`이 문제다. 워크스페이스 전체 폴더 수가 130개인데 루트 폴더만 찾는 쿼리에서 130행을 전부 읽고 있다.

자동 생성된 `parent_id` 단일 인덱스를 타고 있어서, `parent_id IS NULL`인 전체 행을 먼저 읽은 뒤 `workspace_id = 6`으로 필터링하는 순서다. `workspace_id` 필터가 인덱스 단계에서 적용되지 않는다.

### 3-2. 루트 게시글 조회

```sql
EXPLAIN SELECT * FROM post WHERE workspace_id = 6 AND folder_id IS NULL;
```

```
type  : index_merge
key   : FK(folder_id) + FK(workspace_id)
rows  : 303
Extra : Using intersect(FK(folder_id), FK(workspace_id)); Using where
````

`index_merge`는 두 개의 단일 인덱스를 각각 사용한 뒤 결과를 교집합(intersect)으로 합치는 방식이다. 인덱스를 두 번 타고 결과를 합치는 추가 작업이 발생한다. 복합 인덱스 하나로 한 번에 처리하는 것보다 비효율적이다.

### 3-3. @BatchSize IN 쿼리

````sql
EXPLAIN SELECT * FROM folder WHERE parent_id IN (1, 2, 3);
EXPLAIN SELECT * FROM post WHERE folder_id IN (1, 2, 3);
```
```
folder: type=range, key=FK(parent_id), rows=3
post  : type=range, key=FK(folder_id), rows=18
````

이쪽은 `type = range`로 인덱스를 잘 타고 있다.

---

## 4. 정리

|쿼리|type|문제|
|---|---|---|
|`folder WHERE workspace_id AND parent_id IS NULL`|`ref`|rows=130, workspace_id 인덱스 미적용|
|`post WHERE workspace_id AND folder_id IS NULL`|`index_merge`|단일 인덱스 2번 + intersect 비효율|
|`folder WHERE parent_id IN (...)`|`range`|양호|
|`post WHERE folder_id IN (...)`|`range`|양호|

JPA가 자동 생성한 FK 단일 인덱스만으로는 두 컬럼을 동시에 조건으로 쓰는 쿼리를 효율적으로 처리하지 못하고 있다. `workspace_id + parent_id`, `workspace_id + folder_id`를 묶은 복합 인덱스를 추가하면 개선될 것으로 보인다. 다음 글에서 인덱스를 추가하고 결과를 확인해보자.
