## 이메일 비동기 처리로 DB 커넥션 점유 시간 줄이기

## 문제 상황
```
클라이언트 → POST /api/v1/email/send
                    ↓
             DB에 인증번호 저장
                    ↓
         AWS SES API 호출 (네트워크 I/O)
                    ↓  ← 여기서 스레드가 멈춰서 기다림 (보통 100~300ms)
         SES 응답 수신 완료
                    ↓
             200 OK 응답 반환
```

톰캣은 기본적으로 스레드풀(기본 200개)로 요청을 처리하는데, 응답을 기다리는 동안 해당 스레드는 아무것도 못 하고 점유된다.

### 두 가지 자원이 동시에 묶인다

**1. 톰캣 스레드**
톰캣은 스레드풀(기본 200개)로 요청을 처리한다. `sendEmail()`은 외부 네트워크 I/O라서 SES가 응답할 때까지 해당 스레드는 아무것도 못 하고 점유된 채 대기한다. SES 응답 시간은 보통 100~300ms 수준이다.

**2. DB 커넥션**
`@Transactional`이 붙어 있으면 메서드가 끝날 때까지 DB 커넥션을 잡고 있는다. 즉 SES 응답을 기다리는 100~300ms 동안 DB 커넥션도 함께 점유된다. HikariCP 기본 커넥션풀은 10개다. 스레드 200개보다 커넥션 10개가 훨씬 빨리 고갈된다.
```
스레드 점유 시간  : DB 저장(~5ms) + SES 대기(~200ms) + 트랜잭션 커밋(~5ms)
커넥션 점유 시간  : 위와 동일 (트랜잭션 종료까지)

→ SES 대기 200ms 동안 스레드 + 커넥션 둘 다 묶임
```

## 해결 방법

### 방법 1. `@Async` (Spring 비동기)
```
클라이언트 → POST /api/v1/email/send
                    ↓
             DB에 인증번호 저장
                    ↓
         비동기 스레드에 이메일 발송 위임
                    ↓
         200 OK 즉시 응답  ← HTTP 스레드는 여기서 해방

         (별도 스레드) AWS SES API 호출 → 완료
```

**장점**: 구현 간단, 추가 인프라 없음  
**주의할 점**:
- `@Async`는 **같은 클래스 내에서 호출하면 동작 안 함** (프록시 기반이라 자기 자신 호출 시 프록시를 거치지 않음) → 별도 `EmailSender` 컴포넌트로 분리 필요
- `@Transactional`과 `@Async`를 같은 클래스에서 쓰면 트랜잭션 커밋 전에 이메일이 발송될 수 있음 → 트랜잭션 범위와 비동기 호출을 분리해야 함

### 방법 2. 메시지 큐 (Kafka / RabbitMQ)
```
클라이언트 → POST /api/v1/email/send
                    ↓
             DB에 인증번호 저장
                    ↓
         메시지 큐에 이벤트 발행 (수 ms)
                    ↓
         200 OK 즉시 응답

         (별도 Consumer 서버) 큐에서 이벤트 소비 → SES 호출
```

**장점**: 발송 실패 시 재시도가 자연스럽고, 서버가 죽어도 메시지가 유실되지 않음. 대용량 트래픽에 강함  
**단점**: Kafka/RabbitMQ 인프라 구축 필요, 복잡도 상승

### 방법 3. Spring WebFlux (리액티브)

톰캣 대신 Netty 기반으로 Non-blocking I/O 자체를 사용. 스레드 자체를 블로킹하지 않는 방식인데, 기존 코드가 MVC라면 전면 재작성이 필요해서 현실적으로는 마이그레이션 비용이 큼.

현재 규모에서는 별도의 스레드를 만들고 처리시키는 `@Async`로 구현하기로 했다.

## 구현

### 기존 동기 방식

회원가입 시 이메일 인증번호를 발송하는 `sendVerificationCode()`는 이렇게 동작한다.
```java
@Transactional
public void sendVerificationCode(String email) {
    verificationRepository.deleteByEmail(email);   // DB 커넥션 획득
    verificationRepository.save(verification);     // DB 저장

    sendEmail(email, code);  // ← AWS SES API 호출 (동기 블로킹)
                             //   트랜잭션이 열린 채로 외부 네트워크 대기
}
// 문제: @Transactional이 열린 상태에서 sesV2Client.sendEmail() 호출 (커넥션 200ms 점유)
```

### 비동기 방식으로 수정

**1. AsyncConfig - 이메일 전용 스레드풀 설정**
```java
@Slf4j
@EnableAsync
@Configuration
public class AsyncConfig implements AsyncConfigurer {

    @Bean(name = "emailTaskExecutor")
    public Executor emailTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);     // 평소 대기 스레드 5개
        executor.setMaxPoolSize(10);     // 최대 10개까지
        executor.setQueueCapacity(100);  // 10개 다 바쁘면 100개까지 대기
        executor.setThreadNamePrefix("email-async-");
        executor.initialize();
        return executor;
    }

    // @Async 메서드에서 예외 발생 시 중앙 처리
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
                log.error("Async error in {}: {}", method.getName(), ex.getMessage());
    }
}
```

**2. EmailSender - 비동기 발송 컴포넌트**

`@Service`가 아닌 `@Component`를 쓴 이유는 비즈니스 로직이 아니라 이메일 발송이라는 인프라 작업을 담당하기 때문이다.
```java
@Slf4j
@Component
@RequiredArgsConstructor
public class EmailSender {

    private final SesV2Client sesV2Client;

    @Value("${aws.ses.from-email}")
    private String fromEmail;
```

**3. EmailService - 트랜잭션 커밋 후 비동기 호출**
```java
public class EmailService {

    private final EmailSender emailSender;

    @Transactional
    public void sendVerificationCode(String email) {
        // 1. 등록된 이메일인지 확인
        // 2. 기존 인증번호 삭제
        // 3. 인증번호 생성 및 DB 저장

        // 4. 이메일 비동기 발송 (트랜잭션 커밋 후 스레드풀에 위임하고 즉시 반환)
        emailSender.sendAsync(email, code);  // 커넥션 점유 ~10ms
        log.info("인증번호 발송 완료: {}", email);
    }
}
```

트랜잭션 흐름이 바뀐 부분이 핵심이다.
```
BEFORE: 트랜잭션 열림 → DB 저장 → SES 200ms 대기 → 커밋 (커넥션 200ms 점유)
AFTER:  트랜잭션 열림 → DB 저장 → 스레드풀에 던짐 → 커밋 (커넥션 ~10ms 점유)
```

`emailSender.sendAsync()`를 호출하면 프록시가 가로채서 `emailTaskExecutor` 스레드풀에 작업을 던지고 즉시 반환한다. HTTP 스레드는 트랜잭션을 바로 커밋하고 `200 OK`를 반환한다. SES 호출은 별도 스레드가 처리한다.

응답시간이 **276ms → 19.8ms** 개선됐고, DB 커넥션 점유 시간이 줄어들면서 Active Connection도 평균 2개에서 0.047개로 떨어졌다.

`@Async` 하나로 HTTP 스레드가 SES 응답을 기다리지 않게 됐고, 트랜잭션도 DB 저장 직후 커밋되어 커넥션을 빠르게 반납하게 됐다.

현재 이메일 발송 실패 시 재시도가 없다. 발송 실패 로그를 남기는 수준으로 처리했으며, 재시도가 필요하다면 메시지 큐나 `@Retryable` 도입을 고려할 수 있다.
