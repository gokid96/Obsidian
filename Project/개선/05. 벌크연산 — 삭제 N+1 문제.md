# 삭제 N+1 문제와 벌크연산으로 92% 개선하기

## 1. 삭제 N+1

JPA로 엔티티를 삭제하면 Hibernate는 **연관된 엔티티를 하나씩 추적하며 건별로 DELETE를 날린다.**

SELECT N+1과 똑같은 구조다. SELECT N+1은 조회 시 연관 엔티티를 건별로 SELECT하는 문제고, 여기서는 삭제 시 연관 엔티티를 건별로 DELETE 할 때 문제다.

---

## 2. 문제

```java
// Workspace.java
@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> folders;

@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<WorkspaceMember> members;
```

```java
// Folder.java
@OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> children;

@OneToMany(mappedBy = "folder", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Post> posts;
```

`CascadeType.ALL + orphanRemoval = true`는 부모 엔티티의 삭제를 자식에게 전파하는 설정으로, 문제는 Hibernate가 이 Cascade를 처리할 때 영속성 컨텍스트에서 엔티티를 하나씩 추적하며 건별로 DELETE를 날린다는 것이다. 만약 폴더와 게시글이 여러 개 들어있는 워크스페이스 하나를 삭제하면?

`workspaceRepository.delete(workspace)` 한 줄이 내부에서 이렇게 동작한다.

```
workspaceRepository.delete(workspace) 호출
    ↓
Hibernate: folders에 CascadeType.ALL 있네
    ↓
folder 하나씩 DELETE 전파
    ↓
Hibernate: folder.children에도 CascadeType.ALL 있네
    ↓
하위 folder 하나씩 DELETE 전파
    ↓
Hibernate: folder.posts에도 CascadeType.ALL 있네
    ↓
post 하나씩 DELETE 전파
    ↓
...
```

```bash
select from post where workspace_id=? // 1번 (전체 조회)
delete from post where post_id=? // 1번
delete from post where post_id=? // 2번
delete from post where post_id=? // 3번
delete from post where post_id=? // 4번
delete from post where post_id=? // 5번... N번
```

k6로 폴더 130개(depth 3) + 게시글 650개가 담긴 워크스페이스를 삭제해보고 응답 시간도 측정했다.

```
DELETE 쿼리 : 895번
응답시간    : 1,123ms
```

## 3. 벌크연산이 필요한 이유

벌크연산이 필요한 사례로는 대표적으로

- 부모 삭제 시 연관 데이터가 많은 구조 (현재 나의 경우)
- 조건부 대량 삭제 (지난 알림 삭제, 읽은 메세지 삭제, 만료된 세션 토큰 삭제)
- 대량 업데이트 (휴면 계정 처리, 재고 일괄 차감, 포인트 만료)

문제는 단순히 쿼리 수가 많다는 것만이 아니다.

- **DB 왕복 오버헤드**: 쿼리 1번마다 네트워크 왕복이 발생한다.
- **락 경쟁**: 건별 DELETE는 각 행에 개별 락을 잡았다 푼다. 동시 요청이 많으면 락 경쟁이 심해진다.
- **응답시간**: 데이터가 늘어날수록 삭제 시간이 선형으로 증가한다.

벌크연산으로 이걸 **한 번의 쿼리로 묶어서 처리**한다.

```sql
-- 건별 DELETE (Before)
DELETE FROM post WHERE post_id = 1  -- 네트워크 왕복
DELETE FROM post WHERE post_id = 2  -- 네트워크 왕복
DELETE FROM post WHERE post_id = 3  -- 네트워크 왕복

-- 벌크연산 (After)
DELETE FROM post WHERE workspace_id = 1  -- 네트워크 왕복 1번
```

## 4. 벌크연산 적용 방법

#### 1. `@Modifying` (JPQL 벌크 DELETE)

```java
@Modifying(clearAutomatically = true)
@Query("DELETE FROM Post p WHERE p.workspace.workspaceId = :workspaceId")
void deleteAllByWorkspaceId(@Param("workspaceId") Long workspaceId);
```

영속성 컨텍스트를 우회해서 DB에 직접 쿼리를 날린다. `clearAutomatically = true` 를 붙이지 않으면 영속성 컨텍스트와 DB가 불일치한다.

---

#### 2. `deleteAllInBatch`

```java
postRepository.deleteAllInBatch(posts);
```

삭제할 엔티티 목록을 서비스에서 직접 넘겨야 한다. 넘긴 목록을 IN절로 묶어서 1번 쿼리로 삭제한다.

```sql
DELETE FROM post WHERE post_id IN (1, 2, 3, ...)
```

---

#### 3. `ON DELETE CASCADE` (DB 레벨)

```sql
FOREIGN KEY (folder_id) REFERENCES folder(folder_id) ON DELETE CASCADE
```

부모 삭제 시 DB가 알아서 연관 데이터를 삭제한다. JPA 코드 변경 없이 가장 빠르지만 JPA가 삭제 사실을 모른다.

---

## 5. 트레이드오프 — 벌크연산 방법 선택

세 가지 방법을 놓고 봤을 때 기준은 두 가지다.

1. 불필요한 쿼리가 추가되는가
2. JPA 레이어에서 제어가 가능한가

**deleteAllInBatch** 삭제할 엔티티 목록을 직접 넘겨야 한다. 보통 삭제 전에 각 엔티티를 순회하면서 뭔가 처리해야 할 때 사용한다. 현재는 워크스페이스 ID만 있는 상황에서 목록을 만들려면 SELECT가 먼저 나가야 한다. 벌크 연산으로 쿼리를 줄이려는 목적에 역행한다.

**ON DELETE CASCADE** 성능상 가장 빠르다. 하지만 DB가 알아서 처리하는 구조라 JPA는 삭제 사실을 모른다. 지금은 괜찮아도 나중에 삭제 시점에 알림이나 이벤트 발행 같은 로직이 추가되면 자식 엔티티 단위로 삭제를 추적할 수 없다.

**@Modifying** 워크스페이스 ID 하나로 연관 데이터를 한 번에 삭제할 수 있고, 삭제 순서도 서비스 코드에서 직접 제어할 수 있다. 영속성 컨텍스트를 우회하는 문제가 있지만 `clearAutomatically` 옵션으로 해결 가능하다.

> 영속성 컨텍스트 우회란?

`@Modifying`은 DB에 직접 쿼리를 날리기 때문에 JPA는 Post가 삭제된 사실을 모르는 채로 메모리(영속성 컨텍스트 1차 캐시)에 들고 있는다. 그래서 삭제 후 같은 트랜잭션에서 Post를 다시 조회하면 캐시에서 꺼내어 삭제된 데이터가 살아있는 것처럼 보인다. `clearAutomatically = true`로 캐시를 초기화하면 해결된다.

```
ON DELETE CASCADE  → 삭제 후 처리 로직 없음, 그냥 지우기만 하면 됨
deleteAllInBatch   → 삭제 전에 엔티티를 순회하며 뭔가 처리해야 함
@Modifying         → ID만 알고 있고, 추가 처리 로직 없이 한 번에 삭제
```

→ **`@Modifying` 선택**

## 6. @Modifying 적용 중 만난 FK 제약 문제

`@Modifying`으로 한 번에 해결하려 했으나, `folder` 테이블에서 `parent_id`가 `folder_id`를 참조하는 자기참조 구조 때문에 FK 제약 위반이 발생했다. 부모 폴더를 먼저 지우려고 하면 자식 폴더가 아직 살아있어서 제약이 걸리는 것이다.

> 왜 이런 문제가 생길까

MySQL은 쿼리를 받으면 **저장된 순서대로** 삭제하려고 하는데, 루트 폴더가 먼저 나오면

```
folder(depth1, parent_id=null) 삭제 시도
→ folder(depth2, parent_id=depth1) 하위 폴더가 아직 살아있음
→ FK 제약 위반
```

depth가 고정이라면 단계별로 나눌 수 있지만

```
depth 동적으로 생성 → 몇 단계인지 모름 → 순서를 코드에서 제어 불가능
```

해결 방법은 두 가지다.

```
parent_id null 업데이트 방식 → 쿼리 1번 추가, 코드에서 의도가 명확
ON DELETE CASCADE             → 쿼리 1번, 자식 엔티티 삭제 추적 불가
```

`ON DELETE CASCADE`는 DB가 알아서 처리하는 게 코드에서 눈에 보이지 않아 나중에 파악하기 어려워서 설정한 내용을 잊을것같다. 반면 `parent_id`를 null로 업데이트해서 FK 제약을 해제하는 방식은 코드에서 의도가 명확하게 보인다. 쿼리가 1번 더 나가지만 워크스페이스 삭제는 드문 행동이라 성능에 영향을 줄 만한 상황이 아니라고 판단하였다.

결국 **아주 약간의 성능보다 유지보수성**이 낫다.

```java
postRepository.deleteByWorkspaceWorkspaceId(workspaceId);       // 1. 게시글 삭제
folderRepository.clearParentByWorkspaceId(workspaceId);         // 2. 부모폴더 null 업데이트 (FK 제약 해제)
folderRepository.deleteAllByWorkspaceId(workspaceId);           // 3. 폴더 삭제
workspaceMemberRepository.deleteAllByWorkspaceId(workspaceId);  // 4. 멤버 삭제
workspaceRepository.delete(member.getWorkspace());              // 5. 워크스페이스 삭제
```
