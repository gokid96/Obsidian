
## 1. 삭제 N+1 문제

JPA로 엔티티를 삭제하면 Hibernate는 **연관된 엔티티를 하나씩 추적하며 건별로 DELETE를 날린다.**

```sql
DELETE FROM post WHERE post_id = 1
DELETE FROM post WHERE post_id = 2
DELETE FROM post WHERE post_id = 3
...
```

SELECT N+1과 똑같은 구조다. SELECT N+1은 조회 시 연관 엔티티를 건별로 SELECT하는 문제고, 여기서는 삭제 시 연관 엔티티를 건별로 DELETE 문제다

---

## 2. 문제 발견

```java
// Workspace.java
@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> folders;

@OneToMany(mappedBy = "workspace", cascade = CascadeType.ALL, orphanRemoval = true)
private List<WorkspaceMember> members;
```

```java
// Folder.java
@OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Folder> children;

@OneToMany(mappedBy = "folder", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Post> posts;
```

`CascadeType.ALL + orphanRemoval = true`는 부모 엔티티의 삭제를 자식에게 전파하는 설정으로 문제는 Hibernate가 이 Cascade를 처리할 때 영속성 컨텍스트에서 엔티티를 하나씩 추적하며 건별로 DELETE를 날린다 만약 폴더와 게시글이 여러개 들어있는 한개의 워크스페이스를 삭제하면 ?
`workspaceRepository.delete(workspace)` 한 줄이 내부에서 이렇게 동작한다

```
workspaceRepository.delete(workspace) 호출
    ↓
Hibernate: folders에 CascadeType.ALL 있네
    ↓
folder 하나씩 DELETE 전파
    ↓
Hibernate: folder.children에도 CascadeType.ALL 있네
    ↓
하위 folder 하나씩 DELETE 전파
    ↓
Hibernate: folder.posts에도 CascadeType.ALL 있네
    ↓
post 하나씩 DELETE 전파
    ↓
...
```

```bash
select from post where workspace_id=? // 1번 (전체 조회) 
delete from post where post_id=? // 1번 
delete from post where post_id=? // 2번 
delete from post where post_id=? // 3번 
delete from post where post_id=? // 4번 
delete from post where post_id=? // 5번... N번
```

k6로 폴더 130개(depth 3) + 게시글 650개가 담긴 워크스페이스를 삭제 해보고 응답 시간도 측정했다.

## 3. 벌크연산이 필요한 이유

건별 DELETE의 문제는 단순히 쿼리 수가 많다는 것만이 아니다.

- **DB 왕복 오버헤드**: 쿼리 1번마다 네트워크 왕복이 발생한다. 
- **락 경쟁**: 건별 DELETE는 각 행에 개별 락을 잡았다 푼다. 동시 요청이 많으면 락 경쟁이 심해진다.
- **응답시간**: 데이터가 늘어날수록 삭제 시간이 선형으로 증가한다.

벌크연산은 이걸 **한 번의 쿼리로 묶어서 처리**한다.

```sql
-- 건별 삭제 (Before)
DELETE FROM post WHERE post_id = 1
DELETE FROM post WHERE post_id = 2
...  -- 750번

-- 벌크 삭제 (After)
DELETE FROM post WHERE workspace_id = 6  -- 1번
```

## 4. 벌크연산 적용 방법

### `@Modifying` JPQL

Repository에 JPQL 벌크 DELETE 메서드를 추가한다.

```java
// PostRepository.java
@Modifying
@Query("DELETE FROM Post p WHERE p.folder.workspace.workspaceId = :workspaceId")
void deleteAllByWorkspaceId(@Param("workspaceId") Long workspaceId);

// FolderRepository.java
@Modifying
@Query("DELETE FROM Folder f WHERE f.workspace.workspaceId = :workspaceId")
void deleteAllByWorkspaceId(@Param("workspaceId") Long workspaceId);

// WorkspaceMemberRepository.java
@Modifying
@Query("DELETE FROM WorkspaceMember wm WHERE wm.workspace.workspaceId = :workspaceId")
void deleteAllByWorkspaceId(@Param("workspaceId") Long workspaceId);
```

그리고 `WorkspaceService.deleteWorkspace()`에서 순서대로 호출한다.

```java
// Before
workspaceRepository.delete(workspace);  // Cascade로 895번 DELETE

// After
postRepository.deleteAllByWorkspaceId(workspaceId);            // 1번
folderRepository.deleteAllByWorkspaceId(workspaceId);          // 1번
workspaceMemberRepository.deleteAllByWorkspaceId(workspaceId); // 1번
workspaceRepository.delete(workspace);                         // 1번
```

FK 참조 순서대로 (`post → folder → workspace_member → workspace`) 지워야 FK 에러가 나지 않는다.

## 5. 트레이드오프 고민

### 후보 비교

||CascadeType.ALL (현재)|@Modifying JPQL|deleteAllInBatch|ON DELETE CASCADE|
|---|---|---|---|---|
|쿼리 수|N번 (건별)|테이블당 1번|테이블당 1번|DB 처리|
|영속성 컨텍스트|인지 O|인지 X|인지 O|인지 X|
|삭제 순서 제어|JPA 자동|서비스에서 명시|서비스에서 명시|DB 자동|
|추가 조회 필요|X|X|O (엔티티 목록)|X|

### 왜 `@Modifying`을 선택했나

**`ON DELETE CASCADE`** 가 성능상 가장 빠르지만, DB 스키마 변경이 필요하고 JPA가 삭제 사실을 모른 채 트랜잭션이 끝난다. 이후 삭제 이벤트 발행이나 후처리 로직이 추가될 때 JPA 레이어에서 제어하기 어려워진다.

**`deleteAllInBatch`** 는 삭제 대상 엔티티 목록을 서비스 코드에서 직접 수집해야 한다. 워크스페이스 ID만 알고 있는 상황에서 엔티티를 먼저 조회해서 넘기는 건 불필요한 SELECT가 추가된다.

**`@Modifying` JPQL** 은 ID 하나로 연관된 모든 데이터를 한 방에 지울 수 있고, 삭제 순서를 서비스 코드에서 명시적으로 제어할 수 있다.

### `@Modifying`의 주의점 — 영속성 컨텍스트 불일치

`@Modifying`은 DB에 직접 쿼리를 날리기 때문에 **영속성 컨텍스트(1차 캐시)가 삭제 사실을 모른다.** 같은 트랜잭션 안에서 벌크 DELETE 이후 해당 엔티티를 조회하면 삭제된 데이터가 캐시에서 튀어나올 수 있다.

보편적인 해결 방법은 4가지다.

|방법|설명|
|---|---|
|`@Modifying(clearAutomatically = true)`|벌크 연산 후 자동으로 1차 캐시 초기화|
|`em.clear()` 직접 호출|서비스 코드에서 수동으로 1차 캐시 초기화|
|벌크 연산을 트랜잭션 맨 앞에 배치|이후 조회가 없으면 불일치 자체가 발생 안 함|
|별도 트랜잭션으로 분리|벌크 연산과 이후 로직의 영속성 컨텍스트를 분리|

이번 케이스는 벌크 DELETE 이후 추가 조회 없이 트랜잭션이 끝난다. 불일치 문제가 발생하지 않는 구조지만, 관례상 `clearAutomatically = true`를 붙여두는 것이 안전하다.
