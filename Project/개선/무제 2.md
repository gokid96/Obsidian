## 캐시 읽기/쓰기 전략

캐시를 어떻게 채우고, 어떻게 갱신할지에 대한 패턴이다.

---

### 읽기 전략

**Cache-Aside (Lazy Loading)**

```
요청
  ↓
캐시 확인
  ├─ 히트 → 캐시에서 반환
  └─ 미스 → DB 조회 → 캐시에 저장 → 반환
```

앱이 직접 캐시를 관리한다. 캐시 미스 시에만 DB를 조회하고 결과를 캐시에 올린다. 가장 일반적인 패턴으로 Spring의 `@Cacheable`이 이 방식이다.

트레이드오프: 처음 요청(콜드 스타트)은 항상 DB를 탄다. 캐시가 비어있는 상태에서 트래픽이 몰리면 DB에 부하가 집중될 수 있다 → Cache Stampede.

**Read-Through**

```
요청
  ↓
캐시 확인
  ├─ 히트 → 캐시에서 반환
  └─ 미스 → 캐시가 직접 DB 조회 후 저장 → 반환
```

Cache-Aside와 흐름은 같지만 DB 조회를 앱이 아닌 캐시 레이어가 대신한다. 앱 코드가 단순해지지만 캐시가 DB 접근 로직을 알아야 한다. Redis + 별도 라이브러리 조합에서 사용한다.

---

### 쓰기 전략

**Write-Through**

```
쓰기 요청
  ↓
캐시 업데이트 + DB 업데이트 (동시)
  ↓
완료
```

쓸 때 캐시와 DB를 동시에 갱신한다. 캐시와 DB가 항상 일치하는 게 장점이다. 단점은 쓰기마다 두 곳을 갱신하므로 쓰기 성능이 떨어지고, 자주 안 읽히는 데이터도 캐시에 올라간다.

**Write-Back (Write-Behind)**

```
쓰기 요청
  ↓
캐시만 업데이트 → 즉시 응답
  ↓ (비동기, 나중에)
DB 반영
```

캐시에만 먼저 쓰고 DB 반영은 나중에 비동기로 처리한다. 쓰기 성능이 가장 빠르다. 단점은 캐시가 날아가면 DB에 반영 안 된 데이터가 유실될 수 있다. 로그나 조회수처럼 유실을 어느 정도 허용할 수 있는 데이터에 적합하다.

**Write-Around**

```
쓰기 요청
  ↓
DB에만 저장 (캐시 건드리지 않음)
  ↓
다음 읽기 요청에서 캐시 미스 → 그때 캐시에 올림
```

쓰기 시 캐시를 무효화하지 않고 DB에만 반영한다. 다음 읽기 때 미스가 나면서 자연스럽게 갱신된다. 쓰기 빈도가 높고 바로 읽히지 않는 데이터에 적합하다.

---

### 이 프로젝트에서 선택한 패턴

**Cache-Aside + 명시적 Evict**

```
읽기: @Cacheable → 미스 시 DB 조회 후 캐시에 저장
쓰기: @CacheEvict → 변경 시 캐시 무효화, 다음 읽기 때 재적재
```

폴더 트리는 읽기가 압도적으로 많고 쓰기(생성/수정/삭제)는 드물다. Write-Through나 Write-Back은 쓰기 성능을 위한 전략인데 여기서는 쓰기 최적화가 필요하지 않다. 읽기 최적화가 목적이므로 Cache-Aside가 가장 적합하다.
