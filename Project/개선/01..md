``` java
/**  
 * 워크스페이스 멤버 권한 확인 (공통 헬퍼)  
 */
 private WorkspaceMember getMemberOrThrow(Long userId, Long workspaceId) {  
  
    Workspace workspace = workspaceRepository.findById(workspaceId)  
            .orElseThrow(() -> new BusinessException(ErrorCode.WORKSPACE_NOT_FOUND));  
    Users user = userRepository.findById(userId)  
            .orElseThrow(() -> new BusinessException(ErrorCode.USER_NOT_FOUND));  
  
    return workspaceMemberRepository.findByWorkspaceAndUser(workspace, user)  
            .orElseThrow(() -> new BusinessException(ErrorCode.WORKSPACE_NOT_FOUND));
}
```

첫번째로 워크스페이스의 권한 확인을 위해 1.워크스페이스 존재 여부 확인 2. 유저 존재 여부 확인 3.해당 유저가 해당 워크스페이스의 멤버인지 확인 이렇게 불필요한 쿼리를 3번 날리고있다. 
단순하게 `workspace_id + user_id` 값만으로 `workspace_member` 테이블에서 바로 조회하는 방법으로 `workspace_member`에서 바로 조회하면

```
workspace 존재 여부 → workspace_member에 해당 workspace_id가 있으면 존재
user 존재 여부     → workspace_member에 해당 user_id가 있으면 존재
멤버 여부          → 행이 존재하면 멤버
```

세 가지를 **쿼리 1번**으로 다 확인할수있다. 다만 트레이드 오프가있다 

**Before (3번 방식)의 장점**

```
workspace 없음 → WORKSPACE_NOT_FOUND
user 없음      → USER_NOT_FOUND  
멤버 아님      → ACCESS_DENIED
각각 다른 에러코드로 정확한 원인 전달 가능
```

**After (1번 방식)의 단점**

```
findByWorkspaceWorkspaceIdAndUserUserId() 결과가 없으면
→ workspace가 없는 건지
→ user가 없는 건지
→ 멤버가 아닌 건지
구분 불가 → ACCESS_DENIED 하나로 뭉개짐 (접근 권한이 없습니다.)
```
현재는 거의 모든 CRUD를 할때 해당 메서드가 사용되기때문에 데이터베이스 부하를 줄이는 관점으로 접근했다. 또한 보안 관점에서도 workspace가 존재하지 않는지, user가 존재하지 않는지 등의 내부 정보를 외부에 노출하지 않는 것이 오히려 유리하다고 판단해 ACCESS_DENIED 단일 에러코드로 통일했다.

그 후 두번째가 성능에 가장 치명적으로 루트 폴더 안에 속한 자식 폴더들을 lazy loading으로 가져오고있다.

> 레이지 로딩이란?

레이지 로딩(Lazy Loading)이란 필요한 시점까지 객체나 데이터의 로딩을 지연시키는 전략으로, 연관 관계의 필드를 함께 불러오지 않고, Hibernate에서 가짜 객체(프록시)로 만들어 놓는다 그 후 연관 데이터가 필요할 때만 DB에서 가져오는 성능 최적화 전략이다.
반대의 개념으로는 즉시 로딩 (Eager Loading)이 있다.

| 구분    | Eager Loading             | Lazy Loading                |
| ----- | ------------------------- | --------------------------- |
| 로딩 시점 | 즉시 (객체 생성 시)              | 실제 사용 시                     |
| 성능    | 초기 로딩 느림                  | 초기 로딩 빠름                    |
| 메모리   | 많이 사용                     | 필요한 만큼 사용                   |
| 기본값   | `@ManyToOne`, `@OneToOne` | `@OneToMany`, `@ManyToMany` |

레이지 로딩(Lazy Loading)에서 발생하는 문제로는 두가지가 있다.

**LazyInitializationException**: 트랜잭션이 종료된 후 LAZY 프록시에 접근할 때 발생하는 예외

**N+1 문제**: 1번의 쿼리로 조회한 N개의 엔티티에 대해 연관 데이터를 가져오기 위해 추가로 N번의 쿼리가 실행되는 성능 문제

## 현재 Folder 엔티티에서의 상태

```java
//하위 폴더들  
@OneToMany 
private List<Folder> children = new ArrayList<>();

//루트 폴더 가져오기
List<Folder> folders = folderRepository.findByWorkspaceWorkspaceIdAndParentIsNull(workspaceId);
```
->
```sql
SELECT * FROM folder WHERE workspace_id = ? AND parent_id IS NULL
```

`children`은 **프록시 객체** 실제 데이터가 없고 껍데기만 있는 상태.
```java
folders.get(0).getChildren() // 아직 DB 조회 안 함, 프록시 상태
```

실제로 조회가 일어나는 순간은 응답이 나갈때 이루어 지면서 N+1이 발생한다.
```java
/* 하위 폴더 + 게시글 포함 */
public static FolderResponseDTO from(Folder folder) {  
    return FolderResponseDTO.builder()
        ...
		.children(folder.getChildren().stream()  
        .map(FolderResponseDTO::from)  
        .collect(Collectors.toList()))
        .build();
}
```

```
-- 루트폴더1.getChildren() 호출 시 SELECT * FROM folder WHERE parent_id = ? (루트폴더1_id) 
-- 루트폴더2.getChildren() 호출 시 SELECT * FROM folder WHERE parent_id = ? (루트폴더2_id) 
-- 하위폴더1.getChildren() 호출 시 (재귀) SELECT * FROM folder WHERE parent_id = ? (하위폴더1_id) 
-- 하위폴더2.getChildren() 호출 시 (재귀) SELECT * FROM folder WHERE parent_id = ? (하위폴더2_id) 
...총 130번

그리고 `.map(FolderResponseDTO::from)` 이게 재귀 호출이라서 가져온 children 각각에 또 `from()`을 호출하고, 또 `getChildren()` → DB 조회 발생
```

**N+1 해결방법 고려하기**

**1. Fetch Join** (depth가 동적으로 변하는 구조에선 Fetch Join을 쓰기 어려움)
```java
@Query("SELECT f FROM Folder f JOIN FETCH f.children") // 명시한 만큼 만 가져올수 있음
```
연관 엔티티를 JOIN으로 한 번에 가져옴 가장 보편적인 해결책
단점: 카테시안 곱 위험, 페이징 불가

**2. @EntityGraph** (Fetch Join이랑 똑같이 depth를 미리 알아야한다.)
```java
@EntityGraph(attributePaths = {"children"})
List<Folder> findAll();
```
Fetch Join과 결과 동일 JPQL 없이 어노테이션으로 처리
단점: 복잡한 쿼리엔 한계

**3. Batch Size** (depth가 늘어나면 쿼리도 늘어난다. depth에 종속적)
```java
@BatchSize(size = 100)
@OneToMany
private List<Folder> children;
```
```
루트 10개 children 조회 → IN 쿼리 1번 하위 30개 
children 조회 → IN 쿼리 1번 
하위하위 90개 children 조회 → IN 쿼리 1번 
───────────────────────── 
총 3번 
```
LAZY 로딩은 유지하면서 IN 쿼리로 묶어서 처리 130번 → 2번 (100개씩 묶음)
단점: 쿼리가 완전히 1번은 아님

**4. 전체 조회 후 메모리에서 트리 구성**
```java
List<Folder> allFolders = folderRepository.findAll();
// 메모리에서 parent_id 기준으로 트리 구성
```
쿼리 1번
재귀 계층 구조에 가장 자연스러운 해결책
단점: 데이터 많으면 메모리 부담, 구현 복잡
