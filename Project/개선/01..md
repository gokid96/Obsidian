``` java
/**  
 * 워크스페이스 멤버 권한 확인 (공통 헬퍼)  
 */
 private WorkspaceMember getMemberOrThrow(Long userId, Long workspaceId) {  
  
	    Workspace workspace = workspaceRepository.findById(workspaceId)  
	            .orElseThrow(() -> new BusinessException(ErrorCode.WORKSPACE_NOT_FOUND));  
	    Users user = userRepository.findById(userId)  
	            .orElseThrow(() -> new BusinessException(ErrorCode.USER_NOT_FOUND));  
	  
	    return workspaceMemberRepository.findByWorkspaceAndUser(workspace, user)  
	            .orElseThrow(() -> new BusinessException(ErrorCode.WORKSPACE_NOT_FOUND));
}
```

첫번째로 워크스페이스의 권한 확인을 위해 
1.워크스페이스 존재 여부 확인 2. 유저 존재 여부 확인 3.해당 유저가 해당 워크스페이스의 멤버인지 확인 이렇게 불필요한 쿼리를 3번 날리고있다. 
단순하게 `workspace_id + user_id` 값만으로 `workspace_member` 테이블에서 바로 조회하는 방법으로 `workspace_member`에서 바로 조회하면

```
workspace 존재 여부 → workspace_member에 해당 workspace_id가 있으면 존재
user 존재 여부     → workspace_member에 해당 user_id가 있으면 존재
멤버 여부          → 행이 존재하면 멤버
```

세 가지를 **쿼리 1번**으로 다 확인할수있다. 다만 트레이드 오프가있다 

**Before (3번 방식)의 장점**

```
workspace 없음 → WORKSPACE_NOT_FOUND
user 없음      → USER_NOT_FOUND  
멤버 아님      → ACCESS_DENIED
각각 다른 에러코드로 정확한 원인 전달 가능
```

**After (1번 방식)의 단점**

```
findByWorkspaceWorkspaceIdAndUserUserId() 결과가 없으면
→ workspace가 없는 건지
→ user가 없는 건지
→ 멤버가 아닌 건지
구분 불가 → ACCESS_DENIED 하나로 뭉개짐 (접근 권한이 없습니다.)
```
현재는 거의 모든 CRUD를 할때 마다 해당 메서드가 사용 되기 때문에 데이터베이스 부하를 줄이는 관점으로 접근했다. 또한 보안 관점에서도 workspace가 존재하지 않는지, user가 존재하지 않는지 등의 내부 정보를 외부에 노출하지 않는 것이 오히려 유리하다고 판단해 ACCESS_DENIED 단일 에러 코드로 통일했다.

그 후 두번째가 성능에 가장 치명적으로 루트 폴더 안에 속한 자식 폴더들을 lazy loading으로 가져오고있다.

> 레이지 로딩이란?

레이지 로딩(Lazy Loading)이란 필요한 시점까지 객체나 데이터의 로딩을 지연시키는 전략으로, 연관 관계의 필드를 함께 불러오지 않고, Hibernate에서 가짜 객체(프록시)로 만들어 놓는다 
그 후 연관 데이터가 필요할 때만 DB에서 가져오는 성능 최적화 전략이다.
반대의 개념으로는 즉시 로딩 (Eager Loading)이 있다.

| 구분    | Eager Loading             | Lazy Loading                |
| ----- | ------------------------- | --------------------------- |
| 로딩 시점 | 즉시 (객체 생성 시)              | 실제 사용 시                     |
| 성능    | 초기 로딩 느림                  | 초기 로딩 빠름                    |
| 메모리   | 많이 사용                     | 필요한 만큼 사용                   |
| 기본값   | `@ManyToOne`, `@OneToOne` | `@OneToMany`, `@ManyToMany` |
 LAZY - 필요할 때만 쿼리 발생
 EAGER - 항상 무조건 쿼리 발생

레이지 로딩(Lazy Loading)에서 발생하는 문제로는 두가지가 있다.

**LazyInitializationException**: 트랜잭션이 종료된 후 LAZY 프록시에 접근할 때 발생하는 예외

**N+1 문제**: 1번의 쿼리로 조회한 N개의 엔티티에 대해 연관 데이터를 가져오기 위해 추가로 N번의 쿼리가 실행되는 전형적인 문제로 현재의 경우에 해당된다.

## 현재 Folder 엔티티에서의 상태

```java
// 하위 폴더들  
@OneToMany 
private List<Folder> children = new ArrayList<>();
// 폴더 내 게시글들  
@OneToMany
private List<Post> posts = new ArrayList<>();

//루트 폴더 가져오기
List<Folder> folders = folderRepository.findByWorkspaceWorkspaceIdAndParentIsNull(workspaceId);
```
실제 실행되는 쿼리
```sql
SELECT * FROM folder WHERE workspace_id = ? AND parent_id IS NULL
```

`@OneToMany`는 **프록시 객체** 실제 데이터가 없고 껍데기만 있는 상태가 된다.
```java
// 아직 DB 조회 안 함, 프록시 상태 -> 필요할때 쿼리
folders.get(0).getChildren()  → SELECT * FROM folder WHERE parent_id = 1 folders.get(0).getPosts()     → SELECT * FROM post WHERE folder_id = 1 folders.get(1).getChildren()  → SELECT * FROM folder WHERE parent_id = 2 folders.get(1).getPosts()     → SELECT * FROM post WHERE folder_id = 2

//자식 폴더에 접근하는 순간 그 자식의 children/posts도 또 프록시 상태 트리 깊이가 깊어질수록 지수적으로 쿼리가 늘어 남
```

### N+1 해결방법 고려하기

**1. Fetch Join** (depth가 동적으로 변하는 구조에선 Fetch Join을 쓰기 어려움)
```java
// 명시한 만큼 만 가져올수 있음
@Query("SELECT f FROM Folder f JOIN FETCH f.children") 
```
연관 엔티티를 JOIN으로 한 번에 가져옴 가장 보편적인 해결책
단점: 카테시안 곱 위험(MultipleBagFetchException), 페이징 불가
**MultipleBagFetchException**
```sql
-- List 타입 컬렉션 두 개 이상을 동시에 FETCH JOIN하면 Hibernate가 아예 막아버림
@Query("SELECT f FROM Folder f JOIN FETCH f.children JOIN FETCH f.posts") 
-- -> MultipleBagFetchException 발생 
```
카테시안 곱 (SQL은 행 기반이라 관계없는 테이블을 JOIN할때 가능한 모든 조합을 뱉음)
```
folder 1 
	├── children: A, B, C 
	└── posts: post_1, post_2
children 3개, posts 2개인 폴더를 FETCH JOIN하면 관계가 없어서 모든 조합을 생성
3 x 2 = 6개의 중복 행이 생성됨 
 folder_id | child_id | post_id 
	1      | child_A  | post_1
	1      | child_A  | post_2 
	1      | child_B  | post_1 
	1      | child_B  | post_2 
	1      | child_C  | post_1 
	1      | child_C  | post_2
```
---

**2. @EntityGraph** (Fetch Join보다 간단한 경우)
```java
// JPQL 없이 어노테이션으로 연관 엔티티를 한 번에 로딩 
@EntityGraph(attributePaths = {"children", "children.children"}) List<Folder> findAll();
// Fetch Join과 동작 동일, JPQL 없이 어노테이션으로 처리 attributePaths에 명시한 depth까지만 로딩 가능
```
단점: Fetch Join과 동일하게 카테시안 곱, MultipleBagFetchException 위험
depth가 동적으로 변하는 구조에선 사용하기 어려움 복잡한 쿼리엔 한계

---

**3. Batch Size** (depth가 늘어나면 쿼리도 늘어난다. depth에 종속적)
```java
@BatchSize(size = 100)
@OneToMany
private List<Folder> children;

@BatchSize(size = 100)  
@OneToMany
private List<Post> posts = new ArrayList<>();
```
```
children/posts 262번 → IN 쿼리로 묶음 
총 262번 → 8번
```
LAZY 로딩은 유지하면서 IN 쿼리로 묶어서 처리 262번 → 8번
단점: N+1을 완전히 없애는 건 아니고, **쿼리 횟수를 줄여주는** 방식

**4. 전체 조회 후 메모리에서 트리 구성**
```java
// 1. 쿼리 2번으로 전체 조회
List<Folder> allFolders = folderRepository.findAllByWorkspaceId(workspaceId); List<Post> allPosts = postRepository.findAllByWorkspaceId(workspaceId);
// 2. Map으로 그룹핑
// 3. 루트만 필터링해서 트리 조립
```
재귀 계층 구조에 가장 자연스러운 해결책
단점: 데이터 많으면 메모리 부담, 구현 복잡

---
트레이드 오프를 고민한 결과 실제로 문제가 될 만큼 depth가 깊어지는 케이스가 얼마나 자주 발생하냐를 봤을 때, 그게 드문 케이스라면 BatchSize로 충분하다.
실제로 문제가 발생하면 구현이 조금 복잡해지지만 메모리에서 트리 구성하는 방법으로 고민해보기로 하고 일단 100개 씩 가져와보자

1. getMemberOrThrow 쿼리 3번 → 1번
2. @BatchSize(size=100) 추가 → children/posts 262번 → 8번
