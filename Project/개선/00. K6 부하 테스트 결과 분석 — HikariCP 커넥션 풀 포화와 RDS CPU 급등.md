## 1. 테스트 개요

## 4. 근본 원인 흐름

```
VU 증가 (0 → 100)
  └─► DB 쿼리 급증
        └─► HikariCP Pool(10) 포화
              ├─► Pending 연결 23개 대기
              ├─► RDS CPU 53% 급등 (쿼리 처리 지연)
              └─► Connection Acquire Time 80ms 추가
                    └─► API 응답시간 500ms 초과
                          └─► Load Average 9.23 (CPU 큐 포화)
```

폴더트리 API에서 **N+1 쿼리 또는 대용량 조회**가 발생하고 있을 가능성이 높다.  
해당 API가 공개페이지보다 느리고, DB 부하의 주요 원인으로 추정된다.

## 5. 개선 방안

### 🔴 즉시 조치

**1. HikariCP 풀 사이즈 증설**

현재 10으로 설정된 풀 사이즈를 늘려야 한다.  
CPU 코어 수와 쿼리 특성을 고려하여 20~30 범위에서 조정한다.

```yaml
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 25
      minimum-idle: 10
      connection-timeout: 30000
      idle-timeout: 600000
```

> HikariCP 공식 권장 공식: `(core_count * 2) + effective_spindle_count`  
> 단, 무한정 늘리면 RDS 과부하로 이어지므로 RDS의 `max_connections`와 함께 검토해야 한다.

**2. 폴더트리 API 쿼리 최적화**

실행계획(`EXPLAIN ANALYZE`) 확인 후 N+1 쿼리 제거 및 인덱스를 점검한다.

```sql
EXPLAIN ANALYZE
SELECT * FROM folders WHERE workspace_id = ?;
```

---

### 🟡 단기 조치

**3. 폴더트리 응답 캐싱**

폴더 구조는 실시간성이 낮으므로 Redis 캐싱을 도입하면 DB 부하를 크게 줄일 수 있다.

```java
@Cacheable(value = "folderTree", key = "#workspaceId")
public List<FolderDto> getFolderTree(Long workspaceId) {
    // DB 조회 로직
}
```

**4. RDS 인스턴스 스펙 검토**

RDS가 t 계열(버스터블) 인스턴스라면 CPU 크레딧 소진 여부를 확인한다.  
부하 테스트 중 CPU 크레딧이 소진되면 성능이 급격히 저하된다.

---

### 🟢 중기 조치

**5. Auto Scaling 및 Read Replica 도입**

- EC2: Load Average 기준 Auto Scaling 정책 수립
- RDS: 읽기 전용 쿼리를 Read Replica로 분산

## 6. 결론

100 VUs 수준에서 이미 커넥션 풀 포화와 RDS CPU 과부하가 발생하고 있다.  
현재 임계값(p95 < 2s)은 통과했지만, **실제 트래픽 피크 또는 VU 증가 시 장애 가능성**이 있다.

우선순위는 다음과 같다:

1. **HikariCP 풀 사이즈 증설** — 가장 빠른 효과
2. **폴더트리 API 쿼리 튜닝** — 근본 원인 해결
3. **캐싱 도입** — DB 부하 분산

세 가지를 적용한 후 동일한 K6 시나리오로 재테스트하여 개선 효과를 정량적으로 검증하는 것을 권장한다.
