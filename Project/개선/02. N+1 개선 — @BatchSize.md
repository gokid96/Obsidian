# 1. 개요

이전 글에서 측정한 결과를 바탕으로 병목의 근본 원인인 DB 쿼리 수를 직접 확인하고, 개선을 진행했다.

---

## 2. 쿼리 분석

Hibernate SQL 로그로 실제 요청되는 쿼리를 확인했다.

````sql
-- 1. workspace_member 조회 (getMemberOrThrow)
select wm1_0.* from workspace_member wm1_0
left join workspace w1_0 on ...
left join users u1_0 on ...
where w1_0.workspace_id=? and u1_0.user_id=?

-- 2. 루트 폴더 조회
select f1_0.* from folder f1_0
where workspace_id=? and parent_id is null

-- 3. children LAZY 로딩 (130번 반복)
select c1_0.* from folder c1_0 where c1_0.parent_id=?

-- 4. posts LAZY 로딩 (130번 반복)
select p1_0.* from post p1_0 where p1_0.folder_id=?
```
```
docker logs $(docker ps -q) 2>&1 | grep "parent_id=?" | wc -l
130

docker logs $(docker ps -q) 2>&1 | grep "folder_id=?" | wc -l
130
```
```
1. workspace_member 조회  ← getMemberOrThrow
2. 루트 폴더 조회          ← parent_id IS NULL
3. folder where parent_id=? ← children LAZY (130번)
4. post   where folder_id=? ← posts   LAZY (130번)
─────────────────────────
총 : 262번
````

## 3. 개선

### 3-1. getMemberOrThrow — 쿼리 3번 → 1번

권한 확인을 위해 workspace → user → member 순서로 3번 조회하고 있었다.


````java
Workspace workspace = workspaceRepository.findById(workspaceId)...
Users user = userRepository.findById(userId)...
return workspaceMemberRepository.findByWorkspaceAndUser(workspace, user)...
```

`workspace_id + user_id`로 `workspace_member` 테이블에서 바로 조회하면 3가지를 **쿼리 1번**으로 확인할 수 있다.
```
workspace 존재 여부 → workspace_member에 해당 workspace_id가 있으면 존재
user 존재 여부     → workspace_member에 해당 user_id가 있으면 존재
멤버 여부          → 행이 존재하면 멤버
````

**트레이드오프**

| |Before (3번)|After (1번)|
|---|---|---|
|에러 구분|WORKSPACE_NOT_FOUND / USER_NOT_FOUND / ACCESS_DENIED|ACCESS_DENIED 단일 코드|
|쿼리 수|3번|1번|

거의 모든 CRUD마다 호출되는 메서드이기 때문에 DB 부하 절감 관점에서 1번 방식을 선택했다. 보안 관점에서도 workspace/user 존재 여부 등 내부 정보를 외부에 노출하지 않는 것이 유리하다고 판단했다.

---

### 3-2. N+1 — @BatchSize

`@OneToMany`는 기본적으로 Lazy Loading이다. 연관 컬렉션(`children`, `posts`)에 접근하는 순간 각각 쿼리가 발생하고, 트리 구조에서는 depth가 깊어질수록 쿼리가 지수적으로 늘어난다.

**N+1 해결 방법 비교**

|방법|특징|단점|
|---|---|---|
|Fetch Join|JOIN으로 한 번에 로딩|MultipleBagFetchException, depth 고정|
|@EntityGraph|어노테이션으로 간단하게|Fetch Join과 동일한 문제|
|**@BatchSize**|IN 쿼리로 묶어서 처리|depth에 종속적|
|메모리 트리 조립|쿼리 2번으로 전체 조회 후 조립|구현 복잡, 메모리 부담|

depth가 동적으로 변하는 계층 구조에서 Fetch Join과 @EntityGraph는 적용이 어렵다. 현재 서비스에서 depth가 극단적으로 깊어지는 케이스가 드물다고 판단해 **@BatchSize**를 선택했다. 실제로 문제가 발생하면 메모리 트리 조립으로 전환을 고려한다.

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "parent")
private List<Folder> children;

@BatchSize(size = 100)
@OneToMany(mappedBy = "folder")
private List<Post> posts;
```

각각 N번 나가던 쿼리가 IN절로 묶여 depth별로 1번씩 나간다.

```sql
-- Before: 130번
SELECT * FROM folder WHERE parent_id = 1
SELECT * FROM folder WHERE parent_id = 2
...

-- After: IN 쿼리로 묶음
SELECT * FROM folder WHERE parent_id IN (1, 2, 3, ..., 100)
SELECT * FROM folder WHERE parent_id IN (101, ..., 130, null, null, ...)
```

> null 패딩: Hibernate가 size=100으로 고정된 prepared statement를 재사용하기 위해 부족한 자리를 null로 채운다.

**수정 후 쿼리 확인**

```sql
-- IN 쿼리로 변경됨
select c1_0.* from folder c1_0
where c1_0.parent_id in (?,?,?, ... ,?,?,?)

docker logs $(docker ps -q) 2>&1 | grep "folder_id=?" | wc -l
0
docker logs $(docker ps -q) 2>&1 | grep "parent_id=?" | wc -l
0
```

```
1. getMemberOrThrow  → 1번
2. 루트 폴더 조회    → 1번
3. children IN 쿼리  → depth별 묶음
4. posts    IN 쿼리  → depth별 묶음
5. 루트 게시글 조회  → 1번
─────────────────────────
총 : 262번 → 8번
```

## 5. 정리

p(95) 임계값(2000ms)을 통과했고 TPS는 11.9 → 29.6으로 약 2.5배 향상됐다. 쿼리 수는 262번 → 8번으로 줄었다.

다만 `data_received`가 408MB → 1.0GB로 늘었다. TPS 증가로 더 많은 요청을 처리한 영향도 있지만, 트리 조회 시 게시글 목록에 필요하지 않은 `content(MEDIUMTEXT)` 컬럼까지 전체 조회되고 있는 문제가 여전히 남아있다. 다음 단계에서 이를 개선해볼 예정이다.
