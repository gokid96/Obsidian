# 04. 동시성 문제 — Lost Update 재현

> 이전 글에서 N+1 해결, 인덱스 최적화로 읽기 성능을 끌어올렸다.  
> 이번엔 다른 문제다. 여러 사람이 동시에 같은 게시글을 수정하면 어떻게 될까?

---

## 1. 개요

게시글 수정 API는 단순해 보인다.

1. 게시글 조회
2. 내용 변경
3. 저장

하지만 여러 요청이 **동시에** 같은 게시글을 수정하면 문제가 생긴다.  
이걸 **Lost Update(갱신 손실)** 이라고 한다.

---

## 2. Lost Update란?

```
시간  요청A                         요청B
──────────────────────────────────────────────
T1    게시글 조회 (title="무제")
T2                                  게시글 조회 (title="무제")
T3    title="요청A 수정" 저장
T4                                  title="요청B 수정" 저장  ← A의 수정이 사라짐
```

요청A와 요청B 모두 **200 OK**를 받는다.  
하지만 실제 DB에는 마지막으로 저장한 요청B의 내용만 남는다.  
요청A의 수정은 **조용히 사라진다.**

---

## 3. 재현

k6로 50명이 동시에 같은 게시글을 수정하는 시나리오를 돌렸다.

```
checks_total.......: 51
✓ 로그인 성공
✓ 200  ← 50건 전부 성공
```

50건 모두 **200 OK**를 반환했다. 하지만 DB를 확인해보면:

```sql
SELECT post_id, title, updated_at FROM post WHERE post_id = 141419;
```

```
post_id  | title               | updated_at
---------+---------------------+-------------------------
141419   | 수정된 제목 - VU 29  | 2026-03-09 14:14:41.199
```

50번 수정 요청이 모두 성공했지만 **VU 29의 결과 하나만 남았다.**  
나머지 49개의 수정은 조용히 사라졌다. 이게 Lost Update다.

---

## 4. 어떤 방법으로 해결할까?

동시성 문제를 해결하는 방법은 여러 가지다. 상황에 따라 선택이 달라진다.

| 상황                            | 선택        | 이유                   |
| ----------------------------- | --------- | -------------------- |
| 경합이 심하고 정합성 최우선 (수강신청, 재고 차감) | 비관적 락     | 확실하게 잠가서 충돌 원천 차단    |
| 경합이 낮고 성능이 중요 (게시글 수정, 설정 변경) | 낙관적 락     | 대기 없이 처리, 충돌 시에만 재시도 |
| 단순 숫자 증감 (좌석 감소, 조회수 증가)      | 원자적 업데이트  | 락 없이 한 쿼리로 정합성 보장    |
| 중복 삽입 방지 (중복 신청, 중복 가입)       | 유니크 제약조건  | DB가 알아서 거부, 로직 불필요   |
| 트래픽 폭주 대비 (선착순 이벤트)           | 큐 기반 순차처리 | 동시 접근 자체를 없앰         |

게시글 수정 특성을 보면:

- **같은 게시글을 동시에 수정하는 경우는 드물다** → 경합이 낮다
- 충돌이 발생하면 재시도하거나 사용자에게 알리면 된다
- 불필요한 대기 시간을 만들고 싶지 않다

→ **낙관적 락**이 적합하다.

**비관적 락**을 쓰면? 조회 시점에 DB 행을 잠그기 때문에 경합이 낮은 상황에서는 오히려 성능이 떨어진다. 다른 트랜잭션은 락이 풀릴 때까지 대기해야 한다.

**원자적 업데이트**는? `UPDATE post SET title = ? WHERE post_id = ?` 같은 단순 증감에는 효과적이지만, 게시글 수정처럼 여러 필드를 조회 후 변경하는 케이스에는 맞지 않는다.

**유니크 제약조건**은? 중복 삽입을 막는 데 특화되어 있다. 수정 충돌과는 다른 문제다.

**큐 기반 처리**는? 선착순 이벤트처럼 트래픽 자체를 순차화해야 할 때 쓴다. 게시글 수정에는 과하다.
