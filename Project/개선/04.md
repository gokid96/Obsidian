# 04. 동시성 문제 — Lost Update 재현

> 이전 글에서 N+1 해결, 인덱스 최적화로 읽기 성능을 끌어올렸다. 이번엔 다른 문제다. 여러 사람이 동시에 같은 게시글을 수정하면 어떻게 될까?

---

## 1. 개요

게시글 수정 API는 단순해 보인다.

1. 게시글 조회
2. 내용 변경
3. 저장

하지만 여러 요청이 **동시에** 같은 게시글을 수정하면 문제가 생긴다. 이걸 **Lost Update(갱신 손실)** 이라고 한다.

---

## 2. Lost Update란?

```
시간  요청A                         요청B
──────────────────────────────────────────────
T1    게시글 조회 (title="무제")
T2                                  게시글 조회 (title="무제")
T3    title="요청A 수정" 저장
T4                                  title="요청B 수정" 저장  ← A의 수정이 사라짐
```

요청A와 요청B 모두 **200 OK**를 받는다. 하지만 실제 DB에는 마지막으로 저장한 요청B의 내용만 남는다. 요청A의 수정은 **조용히 사라진다.**

Lost Update는 동시성 문제의 대표적인 유형 중 하나다. 동시성 문제란 여러 스레드 또는 여러 서버가 동시에 같은 자원(데이터)에 접근할 때 데이터 정합성이 깨지는 현상이다. Lost Update 외에도 Race Condition, Dirty Read, Non-Repeatable Read, Phantom Read 등이 있다.

---

## 3. 재현

k6로 50명이 동시에 같은 게시글을 수정하는 시나리오를 돌렸다.

```
checks_total.......: 51
✓ 로그인 성공
✓ 200  ← 50건 전부 성공
```

50건 모두 **200 OK**를 반환했다. 하지만 DB를 확인해보면:

```sql
SELECT post_id, title, updated_at FROM post WHERE post_id = 141419;
```

```
post_id  | title               | updated_at
---------+---------------------+-------------------------
141419   | 수정된 제목 - VU 29  | 2026-03-09 14:14:41.199
```

50번 수정 요청이 모두 성공했지만 **VU 29의 결과 하나만 남았다.** 나머지 49개의 수정은 조용히 사라졌다. 이게 Lost Update다.

---

## 4. 어떤 방법으로 해결

동시성 문제를 해결하는 방법은 레벨별로 나뉜다.

- **애플리케이션 레벨** (Java/코드 수준) - synchronized, Lock 등
- **DB 레벨** - 낙관적 락, 비관적 락 등
- **인프라 레벨** - Redis 분산 락, 메시지 큐 등


**애플리케이션 레벨**은 같은 JVM 안에서 스레드 간 동시성을 제어한다. `synchronized`, `ReentrantLock` 등이 대표적이다. 단일 서버에서는 동작하지만, 서버가 여러 대가 되는 순간 각 서버가 자기 JVM의 Lock만 알기 때문에 의미가 없어진다.

**DB 레벨**은 DB가 제공하는 메커니즘을 이용한다. 서버가 여러 대여도 같은 DB를 바라보고 있으면 동작한다. 낙관적 락, 비관적 락, 원자적 업데이트 등이 있다.

**인프라 레벨**은  
**Redis 분산 락**은 DB 트랜잭션 밖에서 락이 필요할 때 (외부 API 호출, 여러 서비스에 걸친 동시성 제어 등 MSA 환경)사용하고 **메시지 큐**는 동시 접근 자체를 없애고 순차 처리가 필요할 때 (선착순 이벤트 등) 사용된다.

 지금은 DB 레벨에서 낙관적 락과 비관적 락 중 어느 쪽이 적합한지 고민했다.
### DB 레벨 

DB가 제공하는 메커니즘을 이용하는 방식이다. 서버가 여러 대여도 같은 DB를 바라보고 있으면 동작한다.

| 상황                            | 선택        | 이유                   |
| ----------------------------- | --------- | -------------------- |
| 경합이 심하고 정합성 최우선 (수강신청, 재고 차감) | 비관적 락     | 확실하게 잠가서 충돌 원천 차단    |
| 경합이 낮고 성능이 중요 (게시글 수정, 설정 변경) | 낙관적 락     | 대기 없이 처리, 충돌 시에만 재시도 |
| 단순 숫자 증감 (좌석 감소, 조회수 증가)      | 원자적 업데이트  | 락 없이 한 쿼리로 정합성 보장    |
| 중복 삽입 방지 (중복 신청, 중복 가입)       | 유니크 제약조건  | DB가 알아서 거부, 로직 불필요   |
| 트래픽 폭주 대비 (선착순 이벤트)           | 큐 기반 순차처리 | 동시 접근 자체를 없앰         |

각 방식을 게시글 수정에 대입해봤다.

**비관적 락**은 조회 시점에 행을 잠근다. 다른 사람이 편집 중이면 수정 자체가 불가능해진다. 협업 도구에서 "지금 수정 불가"는 UX 관점에서 너무 강압적이다.

**원자적 업데이트**는 `UPDATE post SET title = ? WHERE post_id = ?` 같은 단순 증감에는 효과적이지만, 게시글 수정처럼 여러 필드를 조회 후 변경하는 케이스에는 맞지 않는다.

**유니크 제약조건**은 중복 삽입을 막는 데 특화되어 있다. 수정 충돌과는 다른 문제다.

**큐 기반 처리**는 선착순 이벤트처럼 단일 자원에 접근하는 트래픽 자체를 순차화해야 할 때 쓴다. 게시글 단위로 큐를 두는 건 과하다.

**낙관적 락**은 잠그지 않는다. 저장 시점에 version을 비교해 충돌 여부를 감지하고, 충돌이 나면 사용자에게 선택권을 준다.

VI 에디터에서 swap file이 감지되면 "이미 열려있는데 어떻게 할까요?"를 묻는 것과 같은 철학이다. 편집은 자유롭게 하되, 충돌이 생겼을 때 사용자가 판단하게 한다.

→ **낙관적 락을 선택했다.**

---

## 5. 낙관적 락 적용

`@Version`을 추가하면 Hibernate가 저장 시점에 자동으로 `WHERE post_id=? AND version=?` 조건을 추가한다. 영향받은 행이 0이면 충돌로 판단하고 예외를 던진다.

```
@Version 추가
 ↓
saveAndFlush 시점에 Hibernate가 version 체크
 ↓
충돌 시 ObjectOptimisticLockingFailureException
 ↓
GlobalExceptionHandler → 409 반환
```

`@ExceptionHandler`는 "이 예외가 발생하면 내가 처리할게"라고 등록해두는 방식이다. `@Version` 추가 전에도 이미 핸들러 코드가 존재했고, 예외가 발생하면 Spring이 자동으로 찾아서 실행한다. 코드를 별도로 건드릴 필요가 없다.

같은 k6 시나리오를 다시 돌렸다.

```
✓ 로그인 성공
✗ 200
  ↳ 14% — ✓ 7 / ✗ 43
```

```
VU 29  → 200  version: 0
VU 15  → 200  version: 1
VU 19  → 200  version: 2
VU 32  → 200  version: 3
VU 40  → 200  version: 4
VU 37  → 200  version: 5
VU 33  → 200  version: 6
나머지 43건 → 409 "다른 곳에서 수정되었습니다."
```

50건 동시 수정 중 **7건만 순차적으로 성공하고, 43건은 충돌 감지 후 409**를 반환했다. version이 0→1→2→3→4→5→6으로 순차 증가한 것도 확인됐다. Lost Update가 완전히 차단됐다.

---

## 6. 정리

|              | Before                  | After           |
| ------------ | ----------------------- | --------------- |
| 동시 수정 50건 결과 | 200 50건, Lost Update 발생 | 200 7건, 409 43건 |
| 데이터 정합성      | 마지막 쓰기만 남음              | version 순차 보장   |

409를 받은 클라이언트는 "다른 곳에서 수정되었습니다" 메시지와 함께 선택지를 받는다. 내 변경사항을 저장할지, 최신 버전을 불러올지 사용자가 직접 판단한다. 데이터를 조용히 잃는 것보다 훨씬 낫다.
