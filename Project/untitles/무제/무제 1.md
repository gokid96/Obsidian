# 백엔드 포트폴리오 수치화 가이드

> 공식: 문제 발견 → 직접 경험 → 기술 적용 → 수치로 증명

---

## 전체 로드맵

```
1단계: 모니터링 세팅         → 베이스라인 측정
2단계: DB 인덱스            → 쿼리 성능 최적화
3단계: 트랜잭션/락          → 동시성 문제 해결
4단계: N+1 / 비동기         → 서버 코드 최적화
5단계: Caffeine 로컬 캐싱   → 단일 서버 TPS 한계 확인
6단계: 스케일 아웃          → 세션 문제 직접 경험 → JWT 전환
7단계: Redis 캐싱          → 캐시 불일치 해결 + 최종 수치화
```

> 핵심 철학: 책에서 읽은 게 아니라 직접 삽질하고 트레이드오프를 선택한 개발자임을 증명하는 것

## 공통 — 모니터링 도구 세팅

모든 단계에서 공통으로 사용하는 측정 인프라입니다.

### 로컬 환경

|도구|역할|
|---|---|
|Prometheus|메트릭 수집 (응답시간, TPS, 에러율 등)|
|Grafana|수집된 메트릭 시각화 대시보드|
|k6|부하테스트 — TPS, 응답시간 Before/After 비교|
|Spring Actuator|Spring 앱 내부 메트릭 노출|

### 클라우드 환경 (AWS)

|도구|역할|
|---|---|
|CloudWatch|EC2, RDS, ElastiCache 리소스 모니터링|
|RDS Performance Insights|슬로우 쿼리, DB 부하 분석|
|CloudWatch Logs|애플리케이션 로그 수집 및 알람|

### k6 기본 부하테스트 스크립트

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 100,        // 가상 유저 수
  duration: '30s', // 테스트 시간
};

export default function () {
  const res = http.get('http://localhost:8080/api/your-endpoint');
  check(res, { 'status was 200': (r) => r.status === 200 });
  sleep(1);
}
```

측정 지표: `http_req_duration` (응답시간), `http_reqs` (TPS), `http_req_failed` (에러율)

## 2단계 — DB 인덱스로 쿼리 성능 최적화

### Before 측정

```sql
-- 슬로우 쿼리 확인
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 1 AND status = 'PENDING';

-- 확인 포인트
-- type: ALL → 풀스캔 (문제)
-- rows: 100000 → 전체 탐색 중
```

```bash
k6 run --out json=before_index.json load_test.js
```

### 기술 적용

```sql
-- 복합 인덱스 생성
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- 커버링 인덱스 (SELECT 컬럼까지 포함)
CREATE INDEX idx_orders_covering ON orders(user_id, status, created_at, total_price);
```

### After 측정

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 1 AND status = 'PENDING';

-- type: ref → 인덱스 사용
-- rows: 5 → 극적으로 감소
```

### 수치화 결과

|항목|Before|After|개선율|
|---|---|---|---|
|쿼리 응답시간|3,200ms|80ms|97.5% 감소|
|풀스캔 rows|100,000|5|99.9% 감소|
|TPS|30|850|28배 향상|

### 포트폴리오 문장

복합 인덱스 및 커버링 인덱스 적용으로 주문 조회 API 응답시간 3,200ms → 80ms로 97% 개선 (k6 동시 유저 100명 기준)

## 3단계 — 트랜잭션 & 락으로 동시성 문제 해결

### Before 측정

```java
// 문제 상황: 재고 차감 시 동시 요청으로 데이터 정합성 깨짐
@Transactional
public void decreaseStock(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.decrease(quantity); // 동시 요청 시 Lost Update 발생
}
```

```bash
k6 run --vus 500 --duration 10s concurrent_test.js
# 재고가 음수가 되는 현상 발생 확인
```

### 기술 적용

```java
// 비관적 락 적용 (경합이 높은 경우)
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Product findByIdWithLock(@Param("id") Long id);

// 낙관적 락 적용 (경합이 낮은 경우)
@Version
private Long version;
```

### 수치화 결과

|항목|Before|After|개선율|
|---|---|---|---|
|정합성 오류|500건 중 73건|0건|100% 해결|
|데드락 발생|간헐적 발생|0건|완전 제거|
|응답시간 (p99)|450ms|520ms|락 오버헤드 허용 범위|

### 포트폴리오 문장

비관적 락(SELECT FOR UPDATE) 적용으로 동시 500건 요청 환경에서 재고 차감 정합성 오류 73건 → 0건 완전 해결

## 4단계 — 서버 코드 최적화 (N+1 / 벌크 / 비동기)

### 4-1. JPA N+1 문제

```java
// Before: 주문 100건 조회 시 쿼리 101번 발생
List<Order> orders = orderRepository.findAll();
orders.forEach(order -> order.getItems().size()); // N번 추가 쿼리

// After: Fetch Join으로 쿼리 1번으로 해결
@Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.userId = :userId")
List<Order> findAllWithItems(@Param("userId") Long userId);
```

### 4-2. 벌크 연산

```java
// Before: N번 UPDATE
orders.forEach(order -> orderRepository.save(order));

// After: 1번 UPDATE
@Modifying
@Query("UPDATE Order o SET o.status = :status WHERE o.id IN :ids")
int bulkUpdateStatus(@Param("status") OrderStatus status, @Param("ids") List<Long> ids);
```

### 4-3. 비동기 처리

```java
// Before: 이메일 발송 완료까지 응답 대기 (2~3초)
public OrderResponse createOrder(OrderRequest request) {
    Order order = orderService.create(request);
    emailService.sendConfirmation(order); // 블로킹
    return OrderResponse.from(order);
}

// After: 즉시 응답, 이메일은 별도 스레드에서 처리
@Async
public void sendConfirmationAsync(Order order) {
    emailService.sendConfirmation(order);
}
```

### 수치화 결과

|항목|Before|After|개선율|
|---|---|---|---|
|N+1 쿼리 횟수|101번|1번|99% 감소|
|벌크 업데이트 시간|2,400ms|120ms|95% 감소|
|주문 생성 API 응답시간|3,200ms|320ms|90% 감소|

### 포트폴리오 문장

Fetch Join으로 N+1 쿼리 101회 → 1회 제거, @Async 비동기 처리로 주문 생성 API 응답시간 3,200ms → 320ms (90% 개선)

## 6단계 — 스케일 아웃 + 세션 문제 직접 경험 → JWT 전환

이 단계가 포트폴리오의 핵심 차별점입니다. 단순히 "JWT 썼어요"가 아니라 세션의 문제를 직접 경험하고 트레이드오프를 선택한 과정을 보여줍니다.

### 스케일 아웃 구성

```
[클라이언트]
     |
[ALB 로드밸런서]
   /       \
[EC2-1]   [EC2-2]
   \       /
   [RDS MySQL]
```

### 세션 로그인 — 문제 직접 경험

```
실험 과정

1. EC2-1에서 로그인
   → 세션이 EC2-1 메모리에 저장

2. 다음 요청이 ALB에 의해 EC2-2로 라우팅
   → EC2-2에는 세션 없음
   → 401 Unauthorized

3. 로그인이 풀리는 현상 직접 확인
```

### Redis 세션 공유 시도 — SPOF 문제 인식

```java
@EnableRedisHttpSession
public class SessionConfig { }
```

```
문제 인식

Redis 하나가 세션을 모두 관리
→ Redis 장애 발생 시
→ 전체 사용자 로그인 일괄 해제
→ 단일 장애점(SPOF) 확인
```

### JWT로 전환 — Stateless로 해결

```java
// JWT 발급
public String generateToken(Long userId) {
    return Jwts.builder()
        .setSubject(String.valueOf(userId))
        .setExpiration(new Date(System.currentTimeMillis() + EXPIRATION))
        .signWith(secretKey)
        .compact();
}

// 검증 (서버 어디로 가도 동일하게 검증 가능)
public Long validateToken(String token) {
    return Long.parseLong(
        Jwts.parserBuilder()
            .setSigningKey(secretKey)
            .build()
            .parseClaimsJws(token)
            .getBody()
            .getSubject()
    );
}
```

### 세션 vs JWT 트레이드오프

|항목|세션|JWT|
|---|---|---|
|서버 확장성|세션 공유 필요|Stateless|
|SPOF|Redis 단일 장애점|없음|
|토큰 강제 만료|서버에서 즉시 가능|만료 전까지 유효|
|탈취 시 대응|세션 즉시 삭제 가능|Blacklist 별도 필요|

JWT도 완벽하지 않습니다. 토큰 탈취 시 강제 만료가 안 됩니다. 7단계에서 Redis를 재도입하되, 이번엔 세션이 아닌 캐싱 목적으로 활용합니다.

### 포트폴리오 문장

스케일 아웃 환경에서 세션 불일치 문제를 직접 경험 후, Redis 세션 공유의 SPOF 리스크를 판단하여 JWT 기반 Stateless 인증으로 전환. 로드밸런서 환경에서 인증 안정성 확보

## 7단계 — Redis 캐싱 도입 & 캐시 불일치 해결

### 스케일 아웃 후 Caffeine 캐시 불일치 문제

```
문제 상황

EC2-1: 상품 가격 캐시 = 10,000원
EC2-2: 상품 가격 캐시 = 9,000원 (업데이트 안 됨)
→ 같은 상품인데 서버마다 다른 데이터 반환
→ Caffeine 로컬 캐시의 한계 직접 확인
```

### Redis Remote 캐싱으로 전환

```java
// Before: 로컬 캐시 (서버마다 다름)
@Cacheable(value = "products", key = "#id")

// After: Redis 원격 캐시 (모든 서버가 공유)
@Cacheable(value = "products", key = "#id", cacheManager = "redisCacheManager")
public ProductResponse getProduct(Long id) {
    return productRepository.findById(id)
        .map(ProductResponse::from)
        .orElseThrow();
}
```

```
구조 변경

EC2-1 ---> Redis (공유 캐시) <--- EC2-2
                |
           (캐시 miss)
                |
           [RDS MySQL]
```

### 캐시 주요 문제 & 해결책

|문제|원인|해결책|
|---|---|---|
|Cache Stampede|캐시 만료 시 동시 DB 요청 폭주|Mutex Lock / 확률적 만료|
|Cache Penetration|없는 키로 반복 DB 조회|Null 값 캐싱 / Bloom Filter|
|Cache Avalanche|동시 만료로 DB 과부하|TTL 랜덤 지터 적용|

```java
// Cache Avalanche 방지 — TTL 랜덤 지터
long ttl = BASE_TTL + random.nextInt(60); // 300~360초 랜덤
redisTemplate.expire(key, ttl, TimeUnit.SECONDS);
```

### 최종 수치화 결과

|항목|단일 서버 (최초)|스케일 아웃 + Redis|개선율|
|---|---|---|---|
|최대 TPS|120|310|158% 향상|
|DB 쿼리 TPS|120|9|92.5% 감소|
|API 응답시간 (p95)|850ms|45ms|94.7% 감소|
|캐시 히트율|-|92%|-|
|DB CPU 사용률|78%|12%|84% 감소|

### 포트폴리오 문장

Caffeine 로컬 캐시의 서버 간 불일치 문제를 직접 경험 후 Redis Remote 캐싱으로 전환. 스케일 아웃(EC2 2대) + Redis 캐싱으로 단일 서버 대비 TPS 120 → 310으로 158% 향상, DB 부하 92% 감소
