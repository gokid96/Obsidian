# 수치화 가이드

> **공식**: 문제 발견 → 기술 적용 → 수치로 증명 → 이력서 한 줄

---

##  전체 구조

```
Before (문제 상황 측정)
    ↓
기술 적용 (인덱스 / 트랜잭션 / N+1 해결 / Redis)
    ↓
After (개선 결과 측정)
    ↓
이력서 한 줄
```

---

##  모니터링 도구 세팅 (공통)

모든 주차에서 공통으로 사용하는 측정 인프라입니다.

### 로컬 환경

|도구|역할|
|---|---|
|**Prometheus**|메트릭 수집 (응답시간, TPS, 에러율 등)|
|**Grafana**|수집된 메트릭 시각화 대시보드|
|**k6**|부하테스트 — TPS, 응답시간 Before/After 비교|
|**Spring Actuator**|Spring 앱 내부 메트릭 노출|

### 클라우드 환경 (AWS)

|도구|역할|
|---|---|
|**CloudWatch**|EC2, RDS, ElastiCache 리소스 모니터링|
|**RDS Performance Insights**|슬로우 쿼리, DB 부하 분석|
|**CloudWatch Logs**|애플리케이션 로그 수집 및 알람|

### k6 기본 부하테스트 스크립트

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 100,        // 가상 유저 수
  duration: '30s', // 테스트 시간
};

export default function () {
  const res = http.get('http://localhost:8080/api/your-endpoint');
  check(res, { 'status was 200': (r) => r.status === 200 });
  sleep(1);
}
```

> **측정 지표**: `http_req_duration` (응답시간), `http_reqs` (TPS), `http_req_failed` (에러율)

```sql
-- 슬로우 쿼리 확인

```

### 기술 적용

```sql
-- 복합 인덱스 생성
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- 커버링 인덱스 (SELECT 컬럼까지 포함)
CREATE INDEX idx_orders_covering ON orders(user_id, status, created_at, total_price);
```

### After 측정

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 1 AND status = 'PENDING';

-- type: ref → 인덱스 사용
-- rows: 5 → 극적으로 감소
```

##  4주차 — 트랜잭션 & 락으로 동시성 문제 해결

### Before 측정

```java
// 문제 상황: 재고 차감 시 동시 요청으로 데이터 정합성 깨짐
@Transactional
public void decreaseStock(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.decrease(quantity); // 동시 요청 시 Lost Update 발생
}
```

```bash
# k6로 동시 요청 시뮬레이션
k6 run --vus 500 --duration 10s concurrent_test.js
# → 재고가 음수가 되는 현상 발생 확인
```

### 기술 적용

```java
// 비관적 락 적용
@Transactional
public void decreaseStock(Long productId, int quantity) {
    Product product = productRepository.findByIdWithLock(productId); // SELECT FOR UPDATE
    product.decrease(quantity);
}

// Repository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Product findByIdWithLock(@Param("id") Long id);
```

```java
// 낙관적 락 적용 (경합이 낮은 경우)
@Version
private Long version; // 엔티티에 버전 필드 추가
```

### After 측정

```bash
# 동시 500건 요청 후 재고 정합성 검증
k6 run --vus 500 --duration 10s concurrent_test.js
# → 재고 정합성 100% 보장 확인
```

### 수치화 결과 예시

|항목|Before|After|개선율|
|---|---|---|---|
|데이터 정합성 오류|동시 500건 중 **73건** 발생|**0건**|**100% 해결**|
|데드락 발생|간헐적 발생|0건|**완전 제거**|
|응답시간 (p99)|450ms|520ms|(락 오버헤드 허용 범위)|

###  이력서 문장

> "비관적 락(SELECT FOR UPDATE) 적용으로 동시 500건 요청 환경에서 재고 차감 정합성 오류 73건 → 0건으로 완전 해결"

## 📌 5주차 — 서버 코드 최적화 (N+1 / 벌크 연산 / 비동기)

### 5-1. JPA N+1 문제

#### Before

```java
// N+1 발생 코드
List<Order> orders = orderRepository.findAll(); // 1번 쿼리
orders.forEach(order -> {
    order.getItems().size(); // N번 추가 쿼리 발생!
});
```

```bash
# Hibernate 쿼리 로그 확인
spring.jpa.show-sql=true
# → 주문 100건 조회 시 쿼리 101번 실행 확인
```

#### 기술 적용

```java
// Fetch Join으로 해결
@Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.userId = :userId")
List<Order> findAllWithItems(@Param("userId") Long userId);

// 또는 EntityGraph 사용
@EntityGraph(attributePaths = {"items"})
List<Order> findAll();
```

#### After

```bash
# 쿼리 횟수: 101번 → 1번
# Grafana에서 DB 커넥션 사용량 확인
```

---

### 5-2. 벌크 연산

#### Before / After

```java
// Before: 반복 단건 업데이트 (N번 쿼리)
orders.forEach(order -> {
    order.updateStatus(OrderStatus.COMPLETED);
    orderRepository.save(order); // N번 UPDATE
});

// After: 벌크 업데이트 (1번 쿼리)
@Modifying
@Query("UPDATE Order o SET o.status = :status WHERE o.id IN :ids")
int bulkUpdateStatus(@Param("status") OrderStatus status, @Param("ids") List<Long> ids);
```

---

### 5-3. 비동기 처리

#### Before / After

```java
// Before: 동기 처리 — 이메일 발송이 끝날 때까지 응답 대기
public OrderResponse createOrder(OrderRequest request) {
    Order order = orderService.create(request);
    emailService.sendConfirmation(order); // 2~3초 소요
    return OrderResponse.from(order);
}

// After: 비동기 처리 — 즉시 응답 후 이메일은 별도 스레드에서 처리
@Async
public void sendConfirmationAsync(Order order) {
    emailService.sendConfirmation(order);
}
```

###  수치화 결과 예시

|항목|Before|After|개선율|
|---|---|---|---|
|N+1 쿼리 횟수|101번|1번|**99% 감소**|
|벌크 업데이트 시간|2,400ms|120ms|**95% 감소**|
|주문 생성 API 응답시간|3,200ms|320ms|**90% 감소**|

### 이력서 문장

> "Fetch Join으로 N+1 쿼리 101회 → 1회 제거, 비동기 처리(@Async) 도입으로 주문 생성 API 응답시간 3,200ms → 320ms로 90% 개선"

##  6주차 — Redis 캐싱으로 부하 분산

### Before 측정

```bash
# k6로 캐싱 전 부하테스트
k6 run --vus 200 --duration 30s cache_test.js

# Grafana에서 확인할 지표
# - DB 쿼리 횟수
# - DB CPU 사용률
# - API 응답시간
```

### 기술 적용

```java
// 로컬 캐싱 (Caffeine)
@Cacheable(value = "products", key = "#id")
public ProductResponse getProduct(Long id) {
    return productRepository.findById(id)
        .map(ProductResponse::from)
        .orElseThrow();
}

// Redis 원격 캐싱
@Cacheable(value = "popular-products", cacheManager = "redisCacheManager")
public List<ProductResponse> getPopularProducts() {
    return productRepository.findTop10ByOrderBySalesDesc()
        .stream().map(ProductResponse::from).toList();
}
```

### 대표 문제 & 해결책

|문제|원인|해결책|
|---|---|---|
|**Cache Stampede**|캐시 만료 시 동시 DB 요청 폭주|Mutex Lock / 확률적 만료|
|**Cache Penetration**|없는 키로 반복 DB 조회|Null 값 캐싱 / Bloom Filter|
|**Cache Avalanche**|동시 만료로 DB 과부하|TTL 랜덤 지터 적용|

```java
// TTL 랜덤 지터 예시 (Cache Avalanche 방지)
long ttl = BASE_TTL + random.nextInt(60); // 300~360초 랜덤
redisTemplate.expire(key, ttl, TimeUnit.SECONDS);
```

### After 측정

```bash
# k6로 캐싱 후 부하테스트
k6 run --vus 200 --duration 30s cache_test.js

# CloudWatch에서 확인
# - RDS ReadIOPS: 대폭 감소
# - ElastiCache CacheHits / CacheMisses
```

### 📊 수치화 결과 예시

|항목|Before|After|개선율|
|---|---|---|---|
|DB 쿼리 TPS|120|9|**92.5% 감소**|
|API 응답시간 (p95)|850ms|45ms|**94.7% 감소**|
|캐시 히트율|-|**92%**|-|
|DB CPU 사용률|78%|12%|**84% 감소**|

### ✏️ 이력서 문장

> "Redis 캐싱 도입으로 DB 쿼리 TPS 120 → 9로 92% 감소, 캐시 히트율 92% 달성. Cache Stampede/Avalanche 대응 전략 설계 및 CloudWatch로 개선 수치 검증"
