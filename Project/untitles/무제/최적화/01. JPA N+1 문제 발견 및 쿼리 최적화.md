## 문제 발견

폴더 목록 조회 API에서 폴더 개수만큼 쿼리가 추가로 발생하는 N+1 문제 확인. 
루트 폴더 조회 후 각 폴더의 children을 Lazy Loading으로 가져오는 과정에서
폴더 130개 → SELECT 130번 추가 발생.

```
WARN [SLOW SERVICE] FolderService.getRootFolders - 1381ms
INFO [GET] /api/v1/workspaces/6/folders - 1430ms
```

단일 API 호출에서 쿼리 **132번**, 응답 시간 **1,430ms** 확인.

---

## 원인 분석

발생한 쿼리를 분류하면 아래와 같다.

|구분|쿼리|횟수|
|---|---|---|
|권한 체크|workspace_member JOIN|1번|
|루트 폴더 조회|folder WHERE parent_id IS NULL|1번|
|N+1 — children Lazy Loading|folder WHERE parent_id = ?|130번|
|**합계**||**132번**|

원인은 `FolderResponseDTO.from()` 내부의 `folder.getChildren()` 호출. 
Lazy Loading이 걸려 있어, 폴더 하나를 DTO로 변환할 때마다 SELECT가 1번씩 추가로 발생. 
폴더가 130개 → SELECT 130번. 트리 구조 특성상 재귀 호출이 반복되는 구조.

```java
// Before: DTO 변환 시점에 Lazy Loading 발동
public static FolderResponseDTO from(Folder folder) {
    return FolderResponseDTO.builder()
            .children(folder.getChildren().stream() // 여기서 SELECT 발생
                    .map(FolderResponseDTO::from)   // 재귀 호출 → 또 SELECT
                    .collect(Collectors.toList()))
            .build();
}
```

## 해결 방법


- 폴더 + 게시글, **컬렉션이 1개**라 `MultipleBagFetchException` 위험 없음
- 페이징 없이 **워크스페이스 전체 트리를 한 번에** 내려줘야 하는 구조

컬렉션이 1개라 MultipleBagFetchException 위험 없음, 
페이징 없이 전체 트리를 한 번에 내려줘야 하는 구조로 Fetch Join이 적합하다.
### 1. Fetch Join으로 전체 폴더 + 게시글 단건 조회

```java
// FolderRepository
@Query("SELECT DISTINCT f FROM Folder f " +
        "LEFT JOIN FETCH f.posts " +
        "WHERE f.workspace.workspaceId = :workspaceId")
List<Folder> findAllByWorkspaceIdWithPosts(@Param("workspaceId") Long workspaceId);
```

`LEFT JOIN FETCH`를 통해 폴더와 게시글을 쿼리 1번으로 전부 로딩. 
`DISTINCT`로 JOIN 과정에서 발생하는 폴더 중복 제거

### 2. 메모리에서 트리 구조 조립

DB에 재귀 쿼리를 반복하는 대신, 전체 폴더를 한 번에 가져온 뒤 
`Map<folderId, DTO>`를 활용해 부모-자식 관계를 메모리에서 직접 연결.

```java
// After: 전체 폴더 로딩 후 메모리에서 트리 조립
public WorkspaceTreeResponseDTO getRootFolders(Long userId, Long workspaceId) {
    getMemberOrThrow(userId, workspaceId);
	// 로딩
    List<Folder> allFolders = folderRepository.findAllByWorkspaceIdWithPosts(workspaceId);
    List<Post> rootPosts = postRepository.findByWorkspaceWorkspaceIdAndFolderIsNull(workspaceId);

    // folderId → DTO 맵 생성 (children 빈 리스트로 초기화) 메모리에서 트리 구조 만들기
    Map<Long, FolderResponseDTO> dtoMap = allFolders.stream()
            .collect(Collectors.toMap(Folder::getFolderId, FolderResponseDTO::from));

    // 부모-자식 관계 연결
    for (Folder folder : allFolders) {
        if (folder.getParent() != null) {
            FolderResponseDTO parent = dtoMap.get(folder.getParent().getFolderId());
            FolderResponseDTO child = dtoMap.get(folder.getFolderId());
            if (parent != null) parent.getChildren().add(child);
        }
    }

    List<FolderResponseDTO> rootFolders = allFolders.stream()
            .filter(f -> f.getParent() == null)
            .map(f -> dtoMap.get(f.getFolderId()))
            .toList();

    return WorkspaceTreeResponseDTO.builder()
            .folders(rootFolders)
            .rootPosts(rootPosts.stream().map(PostSimpleDTO::from).toList())
            .build();
}
```

### 3. DTO에서 Lazy Loading 제거

```java
// After: children을 빈 리스트로 초기화, 서비스 레이어에서 직접 채움
public static FolderResponseDTO from(Folder folder) {
    return FolderResponseDTO.builder()
            .folderId(folder.getFolderId())
            .name(folder.getName())
            .parentId(folder.getParent() != null ? folder.getParent().getFolderId() : null)
            .children(new ArrayList<>())
            .posts(folder.getPosts() != null
                    ? folder.getPosts().stream().map(PostSimpleDTO::from).collect(Collectors.toList())
                    : new ArrayList<>())
            .build();
}
```

## 결과

```
DEBUG : select ... from workspace_member ...
DEBUG : select distinct ... from folder LEFT JOIN post ...
DEBUG : select ... from post ... where folder_id is null
INFO  [GET] /api/v1/workspaces/6/folders - 127ms
```

|항목|Before|After|
|---|---|---|
|총 쿼리 수|132번|3번|
|응답 시간|1,430ms|127ms|
|SLOW SERVICE 경고|발생|없음|

Fetch Join + 메모리 트리 조립 방식을 통해 쿼리 수 **97.7% 감소**, 
응답 시간 **91.1% 단축**이라는 결과를 얻었다.

워크스페이스 목록 조회에서도 동일한 N+1 패턴을 확인하여 Fetch Join으로 해결했다.

---


- Lazy Loading은 루프 내에서 연관 엔티티에 접근하는 순간 N+1로 이어진다. SQL 로그를 통한 주기적인 확인이 필요하다.
- 트리 구조는 DB 재귀 조회보다 전체 로딩 후 `Map` 기반으로 메모리에서 조립하는 방식이 효율적
- Fetch Join과 페이지네이션은 함께 사용할 수 없다.
