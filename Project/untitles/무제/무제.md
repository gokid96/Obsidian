## 핵심 용어 정리

**MVCC (Multi-Version Concurrency Control)** 데이터를 수정할 때 기존 버전을 유지하면서 새 버전을 만든다. 읽기와 쓰기가 서로 차단되지 않아 동시성이 높아진다. InnoDB는 Undo Log를 활용해 특정 시점의 스냅샷을 읽는다. 예시: 트랜잭션 A가 SELECT하는 동안 트랜잭션 B가 같은 행을 UPDATE해도, A는 B가 커밋하기 전의 버전을 읽는다.

**팬텀 리드 (Phantom Read)** 같은 트랜잭션 안에서 동일한 범위 조회를 했는데, 다른 트랜잭션의 INSERT/DELETE로 인해 결과 행의 수가 달라지는 현상이다. 예시: `SELECT * FROM orders WHERE amount > 1000` 결과가 5건이었는데, 다른 트랜잭션이 INSERT 후 다시 조회하면 6건이 되는 경우.

**Gap Lock** MySQL InnoDB에서 팬텀 리드를 방지하기 위해 실제 행이 아닌 행 사이의 간격(gap)에 잠금을 거는 기법이다. REPEATABLE READ 이상에서 동작한다. 예시: id가 10, 20인 행이 있을 때 `WHERE id BETWEEN 10 AND 20`으로 조회하면 10~20 사이 간격에 락이 걸려 그 사이에 INSERT가 불가능하다.

**데드락 (Deadlock)** 두 개 이상의 트랜잭션이 서로 상대방이 보유한 락을 기다리면서 영원히 진행하지 못하는 상태다. DB 엔진이 감지하면 하나를 강제 롤백한다. 예시: 트랜잭션 A가 행1 잠금 → 행2 요청, 트랜잭션 B가 행2 잠금 → 행1 요청 → 서로 대기하며 멈춤.

**쿼리 플랜 (Query Plan)** DB 옵티마이저가 쿼리를 실행할 때 어떤 인덱스를 타고, 어떤 순서로 데이터를 가져올지 세운 실행 계획이다. `EXPLAIN` 명령으로 확인하며, 느린 쿼리 튜닝의 출발점이다. 예시: `EXPLAIN SELECT * FROM users WHERE email = 'a@b.com'` → type이 ALL이면 풀스캔, ref면 인덱스를 타고 있다는 뜻.

## 1-1. JPA N+1 해결 수치화 (3~4일)

📚 강의: 5주차

### 선택지와 트레이드오프

|해결 방법|장점|단점|적합한 상황|
|---|---|---|---|
|**Fetch Join**|쿼리 1방으로 해결, 직관적|페이징 불가 (MultipleBagFetchException), 컬렉션 2개 이상 JOIN 불가|단건 조회, 연관관계 1~2개|
|**@EntityGraph**|어노테이션으로 간편, 메서드별 전략 다르게 적용 가능|복잡한 조건 불가, 내부적으로 LEFT JOIN이라 카테시안 곱 위험|간단한 연관관계 로딩|
|**@BatchSize**|페이징 가능, 코드 변경 최소|IN 쿼리 추가 발생 (N+1 → 1+1은 되지만 1은 안 됨)|컬렉션 페이징이 필요할 때|
|**DTO 직접 조회 (JPQL)**|필요한 컬럼만 SELECT, 가장 성능 좋음|엔티티 그래프 탐색 불가, 코드량 증가|조회 전용 API, 대량 데이터|

### UNTITLES 선택 기준

- 워크스페이스 → 폴더 → 노트 구조에서 **트리 조회가 핵심**
- 페이징이 필요한 목록과 트리 전체 조회가 공존
- **Fetch Join(트리 조회) + @BatchSize(목록 페이징)** 조합이 최적

## 1-2. DB 인덱스 튜닝 (1~2주)

📚 강의: 3주차

### 인덱스 종류별 트레이드오프

|인덱스 유형|장점|단점|적합한 상황|
|---|---|---|---|
|**단일 컬럼 인덱스**|간단, 다양한 쿼리에 활용 가능|복합 조건에서 효과 제한적|단일 조건 WHERE절|
|**복합 인덱스**|여러 조건을 한 번에 커버, 정렬도 포함 가능|컬럼 순서가 중요 (왼쪽부터 매칭), 인덱스 크기 증가|WHERE + ORDER BY 조합|
|**커버링 인덱스**|테이블 랜덤 I/O 완전 제거, 인덱스만으로 응답|인덱스 크기 매우 커짐, INSERT/UPDATE 시 오버헤드|읽기 비중 높은 조회 API|
|**Full-text 인덱스**|LIKE '%keyword%' 대체 가능|MySQL Full-text는 한글 지원 약함, 별도 설정 필요|검색 기능|

### 복합 인덱스 컬럼 순서 결정 기준

1. **동등 조건 (=)** 컬럼이 앞에 → `workspace_id`
2. **범위/정렬 조건** 컬럼이 뒤에 → `updated_at DESC`
3. **카디널리티** 높은 것이 앞에 (선택도가 좋으므로)
4. 최종: `(workspace_id, updated_at DESC)`

### 인덱스 추가 시 쓰기 성능 영향

- INSERT: 인덱스 B-Tree에도 삽입 필요 → 약 10~20% 느려짐
- UPDATE: 인덱스 컬럼 변경 시 삭제+삽입 발생
- **UNTITLES 판단**: 읽기 비중이 쓰기보다 훨씬 높은 서비스 → 인덱스 추가 이득이 큼

## 1-3. 벌크 연산 최적화 (3~5일)

📚 강의: 5주차

### 선택지와 트레이드오프

|방법|장점|단점|적합한 상황|
|---|---|---|---|
|**@Modifying JPQL**|JPA 생태계 안에서 해결, 타입 안전|영속성 컨텍스트와 동기화 안 됨 (em.clear 필요), 복잡한 조건 한계|단순 벌크 UPDATE/DELETE|
|**JdbcTemplate.batchUpdate()**|가장 빠름, 세밀한 제어 가능|JPA 영속성 컨텍스트 완전 우회, 엔티티 매핑 직접 해야 함|대량 INSERT, 성능 극한 필요 시|
|**saveAll()**|코드 간단, 영속성 컨텍스트 유지|내부적으로 개별 INSERT/UPDATE (벌크 아님), batch_size 설정해야 진짜 배치|소량 데이터, 엔티티 변경 감지 필요 시|

### 영속성 컨텍스트 동기화 문제

```
벌크 연산 실행 → DB는 변경됨 → 영속성 컨텍스트는 변경 전 상태
→ 이후 조회 시 1차 캐시에서 옛날 데이터 반환
→ 해결: em.clear() 또는 @Modifying(clearAutomatically = true)
```

### UNTITLES 선택 기준

- PublishService의 벌크 UPDATE는 단순 조건 → **@Modifying JPQL** 적합
- 이후 조회가 바로 필요 → `clearAutomatically = true` 설정

## 1-4. 동시성 문제 해결 (1~2주)

📚 강의: 4주차

### 해결 과정에서 격리 수준 먼저 검토 (포폴에 과정으로 녹이기)

락을 바로 쓰지 않고 "격리 수준을 올리면 해결되지 않을까?"를 먼저 시도. 결론적으로 안 되는 이유를 한두 줄로 정리하고, 면접에서 물어보면 깊게 설명.

```
REPEATABLE READ: MVCC 스냅샷 읽기라 동시 INSERT를 못 막음
SERIALIZABLE: 공유 락 → 동시 INSERT 시 데드락 발생
→ 격리 수준으로는 count-check-save 해결 불가, 락이 필요
```

### 락 선택지와 트레이드오프 (모놀리식 기준)

|방법|동작 원리|장점|단점|적합한 상황|
|---|---|---|---|---|
|**낙관적 락 (@Version)**|커밋 시점에 버전 비교, 불일치 시 실패|락 대기 없음, 처리량 높음|충돌 시 재시도 필요, count-check-save 패턴에는 부적합|충돌 빈도 낮은 수정 작업|
|**비관적 락 (SELECT FOR UPDATE)**|조회 시점에 행 락 획득, 다른 트랜잭션 대기|확실한 정합성 보장|락 대기시간, 데드락 위험, 처리량 저하|충돌 빈도 높거나 반드시 성공해야 할 때|
|**네임드 락 (GET_LOCK)**|MySQL 유저 레벨 락, 이름 기반|행이 아닌 논리 단위 락 가능, 데드락 없음|MySQL 의존, 단일 서버만, 타임아웃 직접 관리|리소스 생성 제한 같은 비즈니스 락|
|**유니크 제약 + 예외 처리**|DB 유니크 제약으로 중복 방지|가장 확실, 추가 코드 없음|count 기반 제한에는 적용 불가, 예외 처리 필요|중복 생성 방지 (멤버 중복 초대 등)|

### count-check-save 패턴 해결 시 선택 기준

```
Q: 왜 낙관적 락은 안 되나?
A: @Version은 "같은 행"의 수정 충돌을 감지하는 것.
   count-check-save는 "다른 행"을 새로 INSERT하는 것이라 @Version이 적용될 대상이 없음.

Q: 왜 비관적 락보다 네임드 락?
A: 비관적 락은 Workspace 행을 잠가야 하는데, 
   멤버 초대/노트 생성/폴더 생성이 모두 같은 행을 잠그면 서로 블로킹됨.
   네임드 락은 "workspace:{id}:member-invite" 같이 논리 단위로 분리 가능.
```

### 데드락 시나리오와 방지

```
비관적 락 데드락 예시:
  트랜잭션 A: Workspace 락 → Member 테이블 INSERT
  트랜잭션 B: Member 테이블 INSERT → Workspace 락 시도
  → 데드락

네임드 락은 데드락 없음:
  락 이름이 다르면 서로 독립, 같은 이름이면 순차 대기
  단, 타임아웃 필수 설정 (무한 대기 방지)
```

### UNTITLES 선택 기준

- 멤버 초대/노트 생성/폴더 생성은 **count 기반 제한** → 낙관적 락 부적합
- 각각 다른 리소스라 비관적 락은 불필요한 블로킹 → 네임드 락 적합
- 멤버 중복 초대는 **유니크 제약이 이미 있음** (WorkspaceMember 테이블) → 추가 처리 불필요
- 최종: **네임드 락(워크스페이스 단위)** + 유니크 제약(중복 방지)

## 1-5. 이메일 비동기 처리 (3~5일)

📚 강의: 5주차

### 선택지와 트레이드오프

|방법|장점|단점|적합한 상황|
|---|---|---|---|
|**@Async**|구현 간단, 별도 스레드에서 실행|트랜잭션 커밋 전에 실행될 수 있음, 실패 시 트랜잭션 롤백과 무관|트랜잭션과 무관한 작업|
|**@TransactionalEventListener**|트랜잭션 커밋 후 실행 보장, 이벤트 기반으로 결합도 낮음|트랜잭션 롤백 시 이벤트 발행 안 됨 (의도대로), 약간 복잡|트랜잭션 성공 후에만 실행해야 하는 작업|
|**메시지 큐 (Kafka/RabbitMQ)**|가장 안정적, 재시도/DLQ 내장, 분산 환경에 적합|인프라 추가 필요, 오버엔지니어링 가능|대규모 서비스, 메시지 유실 불가|

### 왜 @Async만으로는 부족한가

```
@Transactional
public void sendVerificationCode(String email) {
    verificationRepository.save(verification);  // DB 저장
    sendEmailAsync(email, code);  // @Async로 비동기 발송
}
// 문제: DB 저장이 실패해서 롤백되어도 이메일은 이미 발송됨
// → 사용자가 인증번호를 받았지만 DB에는 없는 상태
```

### UNTITLES 선택 기준

- 이메일 발송은 **DB 저장이 성공한 후에만** 실행해야 함
- 메시지 큐는 현재 규모에 오버엔지니어링
- **@TransactionalEventListener(phase = AFTER_COMMIT)** + @Async 조합이 최적
- 실패 시 재시도: `@Retryable(maxAttempts = 3)`

## 1-5-2. 트랜잭션 전파 전략 설계 (1-5과 함께 진행)

📚 강의: 4주차 — 트랜잭션

### 트랜잭션 전파 옵션 선택지

|전파 옵션|동작|장점|단점|적합한 상황|
|---|---|---|---|---|
|**REQUIRED (기본값)**|기존 트랜잭션 있으면 참여, 없으면 새로 생성|가장 직관적, 대부분의 상황에 적합|부모 롤백 시 자식도 롤백|일반적인 서비스 메서드|
|**REQUIRES_NEW**|항상 새 트랜잭션 생성, 기존 트랜잭션 보류|부모와 독립적으로 커밋/롤백|DB 커넥션 2개 점유, 성능 저하|부모 실패해도 반드시 커밋해야 할 때|
|**NESTED**|세이브포인트 생성, 자식만 롤백 가능|부모 트랜잭션 안에서 부분 롤백|JPA에서 지원 안 함 (JDBC만)|배치 처리 중 부분 실패 허용|
|**NOT_SUPPORTED**|트랜잭션 없이 실행, 기존 트랜잭션 보류|트랜잭션 불필요한 작업 분리|데이터 정합성 보장 안 됨|로깅, 외부 API 호출|
|**SUPPORTS**|기존 트랜잭션 있으면 참여, 없으면 없이 실행|유연함|트랜잭션 유무에 따라 동작 달라짐|읽기 전용 조회|

### 실제 코드에서 트랜잭션 전파가 필요한 곳

#### (1) AuthService.signup() — 회원가입

```java
@Transactional  // 하나의 트랜잭션
public LoginResponse signup(...) {
    Users savedUser = userRepository.save(user);           // 1. 회원 생성
    workspaceRepository.save(personalWorkspace);           // 2. 워크스페이스 생성
    workspaceMemberRepository.save(owner);                 // 3. 멤버 등록
    emailService.deleteVerification(request.getEmail());   // 4. 인증 데이터 삭제
}
```

**문제:** 4번 인증 삭제가 실패하면 1~3도 전부 롤백됨 → 회원가입 자체가 실패하는데, 인증 삭제는 부가 작업이라 실패해도 가입은 성공해야 함

**해결:**

```java
// EmailService에서 deleteVerification을 REQUIRES_NEW로 분리
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void deleteVerification(String email) {
    verificationRepository.deleteByEmail(email);
}
```

→ 인증 삭제가 실패해도 회원가입 트랜잭션은 영향 없음

#### (2) WorkspaceService.inviteMember() — 네임드 락 + 트랜잭션 전파

네임드 락을 적용할 때 트랜잭션 전파가 중요한 이유:

```java
// 락 서비스
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void inviteMemberWithLock(Long workspaceId, MemberInviteRequest request) {
    // GET_LOCK 획득
    // 비즈니스 로직 실행
    // RELEASE_LOCK
}
```

→ **네임드 락은 커넥션 단위**이므로 별도 트랜잭션(별도 커넥션)에서 관리해야 함 → 비즈니스 트랜잭션이 롤백되어도 락은 정상 해제되어야 하므로 REQUIRES_NEW 필수

#### (3) 이메일 비동기 발송 — @TransactionalEventListener와의 관계

```
signup() 트랜잭션 커밋
  → @TransactionalEventListener(AFTER_COMMIT)가 이벤트 수신
  → @Async로 비동기 실행
  → 이 시점에서는 이미 원래 트랜잭션이 끝남
  → 이메일 발송 중 DB 조회가 필요하면 새 트랜잭션 필요
  → REQUIRES_NEW 또는 REQUIRED (새 트랜잭션 자동 생성)
```

### 트랜잭션 전파 주의사항 (면접 단골)

```
주의 1: 같은 클래스 내 메서드 호출은 프록시를 안 탐
  → this.deleteVerification() 호출하면 REQUIRES_NEW가 무시됨
  → 반드시 다른 Bean(다른 클래스)에서 호출해야 적용

주의 2: REQUIRES_NEW는 DB 커넥션을 2개 사용함
  → 커넥션 풀 고갈 위험
  → HikariCP maximumPoolSize 설정과 함께 고려 필요

주의 3: REQUIRES_NEW에서 예외가 부모로 전파되면 부모도 롤백됨
  → 자식 예외를 try-catch로 삼켜야 부모 트랜잭션 유지
```

### 포폴 표현

```
문제: 회원가입 시 인증 데이터 삭제 실패가 회원 생성까지 롤백시킴
      네임드 락 사용 시 비즈니스 트랜잭션과 락 트랜잭션 분리 필요
해결: 부가 작업에 REQUIRES_NEW 전파 적용으로 독립 트랜잭션 분리
      네임드 락 전용 트랜잭션을 REQUIRES_NEW로 분리하여 락 해제 보장
결과: 부가 작업 실패에도 핵심 비즈니스 로직 정상 커밋
      락과 비즈니스 트랜잭션의 생명주기 분리로 안정성 확보
```

### 면접 포인트

- "REQUIRED와 REQUIRES_NEW의 차이는?"
- "같은 클래스에서 호출하면 왜 전파가 안 되나요?" → 프록시 기반 AOP 설명
- "REQUIRES_NEW의 단점은?" → 커넥션 2개 점유, 커넥션 풀 고갈 위험
- "네임드 락에서 왜 REQUIRES_NEW가 필요한가요?" → 커넥션 단위 락이라서

## 1-6. 로컬 캐시 도입 (1주)

📚 강의: 6주차

### 캐시 라이브러리 선택지

|라이브러리|장점|단점|적합한 상황|
|---|---|---|---|
|**Caffeine**|가장 빠름 (W-TinyLFU 알고리즘), Spring Cache 통합 쉬움|JVM 메모리 사용, 서버 재시작 시 유실|단일 서버, 읽기 비중 높은 서비스|
|**EhCache**|디스크 저장 가능, JCache 표준|Caffeine보다 느림, 설정 복잡|캐시 크기가 메모리 초과할 때|
|**Guava Cache**|Google 라이브러리, 안정적|Caffeine이 상위 호환, 더 이상 권장 안 됨|레거시 프로젝트|

### 캐시 전략 선택지

|전략|동작|장점|단점|적합한 상황|
|---|---|---|---|---|
|**Cache-aside (Lazy Loading)**|캐시 미스 시 DB 조회 → 캐시 저장|필요한 데이터만 캐싱, 구현 단순|첫 요청은 항상 느림 (Cold Start)|읽기 비중 높은 대부분의 서비스|
|**Write-through**|쓰기 시 DB + 캐시 동시 갱신|캐시가 항상 최신|쓰기 성능 저하, 안 쓰는 데이터도 캐싱|쓰기 후 즉시 읽기가 많을 때|
|**Write-behind**|쓰기 시 캐시만 갱신, 나중에 DB 반영|쓰기 성능 가장 좋음|데이터 유실 위험, 구현 복잡|쓰기 빈도 극히 높을 때|
|**Read-through**|캐시가 직접 DB 조회 담당|애플리케이션 코드 단순|캐시 라이브러리에 의존|캐시 프레임워크가 지원할 때|

### TTL 설정 기준

|TTL|장점|단점|적합한 대상|
|---|---|---|---|
|**짧은 TTL (1~5분)**|데이터 정합성 높음|캐시 히트율 낮음, DB 부하 여전|자주 변경되는 데이터 (노트 목록)|
|**긴 TTL (30분~1시간)**|히트율 높음, DB 부하 대폭 감소|정합성 떨어짐, 메모리 많이 사용|거의 안 변하는 데이터 (워크스페이스 설정)|
|**TTL 없음 + 이벤트 무효화**|정합성 + 히트율 모두 높음|무효화 누락 시 영구 오류, 구현 복잡|변경 시점을 정확히 알 수 있을 때|

### 캐시 무효화 전략 선택지

|방법|장점|단점|
|---|---|---|
|**TTL 만료**|가장 단순, 누락 없음|만료 전까지 옛날 데이터 응답|
|**수동 evict**|변경 시점에 즉시 무효화|evict 호출 누락 시 영구 오류|
|**이벤트 기반 무효화**|결합도 낮음, 확장 용이|이벤트 유실 가능성|

### UNTITLES 선택 기준

- 단일 서버 → **Caffeine** (가장 빠름)
- 워크스페이스 트리는 자주 변경되지만 변경 시점을 알 수 있음 → **Cache-aside + 이벤트 기반 무효화 + TTL 5분 (안전망)**
- 공개 페이지는 비로그인 반복 조회 → **Cache-aside + TTL 10분** (변경 빈도 낮음)
- 멤버 권한은 거의 안 바뀜 → **Cache-aside + TTL 30분**

## 3-1. Redis 캐시 전환 시 추가 고려사항

### 로컬 캐시 vs Redis 캐시 트레이드오프

|항목|로컬 캐시 (Caffeine)|Redis 캐시|
|---|---|---|
|**응답 속도**|~1ms (메모리 직접 접근)|~3~5ms (네트워크 홉)|
|**정합성**|서버별 캐시 불일치|공유 캐시로 정합성 보장|
|**메모리**|JVM 힙 사용|별도 Redis 메모리|
|**장애 영향**|서버 재시작 시 유실|Redis 장애 시 전체 캐시 불가|
|**확장성**|서버 수만큼 메모리 중복|캐시 하나로 공유|

### Redis 캐시 문제 사례와 해결 전략

|문제|설명|해결|
|---|---|---|
|**Cache Stampede**|TTL 동시 만료 → 다수 요청이 DB로 몰림|TTL에 랜덤 분산 (jitter) 추가, 또는 뮤텍스 락|
|**Cache Avalanche**|대량 키가 동시 만료 → DB 과부하|TTL 랜덤화, 캐시 워밍업|
|**Cache Penetration**|존재하지 않는 키 반복 조회 → 매번 DB|빈 값도 캐싱 (null 캐시), Bloom Filter|

### Stampede 해결 전략 선택지

|방법|장점|단점|
|---|---|---|
|**TTL 분산 (jitter)**|구현 단순, 효과적|완벽한 방지는 안 됨|
|**뮤텍스 락**|확실한 방지|락 경합, 구현 복잡|
|**사전 갱신 (TTL 50% 시점)**|만료 전에 미리 갱신|불필요한 갱신 가능|

### UNTITLES 선택 기준

- 트래픽 규모 고려 시 **TTL 분산**으로 충분
- 워크스페이스 트리 캐시: 기본 TTL 5분 + 랜덤 0~60초
- 공개 페이지 캐시: 기본 TTL 10분 + 랜덤 0~120초

## 3-2. 분산 락 선택지

### 분산 환경 락 전략 비교

|방법|동작 원리|장점|단점|적합한 상황|
|---|---|---|---|---|
|**Redis SETNX (직접 구현)**|SETNX로 락 획득, TTL로 자동 해제|구현 단순, 빠름|단일 Redis 장애 시 락 유실, 락 해제 타이밍 이슈|단순한 분산 락|
|**Redisson (라이브러리)**|워치독 자동 연장, 재입 가능 락|안정적, 프로덕션 검증|라이브러리 의존, 학습 비용|프로덕션 환경|
|**Redlock (다중 Redis)**|Redis N대 중 과반수 획득|단일 Redis 장애에도 안전|Redis 3대 이상 필요, 구현 복잡, 논쟁 있음 (Martin Kleppmann)|고가용성 필수|
|**ZooKeeper 분산 락**|순서 보장, 강한 일관성|가장 안정적|별도 인프라, 성능 낮음|금융 등 강한 일관성 필요|

### SETNX 직접 구현 vs Redisson

|항목|SETNX 직접 구현|Redisson|
|---|---|---|
|**구현 난이도**|간단하지만 엣지 케이스 많음|라이브러리가 처리|
|**워치독**|직접 구현 필요|자동 연장|
|**재입 가능**|직접 구현 필요|기본 지원|
|**학습 가치**|분산 락 원리 이해에 좋음|실무 적용에 좋음|

### UNTITLES 선택 기준

- 포폴 목적 → **SETNX 직접 구현**(원리 이해 증명) + **Redisson 비교**(실무 감각)
- 두 방식 모두 구현 후 k6 테스트로 성능/안정성 비교
- "직접 구현 후 Redisson으로 전환하며 차이를 확인했다"는 스토리

## 3-3. 세션 → JWT 전환

### 인증 방식 비교

|항목|세션 기반|JWT 기반|
|---|---|---|
|**상태**|서버(Redis)에 세션 저장|클라이언트가 토큰 보유, 서버 무상태|
|**확장성**|세션 수 = Redis 메모리|서버 무제한 확장|
|**요청당 비용**|매번 Redis 조회|토큰 서명 검증만 (CPU)|
|**즉시 만료**|session.invalidate()로 즉시|불가능 (만료까지 유효), 블랙리스트 필요|
|**보안**|서버가 세션 제어 가능|토큰 탈취 시 만료까지 유효|
|**장애 영향**|Redis 장애 = 전체 로그인 불가|Redis 장애 = Refresh만 영향|
|**구현 복잡도**|Spring Session으로 간단|토큰 발급/검증/갱신 직접 구현|

### JWT 토큰 전략 선택지

|전략|장점|단점|
|---|---|---|
|**Access Token만**|구현 가장 단순|만료 길면 보안 약함, 짧으면 UX 나쁨|
|**Access + Refresh**|보안 + UX 균형|Refresh 저장소 필요, 구현 복잡도 증가|
|**Access + Refresh + Rotation**|Refresh 탈취 감지 가능|가장 복잡, 동시 요청 시 이슈|

### Refresh Token 저장소 선택지

|방법|장점|단점|
|---|---|---|
|**Redis**|빠름, TTL 자동 만료, 이미 인프라 있음|Redis 장애 시 Refresh 불가|
|**DB**|안정적, 추가 인프라 불필요|매번 DB 조회, 만료 처리 직접 구현|
|**쿠키 (httpOnly)**|서버 저장 불필요|CSRF 위험, 토큰 크기 제한|

### UNTITLES 선택 기준

- **Access (15분) + Refresh (7일)** 구조
- Access Token이 짧으므로 탈취 리스크 최소화
- Refresh Token은 **Redis에 저장** (이미 인프라 있음, TTL 자동 만료)
- 로그아웃 시 Refresh Token 삭제 + Access Token 블랙리스트 (남은 TTL만큼)
- OAuth2 로그인 시에도 동일하게 JWT 발급

## 3-4. 비동기 이벤트 (선택)

### 이벤트 처리 선택지

|방법|장점|단점|적합한 상황|
|---|---|---|---|
|**ApplicationEvent**|Spring 내장, 추가 인프라 없음|서버 내부만, 이벤트 유실 가능|모놀리식, 단순 비동기|
|**Kafka**|메시지 유실 없음, 리플레이 가능, MSA 적합|인프라 복잡, 운영 부담|대규모 서비스, MSA|
|**RabbitMQ**|Kafka보다 가벼움, 라우팅 유연|Kafka만큼 안 빠름|중간 규모, 복잡한 라우팅|

### UNTITLES 선택 기준

- 모놀리식 → 분산 전환이지만 MSA는 아님
- 이벤트 종류: 캐시 무효화, 이메일 발송 정도
- **ApplicationEvent + @Async**로 충분
- 향후 MSA 전환 시 Kafka로 교체 가능하다는 확장 방향만 언급

# 면접에서 "왜?" 질문 대응 요약

|질문|답변 흐름|
|---|---|
|"왜 Caffeine을 골랐나요?"|W-TinyLFU 알고리즘으로 가장 빠르고, 단일 서버에서 Spring Cache 통합이 간편해서|
|"왜 Cache-aside 패턴?"|읽기 비중 높은 서비스고, 필요한 데이터만 캐싱하는 게 메모리 효율적이라서|
|"왜 네임드 락?"|count-check-save는 낙관적 락으로 안 되고, 비관적 락은 서로 다른 작업끼리 블로킹되니까|
|"격리 수준을 올리면 안 되나요?"|REPEATABLE READ는 MVCC 스냅샷이라 동시 INSERT를 못 막고, SERIALIZABLE은 데드락 발생. 직접 테스트로 확인함|
|"MVCC가 뭔가요?"|트랜잭션마다 스냅샷을 유지해서 락 없이 읽기를 허용하는 방식. 쓰기 충돌은 막지 못함|
|"REQUIRES_NEW는 언제 쓰나요?"|부가 작업 실패가 핵심 로직을 롤백시키면 안 될 때. 네임드 락처럼 별도 커넥션이 필요할 때|
|"같은 클래스에서 호출하면?"|Spring AOP가 프록시 기반이라 내부 호출은 프록시를 안 탐. 전파 설정이 무시됨|
|"왜 Redis로 캐시 전환?"|서버 2대에서 로컬 캐시 정합성이 깨져서, 직접 겪고 전환|
|"왜 SETNX로 직접 구현?"|분산 락 원리를 이해하기 위해, 이후 Redisson으로 전환하며 차이 비교|
|"왜 세션에서 JWT로?"|Redis 세션이 SPOF가 되는 걸 경험하고, 서버 무상태화를 위해|
|"왜 @TransactionalEventListener?"|@Async만 쓰면 트랜잭션 롤백 시에도 이메일이 발송되는 문제가 있어서|
|"왜 복합 인덱스 순서가 그렇게?"|동등 조건(workspace_id)이 앞, 정렬 조건(updated_at)이 뒤가 B-Tree 탐색에 효율적이라서|
|"왜 벌크 연산 후 em.clear()?"|영속성 컨텍스트가 DB와 동기화 안 되어 이후 조회 시 옛날 데이터가 나오니까|
