**1순위 — version 수동 비교 제거 (JPA @Version 의존)**
장점: race condition 제거, 코드 단순화 

트레이드오프: JPA가 `saveAndFlush` 시점에 충돌을 감지하므로, 그 전에 수행한 title/content 업데이트 로직이 헛돌 수 있음. 하지만 트랜잭션이 롤백되니 실제 문제는 없고, 수동 비교의 race condition보다 훨씬 안전함

**2순위 — 저장 실패 시 재시도 로직**
장점: 데이터 유실 방지, 사용자 신뢰도 향상 

트레이드오프: 재시도 중 사용자가 계속 수정하면 어떤 버전을 저장할지 복잡해짐. 재시도 횟수를 제한하지 않으면 서버 장애 시 요청 폭탄이 될 수 있음. exponential backoff + 최대 3회 정도로 제한 필요

**3순위 — 디바운스 1초 → 2~3초**
장점: 구현 비용 0 (숫자만 바꾸면 됨), 서버 부하 즉시 감소 

트레이드오프: 사용자가 저장 전에 브라우저를 닫으면 유실 구간이 1초 → 3초로 늘어남. `beforeunload`에서 즉시 저장을 시도하고 있지만, 비동기 요청이라 보장이 안 됨. `navigator.sendBeacon`으로 보완 가능

**4순위 — 로컬 캐시 Write-behind**

장점: DB 쓰기 횟수 대폭 감소 (10번 수정 → 1번 flush) 

트레이드오프: 캐시에만 있고 DB에 안 쓰인 상태에서 **서버가 죽으면 데이터 유실**. flush 주기를 짧게 하면 캐시 의미가 줄고, 길게 하면 유실 위험 증가. 또한 서버 2대 이상으로 확장할 때 로컬 캐시를 Redis로 교체해야 하는 마이그레이션 비용 발생

**5순위 — diff 전송**

장점: 네트워크 트래픽 대폭 감소. 10만 자 문서에서 한 글자 수정 시 10만 자 대신 몇 바이트만 전송 

트레이드오프: **구현 복잡도가 매우 높음**. 클라이언트와 서버 양쪽에 diff/patch 로직 필요. 충돌 해결이 현재 version 비교보다 훨씬 복잡해지고, OT/CRDT 같은 알고리즘이 필요할 수 있음. 디버깅도 어려워짐. 현재 문서 크기가 크지 않다면 ROI가 낮음

---

핵심은 **1~3순위는 리스크 대비 비용이 낮고**, 4~5순위는 **효과는 크지만 새로운 문제를 만들 수 있다**
