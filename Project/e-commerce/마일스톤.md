# 레퍼런스 대비 차이

> 개인 메모. 레퍼런스 언급 포함이므로 repo에 커밋하지 말 것.

> 레퍼런스(discphy)도 마일스톤을 그대로 안 따르고 중간에 네이밍/구조/방식을 번복함. 그래서 우리 계획과 어긋나는 지점을 정리.

  

## A. 이미 구조적으로 다른 점 (의도적, 전 커밋에 영향)

  

| 항목         | 우리                                       | 레퍼런스                                   |
| ---------- | ---------------------------------------- | -------------------------------------- |
| 패키지        | feature-by-package (`coupon/domain/...`) | layer-by-package (`domain/coupon/...`) |
| Repository | 3-tier `CoreRepository`                  | 2-tier `RepositoryImpl`                |
| 반환 타입      | `Optional` + 서비스 orElseThrow             | 엔티티 직접 + impl orElseThrow              |
| stock      | product 하위 패키지                           | 독립 도메인                                 |
| UserCoupon | CouponService에 통합                        | user 도메인 분리 (UserCouponService)        |
| 메서드명       | `Coupon.issue()`                         | `Coupon.publish()`                     |


→ 레퍼런스의 `XxxRepositoryImpl` 커밋은 우리 `XxxCoreRepository`로, 파일 경로도 전부 다르게 매핑.

  

## B. 레퍼런스가 중간에 번복/변경한 것 (계획에 영향)

1. **WithLock 네이밍 번복** — 레퍼런스: STEP05 `findWithLockBy...` → 이틀 뒤 `findByXxxWithLock + @Query`로 통일. 우리: 반대로 `findWithLockBy`로 고정(결정 가). → 우리는 "postfix 통일" 리팩토링을 **안 함**.
2. 
3. **`updateBalance` → `chargeBalance` 리네임** — 레퍼런스: week5/2에 변경. 우리: **이미 `chargeBalance`** → 리네임 커밋 불필요.

4. **Message 도메인 생성 → 대체** — 레퍼런스: STEP07 추출 → STEP08 Kafka 전환 때 제거. (우리 #43 추출 / #47 기존 제거에 반영)

5. **Outbox 구현 → 단순화** — 레퍼런스: STEP08 Outbox 구현 → 이후 수동 제거(@Transactional 없는 로직은 바로 카프카 발행). → 우리 #49도 "구현 후 정리" 형태. Outbox를 끝까지 유지 안 할 가능성.

6. **인기상품 2번 전환** — 즉석집계 → Rank(DB 배치) → Redis. (우리 #37에 두 단계로 반영)

## C. 우리 계획에서 빠지거나 달라지는 커밋

- **#29** — "WithLock postfix 통일" 커밋 없음 (우리 고정).
- **#31/#32** — "updateBalance → chargeBalance" 없음 (이미 최종).
- **#44** — 레퍼런스 "User에서 UserCoupon 제거"는 우리에 해당 없음(우린 coupon에 있음). 분리한다면 "coupon에서 UserCoupon 분리"로 바뀜.
- **payment** — 레퍼런스 `pay()`는 `PaymentInfo` 반환, 우리는 `void`. STEP07 결제완료 이벤트에서 결제 정보가 필요하면 그때 반환형 변경 가능성.

## 1. 핵심 작업 방식 (매 작업마다 반복)

1. 레퍼런스의 "내 시점" 커밋 코드를 **먼저 확인** (`git -C <ref> show <hash>`, `git log --oneline --all`).

2. 그 내용을 **내 프로젝트 구조에 맞게 변환**한 코드 제공.

3. 각 코드의 **역할 설명**을 코드 위에 첨부.

4. **레포에 직접 쓰지 않음 → 사용자가 직접 타이핑.**

   - 예외: md/문서 파일은 사용자가 "만들어줘"라고 명시하면 직접 생성 OK.

1. 브랜치 작성부터 커밋,필요하다면 푸시 메세지까지 포함해서 주기
2. 코드 줄 때 **파일 전체 경로**를 함께 제시.

3. **레퍼런스와 다른 점/이슈는 무조건 먼저 보고.**

4. **git 명령은 사용자 PowerShell에서 실행** (샌드박스 bash 쓰기 금지 → 인덱스 깨짐).

5. **커밋/PR/코드 어디에도 "레퍼런스" 언급 금지.**

  

## 2. 프로젝트 환경 (Boot 4 차이 주의)

- 스택: Spring Boot 4.0.5 / Spring Framework 7 / Java 21 / Gradle(Groovy) / JPA·Hibernate 7

- 레퍼런스는 Boot 3.x → 차이로 적응한 의존성:

  - AOP: `spring-boot-starter-aop` (Boot4에 없음) → **`spring-boot-starter-aspectj`**

  - Redisson: **`org.redisson:redisson-spring-boot-starter:4.4.0`** (4.x = Boot4 라인, POM에 spring-boot 4.0.6)

  - 웹 스타터도 `starter-web` → `starter-webmvc`

- DB: **네이티브 Windows MySQL 서비스가 3306 점유** (앱이 이걸 사용). compose로 mysql 띄우지 말 것(충돌).

- `docker-compose.yml`: **redis만** (6379). 기동: `docker compose up -d`.

- `data/`는 `.gitignore` (docker 볼륨 런타임 데이터). `git add .` 금지, 파일 콕 집어서 add.

- 테스트:

  - MySQL: `@ServiceConnection` Testcontainer (`TestcontainersConfiguration`).

  - 통합/분산락 테스트는 **로컬 Redis(6379)가 떠 있어야 통과** (레퍼런스도 동일 전제, Redis 테스트컨테이너 미사용).

  - 단위 테스트는 `@ExtendWith(MockitoExtension.class)` 직접 사용 (MockTestSupport 없음).

  - 테스트 redis 설정은 `src/test/resources/application.yaml`에 `spring.data.redis.host/port` 명시 (메인 yaml은 테스트에서 덮어써져 안 보임).
