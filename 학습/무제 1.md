**1. `DatabaseCleaner.java` 작성**

경로: `src/test/java/.../support/database/DatabaseCleaner.java`

```java
@Component
@Profile("test")
public class DatabaseCleaner {

    @PersistenceContext
    private EntityManager em;

    private final List tables = new ArrayList<>();

    @PostConstruct
    public void initTables() {
        em.getMetamodel().getEntities().stream()
            .filter(e -> e.getJavaType().isAnnotationPresent(Entity.class))
            .map(this::getTableName)
            .forEach(tables::add);
    }

    @Transactional
    public void clean() {
        em.flush();
        em.clear();
        em.createNativeQuery("SET FOREIGN_KEY_CHECKS = 0").executeUpdate();
        for (String table : tables) {
            em.createNativeQuery("TRUNCATE TABLE " + table).executeUpdate();
        }
        em.createNativeQuery("SET FOREIGN_KEY_CHECKS = 1").executeUpdate();
    }

    private String getTableName(EntityType entityType) {
        Table table = entityType.getJavaType().getAnnotation(Table.class);
        if (table != null && !table.name().isEmpty()) return table.name();
        return entityType.getName().replaceAll("([a-z])([A-Z]+)", "$1_$2").toLowerCase();
    }
}
```

> ⚠️ `DatabaseCleaner`가 `@Table(name=...)` 을 읽어서 테이블명을 찾습니다.  
> `@Table` 없는 엔티티는 클래스명을 snake_case로 변환해 사용합니다.  
> 따라서 **인덱스 작업(#27)과 함께 `@Table` 추가 후 테스트 필요**합니다.

**2. `ConcurrencyTestSupport.java` 작성**

경로: `src/test/java/.../support/ConcurrencyTestSupport.java`

```java
public abstract class ConcurrencyTestSupport extends IntegrationTestSupport {

    @Autowired
    private DatabaseCleaner databaseCleaner;

    @AfterEach
    void tearDown() {
        databaseCleaner.clean();
    }

    protected void executeConcurrency(int threadCount, Runnable runnable) {
        executeConcurrency(IntStream.range(0, threadCount)
            .mapToObj(i -> runnable)
            .toList());
    }

    protected void executeConcurrency(List runnables) {
        ExecutorService executorService = Executors.newFixedThreadPool(runnables.size());
        List<CompletableFuture> futures = runnables.stream()
            .map(r -> CompletableFuture.runAsync(() -> {
                try { r.run(); } catch (Exception e) { e.printStackTrace(); }
            }, executorService))
            .toList();
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
        executorService.shutdown();
    }
}
```

## 0. 핵심 원칙

  

- **레퍼런스(discphy/e-commerce) 타임라인을 그대로 따라간다.** 레퍼런스는 포폴용으로 *점진적으로 성장*시킨 프로젝트 — "처음부터 완벽"이 아니라 성장하듯 만든 것.

- 초기에 불완전한 코드(N+1, 미사용 enum 등)도 **레퍼런스가 그렇게 했으면 그대로 둔다.** 레퍼런스가 개선한 시점에 같이 개선한다 (**점진적 개선**).

- **효율/최적화 판단을 멋대로 끼워넣지 않는다.** ("N+1은 유지 권장" 같은 권고 금지.) 레퍼런스가 의도적으로 그렇게 했을 수 있음.

- 내가 이미 레퍼런스보다 앞서 있으면(개선본 보유), **레퍼런스 최종본**과 비교해서 "되돌렸다 다시 하는 헛수고"는 피한다.

## 1. Claude에게 코드 요청 시 규칙 (이 형식으로 줄 것)

  

- **항상 레퍼런스 해당 시점 코드를 먼저 확인하고 판단.** 기억/추측으로 답하지 말 것.

- 내 코드와 **다르면 "어디가 어떻게 다른지" 명시** (🔍 레퍼런스 대비).

- 코드 줄 때 **파일 경로를 먼저 명시.**

- 단순히 "뭐 추가" 식 금지 → **① 파일의 역할 ② 왜 추가하는지 ③ 무슨 일을 하는지**를 같이 설명.

- **동작 영향 있음/없음 + 언제 의미가 생기는지**부터 한 줄로 짚기.

- 효율/방식을 강요하지 말고 **선택지를 제시 → 내가 결정.**

- 최근 편집한 파일은 bash 마운트가 stale일 수 있음 → **Read 도구로 실제 내용 확인.**

- 산출물(커밋/PR/주석/문서)에 **"레퍼런스" 언급 금지.** 비교 설명은 대화에서만.

## 1.5 새 기능 추가 워크플로우

  

**(1) 시작할 때 — 전체 그림 먼저 + 레퍼런스 항목 전수 나열.**

코드를 바로 주지 말고, 맨 처음에 **"이 기능이 뭔지 + 어떤 흐름(데이터 흐름)으로 동작하는지 + 어떤 계층/파일을 만드는지"** 설계 개요를 먼저 설명한다.

- 엔드포인트/입출력, 호출 체인(Controller → Facade → Service → Repository), 계층별 추가 파일 목록.

- "지금 만드는 게 전체 중 어디인지" 감이 오게.

- **⚠️ 추측 금지 — 레퍼런스의 해당 항목(메서드/클래스/테스트)을 먼저 "전수 나열"하고 그대로 매칭한다.** 예: 테스트면 레퍼런스 그 시점의 테스트 파일·@Test 메서드를 모두 세어 목록화한 뒤 1:1로 맞춤. "아마 이 정도겠지"로 일부만 만들지 말 것. (개수·시나리오·단언까지 레퍼런스 기준으로 먼저 확정)

  

**(2) 진행 순서 — 작은 것부터, 매 단계 검증.**

도메인 → 인프라 → 애플리케이션 → 인터페이스. 한 계층 = 구현 + 테스트 + green → 다음. (5번 참고)

  

**(3) 결정 포인트 — 트레이드오프 설명.**

선택해야 할 지점이 나오면 **각 선택지의 장단점(트레이드오프)을 설명**하고 내가 결정하게 한다.

- 형식: `(가) 방식 — 장점 / 단점`, `(나) 방식 — 장점 / 단점`, 그리고 레퍼런스는 어느 쪽인지.

- 효율을 **강요하지 말고**, 사실(동작 영향·레퍼런스 차이·유지보수)만 주고 선택은 나에게.

  

**(4) 설명 방식 — 쉽게, 예시로.**

어려운 개념·차이를 물어보면 **추상적 설명 말고 작은 구체 예시(입력→출력)로, 같은 흐름을 나란히 따라가며 차이를 ★로 짚어** 보여준다.

- 말은 줄이고 그림/흐름처럼. 전문용어 남발 금지.

- 예: "레퍼런스 흐름 / 우리 흐름"을 같은 데이터(상품 6번·5번)로 단계별로 보여주고, 다른 지점만 ★ 표시.

## 2. 아키텍처 & 패키지 구조

  

Clean Layered Architecture + Feature-by-package. 도메인별 구조:

  

```

<domain>/

  application/      → Facade, Criteria, Result

  domain/           → Entity, Command/Info DTO, Repository(interface), Service, enum

  infrastructure/   → CoreRepository(@Component)

    jpa/            → JpaRepository

  interfaces/       → Controller

    dto/            → Request, Response

```

## 3. Repository — 3-tier 구조

  

```

domain/XxxRepository           (interface, @Repository)

  ↑ 구현

infrastructure/XxxCoreRepository   (@Component, XxxJpaRepository 주입)

  ↓ 위임

infrastructure/jpa/XxxJpaRepository (extends JpaRepository<Entity, Long>)

```

  

> 레퍼런스는 2-tier(`RepositoryImpl`)지만, 우리는 3-tier(`CoreRepository`)로 간다.

## 4. DTO 컨벤션 — **전부 @Builder로 통일**

  

- Command / Criteria / Info / Result 모든 DTO는 **`@Builder` + 정적 팩토리 `of()`**.

- 필드가 1개여도 @Builder (일관성 우선).

- 바깥 래퍼 클래스: `@NoArgsConstructor(access = AccessLevel.PROTECTED)`.

- 내부 클래스: `@Getter`, `private` 생성자 + `@Builder`, `of(...)` 정적 팩토리.

- 생성자는 `private`, 외부 생성은 `of()`로만.

  

```java

@Getter

public static class Xxx {

    private final Long id;

  

    @Builder

    private Xxx(Long id) { this.id = id; }

  

    public static Xxx of(Long id) {

        return Xxx.builder().id(id).build();

    }

}

```

  

> 정리 예정: 기존 `new` 방식(ProductInfo.Products, StockInfo.Stock) → @Builder로 통일.

## 5. 테스트 — TDD, 실무 방식

  

- **한 계층 = 구현 + 그 계층 테스트 + 실행(green) → 다음 계층.** 죽은 코드 없이 매 단계 검증.

- 순서: **도메인 → 인프라 → 애플리케이션 → 인터페이스.**

- 단위테스트 컨벤션:

  - `@ExtendWith(MockitoExtension.class)`, `@Mock` / `@InjectMocks`

  - `@DisplayName`(한글 설명), `@Test`

  - `// given` / `// when` / `// then` 주석

  - BDDMockito: `given(...).willReturn(...)`, `verify(...)`

  - AssertJ: `assertThat(...)`

## 6. Git 워크플로우

  

- **main 직접 커밋 금지.** feature 브랜치 → PR → merge.

- 브랜치명: `feat/`, `fix/`, `docs/`, `chore/`, `test/` …

- 커밋 컨벤션: `[FEAT] [FIX] [TEST] [REFACTOR] [DOCS] [CHORE]`

- 커밋 분리: 기능 / 테스트 / 문서 섞지 말 것.

- `git config core.autocrlf true` (Windows CRLF 노이즈 방지).

  

### 커밋 시점 (기능 단위)

  

- **작업 시작 전 반드시 feature 브랜치부터.** main에서 작업하다 커밋하지 말 것. (main이면 즉시 `git switch -c feat/...`)

- **하나의 기능 = 하나의 논리 단위로 커밋.** 기능이 엔드포인트까지 완성되고 테스트가 green이면 커밋한다.

  - 기능 커밋: `[FEAT] <기능명>` / 테스트 커밋: `[TEST] <기능명>` 으로 분리.

  - (한 기능을 한 [FEAT]로 묶어도 됨 — 단 기능/테스트/문서는 섞지 않기)

- **체크포인트 커밋 OK.** 변경 파일이 많이 쌓이거나(예: 10개+) 한 계층이 green이 되면, 중간에 끊어서 커밋해 작업을 보존한다. (작업 유실·꼬임 방지)

- **커밋 전 항상 `git status`로 의도한 파일만** 들어가는지 확인 (CRLF 노이즈·잡파일 배제).

- 기능 완성 후 **PR → merge**. PR 전 전체 `./gradlew build` green 확인.

  

### 이슈 ↔ PR ↔ 브랜치 (실제 구조)

  

- **이슈 구조 = 부모 이슈(STEP별, #1~#9) + 서브이슈(실제 작업 단위).** 마일스톤 = STEP.

- **한 서브이슈 = 한 브랜치 = 한 PR.** (예: 인기상품 = 서브이슈 #83 → `feat/step04-popular-products` → PR 1개)

- 한 STEP이 여러 서브이슈로 쪼개져 있으면 그 수만큼 PR. (예: 주문 = #23 도메인+단위테스트 / #24 인프라 / #25 통합테스트 → 각각 PR)

- 서브이슈가 하나면 PR도 하나. 억지로 더 쪼개지 않는다.

- PR 본문에 `Closes #<서브이슈번호>`. 부모 이슈는 서브이슈 다 닫히면 자동 정리.

- **브랜치명**: `feat/stepNN-<기능>` 식.

- **PR 제목**: `[TAG] 기능명` (이슈 제목엔 태그 없지만 PR/커밋엔 `[FEAT]` 등 태그 붙임).

- **PR 본문**: 보통 비움. 이슈 연결은 본문에 `Closes #<이슈번호>` (머지 시 이슈 자동 닫힘).

- **PR 메타**: Feature 등 라벨 + 마일스톤 + 본인 self-assign (이슈와 동일하게).

- 이슈·PR 본문에 장황한 설명 안 씀 (제목+태그+라벨로 충분).

## 7. 기술 스택 & 확정 결정

  

- **Spring Boot 4.x, Java 21, JPA/Hibernate, Gradle**

- 테스트: **Testcontainers MySQL** (`@ServiceConnection`)
