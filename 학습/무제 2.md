#### 정합성 / 동시성

```text
정합성 / 동시성
├── 1. Java/JVM 레벨 동시성 제어

│   ├── synchronized
│   │   └── 단일 JVM에서 한 번에 하나의 스레드만 임계 영역에 접근하도록 제어
│   ├── volatile
│   │   └── 한 스레드의 변수 변경 내용을 다른 스레드가 즉시 볼 수 있도록 가시성을 보장
│   ├── AtomicInteger / AtomicLong / AtomicReference
│   │   └── CAS 기반으로 락 없이 원자적인 값 변경을 수행
│   ├── java.util.concurrent
│   │   ├── Lock / ReentrantLock
│   │   │   └── synchronized보다 세밀하게 락 획득과 해제를 제어
│   │   ├── ReadWriteLock
│   │   │   └── 읽기는 동시에 허용하고 쓰기는 하나만 수행하도록 제어
│   │   ├── Semaphore
│   │   │   └── 동시에 접근할 수 있는 스레드의 개수를 제한
│   │   ├── CountDownLatch
│   │   │   └── 여러 작업이 완료될 때까지 다른 스레드의 진행을 대기
│   │   ├── CyclicBarrier
│   │   │   └── 여러 스레드가 특정 지점까지 도달할 때까지 서로 대기
│   │   ├── Phaser
│   │   │   └── 여러 단계에 걸쳐 스레드들의 작업 완료를 동기화
│   │   └── ConcurrentHashMap
│   │       └── 여러 스레드가 동시에 Map을 안전하게 사용할 수 있도록 지원
│   └── ExecutorService / Thread Pool
│       └── 스레드를 직접 생성하지 않고 재사용하며 작업 실행을 관리
│
├── 2. DB 레벨 동시성 / 트랜잭션 제어
│   ├── 원자적 UPDATE
│   │   └── 조건 확인과 데이터 변경을 하나의 DB 연산으로 처리하여 동시 수정 문제를 방지
│   ├── 비관적 락 (Pessimistic Lock)
│   │   └── 충돌을 예상하고 데이터를 먼저 잠가 다른 트랜잭션의 접근을 대기시킴
│   ├── 낙관적 락 (Optimistic Lock)
│   │   └── 충돌이 발생하지 않을 것으로 보고 처리한 뒤 충돌 여부를 검사하여 실패 처리
│   ├── Isolation Level
│   │   └── 동시에 실행되는 트랜잭션이 서로의 데이터를 얼마나 볼 수 있는지 결정
│   │   ├── READ UNCOMMITTED
│   │   │   └── 커밋되지 않은 데이터도 읽을 수 있어 Dirty Read가 발생할 수 있음
│   │   ├── READ COMMITTED
│   │   │   └── 커밋된 데이터만 읽으며 Non-repeatable Read가 발생할 수 있음
│   │   ├── REPEATABLE READ
│   │   │   └── 같은 트랜잭션에서 같은 행을 반복 조회해도 동일한 결과를 보장하도록 함
│   │   └── SERIALIZABLE
│   │       └── 트랜잭션을 직렬 실행하는 것처럼 강하게 격리하여 동시성이 가장 낮음
│   ├── DB Transaction
│   │   └── 여러 DB 작업을 하나의 작업 단위로 묶어 성공 또는 실패를 함께 처리
│   │   ├── BEGIN
│   │   │   └── 트랜잭션 시작
│   │   ├── COMMIT
│   │   │   └── 트랜잭션의 변경 내용을 최종 반영
│   │   └── ROLLBACK
│   │       └── 트랜잭션에서 수행한 변경 내용을 취소
│   ├── DB Constraint
│   │   └── DB가 잘못된 데이터가 저장되지 않도록 규칙을 강제
│   │   ├── PRIMARY KEY
│   │   │   └── 각 데이터를 유일하게 식별하고 중복을 방지
│   │   ├── UNIQUE
│   │   │   └── 특정 컬럼의 중복 값을 방지
│   │   ├── FOREIGN KEY
│   │   │   └── 테이블 간 참조 관계가 깨지지 않도록 보장
│   │   ├── NOT NULL
│   │   │   └── 필수 컬럼에 NULL 값이 저장되는 것을 방지
│   │   └── CHECK
│   │       └── 지정한 조건을 만족하지 않는 값의 저장을 방지
│   └── Database Index
│       └── 데이터 조회 성능을 향상시키며 동시 접근 시 DB 부하를 줄이는 데 도움
│
├── 3. 애플리케이션 레벨 데이터 정합성
│   ├── Idempotency (멱등성)
│   │   └── 동일한 요청을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같도록 처리
│   ├── Idempotency Key
│   │   └── 동일 요청에 고유한 키를 부여하여 중복 요청이나 중복 결제를 방지
│   ├── Deduplication
│   │   └── 이미 처리한 메시지나 이벤트를 다시 처리하지 않도록 중복 제거
│   └── State Machine
│       └── 주문·결제 등의 상태가 허용된 순서대로만 변경되도록 제한
│
├── 4. 분산 환경 동시성 제어
│   ├── Distributed Lock
│   │   └── 여러 서버가 동일한 자원에 동시에 접근하지 못하도록 분산 환경에서 하나의 락을 공유
│   │   ├── Redis Distributed Lock
│   │   │   └── Redis를 이용해 여러 서버가 공유하는 분산 락을 구현
│   │   ├── ZooKeeper Lock
│   │   │   └── ZooKeeper의 분산 합의 기능을 이용해 락을 구현
│   │   └── DB 기반 Distributed Lock
│   │       └── DB의 Lock 또는 특정 Row를 이용해 여러 서버의 접근을 제어
│   ├── Leader Election
│   │   └── 여러 서버 중 하나를 Leader로 선정하여 특정 작업을 한 서버만 수행하도록 함
│   └── Fencing Token
│       └── 오래된 Lock 보유자가 뒤늦게 작업하는 것을 토큰 검증으로 차단
│
├── 5. 메시지 / 이벤트 정합성
│   ├── Message Queue
│   │   └── 서비스 간 메시지를 중간에 저장하고 전달하여 비동기 처리와 장애 대응을 지원
│   ├── At-Least-Once Delivery
│   │   └── 메시지가 최소 한 번 전달되도록 하며 중복 전달 가능성이 존재
│   ├── At-Most-Once Delivery
│   │   └── 메시지를 최대 한 번 전달하여 중복은 줄이지만 메시지 유실 가능성이 존재
│   ├── Exactly-Once Processing
│   │   └── 메시지가 중복 처리되거나 유실되지 않은 것처럼 처리 결과를 보장하는 전략
│   ├── Retry
│   │   └── 일시적인 처리 실패가 발생하면 일정 조건에 따라 메시지나 작업을 재처리
│   ├── Dead Letter Queue (DLQ)
│   │   └── 반복적으로 처리에 실패한 메시지를 별도로 격리하여 후속 처리
│   └── Event Ordering
│       └── 이벤트가 발생한 순서에 맞게 처리되도록 보장
└── 6. 분산 트랜잭션 / 최종적 일관성
    ├── 2PC (Two-Phase Commit)
    │   └── 여러 시스템이 모두 성공적으로 커밋할 수 있는지 확인한 뒤 함께 커밋
    │   ├── Prepare
    │   │   └── 모든 참여자가 커밋 가능한 상태인지 확인
    │   └── Commit
    │       └── 모든 참여자에게 최종 커밋을 지시
    ├── Saga Pattern
    │   └── 여러 서비스의 로컬 트랜잭션을 연결하고 실패 시 보상 트랜잭션으로 이전 작업을 되돌림
    │   ├── Choreography
    │   │   └── 각 서비스가 이벤트를 발행하고 다른 서비스가 이벤트를 받아 다음 작업을 수행
    │   └── Orchestration
    │       └── 중앙 Orchestrator가 각 서비스의 작업 순서를 직접 제어
    │
    ├── Outbox Pattern
    │   └── DB 데이터 변경과 이벤트 기록을 같은 트랜잭션으로 처리하여 이벤트 유실을 방지
    ├── Inbox Pattern
    │   └── 수신한 이벤트의 처리 이력을 저장하여 동일 이벤트의 중복 처리를 방지
    ├── Transactional Messaging
    │   └── DB 변경과 메시지 전달 사이에서 발생할 수 있는 불일치를 줄이기 위한 메시징 처리 방식
    └── Compensation Transaction
        └── 이미 완료된 작업을 취소하거나 복구하는 별도의 보상 작업을 수행
```

### 큰 틀만 다시 외우면

```text
1. Java/JVM
   → 한 서버 안에서 여러 Thread가 동시에 실행될 때

2. DB
   → 여러 요청이 같은 DB 데이터를 동시에 읽고 수정할 때

3. Application
   → 중복 요청 / 중복 처리 / 잘못된 상태 변경을 막을 때

4. Distributed
   → 여러 서버가 같은 자원을 동시에 사용할 때

5. Message / Event
   → 서비스 간 메시지 유실 / 중복 / 순서 문제를 다룰 때

6. Distributed Transaction
   → 여러 서비스의 작업을 하나의 비즈니스 작업처럼 일관되게 처리할 때
```
